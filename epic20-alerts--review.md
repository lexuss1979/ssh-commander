отклонений от roadmap на месте и обоснованы. Разделение «вся математика на

## Замечания

### 1. Устаревший текст у алерта, который держится гистерезисом (средний)

`web/src/alerts.ts:107-116`

```ts
const holds = rule.active || rule.value > rule.threshold - ALERT_CLEAR_DELTA[rule.kind];
if (holds) {
  next.set(key, {
    ...existing,
    value: rule.value,
    threshold: rule.threshold,
    message: rule.message ?? existing.message,   // ← при inactive message === null
  });
}
```

Сервер заполняет `message` только при `active === true`
(`services/alerts.ts:80-84`). В зоне гистерезиса (диск упал с 93.4% до 87%,
порог 90, дельта 5) правило неактивно, но алерт держится — и в панели остаётся
исходный текст «Диск «/» занят на **93.4%** (порог 90%)». Актуальное значение
приходит в `value`, но ни колокольчик (`AlertsBell.tsx:118`), ни `title` чипа
профиля (`App.tsx:456`) его не отображают — рендерится только `message`.

Пользователь видит цифру, которой уже нет, ровно в тот период, когда ему важно
понять «падает или держится». Два варианта: рендерить строку на клиенте из
`value`/`threshold`/`kind`, либо заполнять `message` на сервере всегда (тогда
`active` остаётся отдельным флагом, а текст всегда свежий).

### 2. Алерты включены по умолчанию ⇒ фоновый опрос у всех, без opt-in (средний)

`web/src/alerts.ts:17-23` — `DEFAULT_ALERTS_SETTINGS.enabled = true`, а
`App.tsx:226`:

```ts
if (!pageVisible && !alertsSettingsRef.current.enabled) return;
```

На `main` было `if (!authed || !pageVisible) return` — скрытая вкладка
полностью останавливала опрос. Теперь у **любого** существующего пользователя
(в localStorage ключа `sc-alerts` ещё нет ⇒ дефолт) свёрнутая вкладка
продолжает бесконечно дёргать `/api/overview` + `/api/alerts`, то есть SSH-зонды
всех профилей, круглосуточно. План описывает отклонение №4 как осознанное, но
обсуждает его в связке с уведомлениями — а уведомления по умолчанию выключены
(`notify: false`), так что в дефолтной конфигурации фоновый опрос не даёт
пользователю ничего.

Предложение: либо `enabled: false` по умолчанию, либо снимать паузу только при
`notify === true` — единственный сценарий, где фоновый опрос имеет смысл.

### 3. `mergeAlertStates` — единственная stateful-логика — без тестов (средний, покрытие)

План обосновал вынос вычислений на сервер тем, что «во `web/` нет
тест-раннера», и честно записал это в риски. Но `web/src/alerts.ts` — чистый
TypeScript без импортов React и DOM (`localStorage` используется только в
`load/saveAlertsSettings`), и раннер сервера может импортировать его напрямую.
Непокрытыми остались как раз ветки, где легко ошибиться:

- активация по `>=`, снятие по `value <= threshold − delta`, дельта 0 у
  `server-down`;
- `since` сохраняется при удержании и не сбрасывается;
- `message: rule.message ?? existing.message` (см. замечание 1);
- ключи, пропавшие из ответа (профиль удалён, диск отмонтирован,
  load-правило исчезло) → `resolved` молча;
- `fired` пуст на первой синхронизации (re-baseline).

Отдельный `server/test/alerts-merge.test.ts` с импортом из `../../web/src/alerts.js`
(или мини-конфиг vitest во `web/`) закрывает это дёшево.

### 4. Прочее (низкое / нитпики)

- **«По умолчанию» сбрасывает только пороги** (`AlertsBell.tsx:196-200`):
  `enabled` и `notify` остаются как были. Кнопка обещает больше, чем делает —
  либо переименовать («Сбросить пороги»), либо сбрасывать всё.
- **`Notification.requestPermission()` только в промис-форме**
  (`AlertsBell.tsx:173`): в legacy-Safari это колбэчный API, возвращающий
  `undefined` ⇒ `perm !== 'granted'` ⇒ тумблер выключается и показывает
  «Разрешение на уведомления не выдано», даже когда оно выдано. Фикс — обёртка
  `Promise.resolve(Notification.requestPermission(cb))`.
- **Присваивание ref в теле рендера** (`App.tsx:106,108`):
  `alertsSettingsRef.current = alertsSettings; profilesRef.current = profiles;`
  — побочный эффект фазы рендера. Здесь идемпотентно и безопасно, но при
  конкурентном рендере отброшенный рендер тоже запишет ref; каноническая форма
  — синхронизация в `useEffect`.
- **Модалка настроек не закрывается по Escape.** Отказ от закрытия по оверлею
  обоснован (не терять введённые пороги), Escape обычно всё же оставляют.
- **`formatSince` считает от `Date.now()` в рендере** (`AlertsBell.tsx:18`):
  «уже N мин» обновляется только на тике опроса (10 с). На практике достаточно,
  но при открытой панели и остановленном опросе метка застынет.
- **Ручной сценарий в плане невыполним как записан**: «порог диска временно 1%»
  — и zod (`min(50)`), и инпут (`min={50}`) не пропустят значение ниже 50.
  Стоит поправить сценарий в `docs/alerts-plan.md` (например, «порог = текущая
  занятость минус 1»).
- **`resolved` из `mergeAlertStates` не используется** в `App.tsx:192`
  (деструктурируются только `next` и `fired`). Как элемент API модуля это
  нормально, просто отмечаю — уведомлений о снятии нет по плану.
- **`docs/alerts-plan.md:5`** всё ещё «Статус: план, ожидает согласования»,
  хотя roadmap уже помечен «реализовано».
- **Конфликт при слиянии**: `docs/roadmap.md` правят в одном и том же блоке обе
  ветки (19 и 20) — ожидается ручное разрешение.

## Что сделано хорошо

- Экономия SSH: `/api/alerts` действительно ложится на кэш `collectOverview`
  (4 с), и параллельный `Promise.allSettled` в одном тике гарантирует попадание
  в живой кэш — обоснование в комментарии `App.tsx:173-180` точное.
- Отдача состояний **всех** правил, а не только сработавших, — правильное
  следствие «гистерезис на клиенте»; без `value` клиент не смог бы молчать
  в зоне нечувствительности.
- Отсутствующая метрика (`null`) не порождает правила вовсе, и клиент снимает
  «пропавший» ключ молча — вселенная состояний определяется ответом. Логика
  единообразна для диска, памяти и load, покрыта тестами.
- Re-baseline на сохранении настроек и `syncedOnceRef` на первой синхронизации
  закрывают обе ловушки залпа уведомлений (F5 и подъём порога); сброс на
  logout не забыт (`App.tsx:286-288`).
- Отказ от общего `Modal` для настроек ради «не терять введённые пороги по
  клику мимо окна» — осознанный и уместный.
- `pluralCoresPrepositional` / русские склонения и `field-hint` с объяснением
  дельты — сообщения читаются человеком, а не как дамп чисел.
- Тесты роута сделаны по прецеденту `file-tail-route.test.ts`, включая три
  негативных кейса валидации (`disk=abc`, `disk=10`, `load=0`).
