# AGENTS.md — ssh-commander

Локальный веб-инструмент для управления удалённым Linux-сервером по SSH: терминал, файловый менеджер (SFTP), Docker Explorer и AI-агент. Запускается через Docker, слушает только `127.0.0.1`, защищён паролем. Интерфейс — ru/en (словари `web/src/i18n/`, переключатель в модалке «Настройки», раздел «Интерфейс»), язык агента = язык интерфейса (передаётся клиентом параметром `lang` WS-подключения агента, дефолт `ru`); локализованы и выводы инструментов/служебные заметки агента (словарь `server/src/ai/strings.ts`, ru-строки зафиксированы — на них завязаны тесты). Комментарии в коде и тесты — на английском (эпик перевода, план `docs/en-comments-plan.md`); документация — на русском; сообщения коммитов — на английском (история переведена при подготовке к публикации).

Этот файл — только правила, команды и инварианты. Детали реализации (устройство сервисов, API-маршруты, механика UI, состав unit-тестов) — в `docs/architecture.md`; заглядывай туда при работе с конкретной подсистемой.

## Быстрые команды

```bash
# Готовый образ (без сборки)
docker compose -f docker-compose.release.yml up -d
# Обновление: сначала остановка, бэкап data/ и keys/, затем осознанная смена image
docker compose -f docker-compose.release.yml pull
docker compose -f docker-compose.release.yml up -d

# Production из исходников
docker compose up -d --build        # пересборка обязательна после изменений кода
docker compose down                 # остановить

# Dev-режим в Docker: hot-reload без пересборки образа при изменении кода
scripts/docker-dev.sh up            # dev-образ (только npm ci) + запуск: API на :8081, web на :5173
scripts/docker-dev.sh logs          # логи обоих процессов
scripts/docker-dev.sh restart       # перезапуск контейнера
scripts/docker-dev.sh down

# Разработка
cd server && npm install && npm run dev   # API + WebSocket на :8080
cd web && npm install && npm run dev      # Vite на :5173, проксирует /api и /ws на :8080

# Сборка и тесты
cd server && npm run build && npm test    # tsc + vitest (unit)
cd web && npm run build                   # tsc && vite build → web/dist
cd web && npm run lint                    # eslint (react-hooks/rules-of-hooks)

# Хуки git (после clone — каталог .git/hooks не версионируется)
bash scripts/install-hooks.sh             # ставит pre-commit
```

Фронтенд собирается внутри Dockerfile автоматически — вручную собирать его для контейнера не нужно.

## Карта проекта

- `server/` — Node.js + TypeScript (ESM, strict). Express + `ws` + `ssh2`. Вход `src/index.ts`; HTTP-маршруты — `src/routes/`, бизнес-логика — `src/services/`, SSH-слой — `src/ssh/`, AI-агент — `src/ai/`, WebSocket — `src/ws/`.
- `web/` — React 18 + Vite + xterm.js. Вход `src/main.tsx`, корневой компонент `src/App.tsx`. Layout в стиле VS Code: верхний таббар разделов профиля, левый сайдбар, постоянная панель AI-агента справа. Вкладки и панель агента — keep-alive: скрываются `display:none`, не размонтируются, WS не рвётся; страницы получают prop `visible` и ставят фоновый polling на паузу при скрытии. Страницы — `src/pages/` (в т.ч. `NginxPage.tsx` — вкладка «Nginx»), переиспользуемое — `src/components/`.
- `Dockerfile` — multi-stage (`web-builder` → `server-builder` → `server-deps` → runtime `node:22-alpine`).
- `docker-compose.release.yml` — самостоятельный Compose с конкретной версией GHCR-образа, loopback-портами и прежними `./data`, `./keys`; глобального `container_name` нет. До смены способа запуска остановить прежний экземпляр, два процесса не должны писать в одни данные. Инструкции: `docs/installation.md` / `docs/installation.en.md`.
- `.github/workflows/ci.yml` → reusable `checks.yml`: обе сборки, тесты сервера, lint web и оба audit через `npm ci`, Node 22. `release.yml` публикует только существующий стабильный тег `vX.Y.Z`: автоматически по push тега либо вручную из `main` с явным `release_tag`. Проверки и образ — из разрешённого SHA этого тега, скрипты выпуска — отдельный checkout; GHCR публикуется после smoke обеих платформ (ARM64 через QEMU). Теги версий не перезаписывать; повтор использует прежний digest. Порядок выпуска — `docs/releasing.md`. Тексты GitHub Release (заголовок и заметки) — **на английском**; CHANGELOG при этом остаётся на русском.
- `docker-compose.yml` — публикация `127.0.0.1:8080:8080`, volumes `./data:/data` и `./keys:/keys`. `docker-compose.dev.yml` + `scripts/docker-dev.sh` — dev-режим с hot-reload; изменение зависимостей (package.json/lock) требует пересборки dev-стадии через `scripts/docker-dev.sh up`.
- `docs/roadmap.md` — план развития (эпики); перед каждым эпиком — детальное планирование. `docs/architecture.md` — детали реализации.
- `data/` — volume: `profiles.json` (профили, пароли открытым текстом), `db-connections.json` (подключения БД, пароли открытым текстом), `settings.json` (настройки приложения — источник правды в рантайме: `passwordHash` — scrypt-хеш пароля веб-интерфейса (опционален), `aiProvider` — пресет провайдера (`deepseek`/`openai`/`opencode-go`/`custom`), `aiApiKey`/`aiApiBase`/`aiModel` — конфиг AI-агента; сеются из env при первом старте или задаются в onboarding), `snippets.json` (сохранённые команды), `ai-dialogues.json` (диалоги агента), `ai-usage.json` (журнал расходов AI: токены и стоимость каждого вызова), `ai-prices.json` (опциональный оверрайд цен моделей — справочник, битый файл не блокирует запись), `memory/<profileId>/MEMORY.md` (память агента).
- `keys/` — SSH-ключи, монтируются в контейнер в `/keys` (в образ не копируются); импорт через UI сохраняет с правами 0600.
- `server/test/` — unit-тесты (vitest) и ручные сценарии (`*.manual.mjs` / `*.manual.ts`).

## Конфигурация (env)

Задаётся через `.env` (шаблон — `.env.example`), в контейнере — через `environment` в compose.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_PORT` / `APP_HOST` | `8080` / `127.0.0.1` | Порт и адрес HTTP/WS сервера. Дефолт петлевой; `0.0.0.0` нужен только внутри контейнера и задан `ENV` в Dockerfile — при не-петлевом адресе сервер печатает предупреждение |
| `APP_PASSWORD` | пусто | Пароль входа в веб-интерфейс. **Только seed при первом старте** (копируется хешем в `data/settings.json`; пусто — пароль задаётся в UI через onboarding); дальше — только `data/settings.json` (смена — страница «Настройки»), изменение env после первого старта ни на что не влияет |
| `DATA_DIR` | `/data` (docker) | Каталог с `settings.json`, `profiles.json`, `db-connections.json`, `ai-dialogues.json` и `memory/` |
| `KEYS_DIR` | `/keys` (docker) | Каталог с SSH-ключами |
| `WEB_DIST` | авто-определение | Путь к собранному фронтенду |
| `AI_API_BASE` | `https://api.deepseek.com/v1` | Базовый URL OpenAI-совместимого API. **Только seed при первом старте** (вместе с ключом определяет пресет провайдера); дальше — только `data/settings.json` (смена — страница «Настройки») |
| `AI_API_KEY` | пусто | Ключ API; без него (ни в settings, ни в seed) агент недоступен. **Только seed при первом старте**; дальше — только `data/settings.json` (смена/очистка — страница «Настройки», без рестарта) |
| `AI_MODEL` | `deepseek-v4-flash` | Модель агента. **Только seed при первом старте**; дальше — только `data/settings.json` (смена — страница «Настройки») |
| `AI_MAX_STEPS` | `30` | Лимит шагов цикла агента |
| `AI_TEMPERATURE` | `0.2` | Температура модели |
| `AI_SEARCH_API_BASE` | пусто | Anthropic-совместимая база веб-поиска для агента (env-only). У пресета DeepSeek (`aiProvider` в settings) поиск включён автоматически — константный endpoint `https://api.deepseek.com/anthropic`, тот же ключ; этот env нужен только остальным провайдерам (например, связка «чат OpenAI + поиск DeepSeek»). Пусто и не DeepSeek — поиск выключен, инструмент `web_search` модели не объявляется |
| `AI_SEARCH_MODEL` | `deepseek-v4-flash` | Модель для веб-поиска (серверный инструмент `web_search_20260209`) |
| `TUNNEL_PORT_MIN` / `TUNNEL_PORT_MAX` | `10000` / `10049` | Диапазон портов для SSH-туннелей (локальный конец). В Docker compose публикуется на `127.0.0.1` |

`WEB_DIST`/`KEYS_DIR` при локальном запуске определяются относительно расположения модуля (работает и локальная раскладка `server/dist`, и docker-раскладка `/app/dist`); явный env всегда приоритетнее.

## Правила работы с кодом

- TypeScript strict; сервер — ESM, относительные импорты с расширением `.js`; фронтенд — `noUnusedLocals`, `noUnusedParameters`.
- Пути в API: абсолютные, нормализация `//` и хвостового `/`; операции удаления запрещают `/` и `..` (`src/util/path.ts`); рекурсивное удаление использует `rm -rf -- <shq(path)>`.
- Секреты: ключи, `.env` и `data/profiles.json` в git не попадают (`.gitignore`); не добавлять их в коммиты и не логировать содержимое.
- Docker-сборка: при изменении сервера/фронта контейнер пересобирается через `docker compose up -d --build`; `WEB_DIST` в Dockerfile задан явно — не удалять.
- Интерфейс: тёмная и светлая темы на CSS-переменных (`web/src/styles.css`, атрибут `data-theme` на `<html>`), переключатель в модалке «Настройки» (раздел «Интерфейс»), выбор сохраняется в `localStorage`; язык ru/en — словари `web/src/i18n/` (`ru.ts`/`en.ts`, `en` типизирован как `typeof ru`), `t()`/`useT()` из `i18n`, переключатель рядом с темой, выбор в `localStorage` `sc-lang`, дефолт из `navigator.language`; **новая UI-строка добавляется в оба словаря сразу** (паритет гарантируют типы и `server/test/i18n.test.ts`), детали — `docs/i18n-execution-plan.md`; скроллируемые области используют `scrollbar-gutter: stable` против дёргания layout. Всё настроечное сведено в модалку «Настройки» (`web/src/components/SettingsModal.tsx`, шестерёнка в футере сайдбара): разделы «Интерфейс» (тема/язык), «Безопасность» (пароль), «AI-агент» (ключ/модель), «Расходы AI» и «Алерты» (пороги).
- Git: репозиторий инициализирован в корне проекта, ветка `main`.

## AI-агент: правила и инварианты

Два класса инструментов:
- Read-only (выполняются автоматически): `exec_readonly, read_file, read_memory, list_dir, docker_ps, docker_logs, docker_inspect, security_audit, disk_usage, web_search, list_servers` (`web_search` — только когда поиск настроен; запрос уходит во внешний поисковый API — приватный нюанс, отключается сменой провайдера/env).
- Мутирующие: `exec, write_file, write_memory, docker_action, connect_server`. В режиме `always` никогда не выполняются без approve/reject в UI; режимы `needed` (дефолт) и `never` осознанно сужают этот барьер — см. «Уровень доступа агента» ниже.

Если расширяешь набор инструментов — обязательно:
1. добавь определение в `src/ai/tools.ts`,
2. добавь имя в `READ_ONLY_TOOLS` (если read-only) и обработчик в `runTool` в `src/ai/agent.ts`,
3. если инструмент исполняет произвольный shell — проверь, что он не попал в read-only класс без проверок guard.

- `exec_readonly` фильтруется **allow-листом** в `src/ai/guard.ts` (только читающие утилиты; запрещены конвейеры/редиректы/подстановки/интерпретаторы и все сетевые клиенты). Allow-лист консервативен — лучше отказать, чем пропустить; чего в нём нет, идёт через `exec` с подтверждением. Результат `exec`/`exec_readonly` всегда содержит exit code; ненулевой код возвращается модели как ошибка. История замены deny-листа — `docs/architecture.md`.
- Уровень доступа агента (план `docs/agent-access-levels-plan.md`, ревизия v2): режим **per-dialogue** — поле `approvalMode` в `ai-dialogues.json`; глобальных настроек режима нет. **Дефолт `needed` — и для новых, и для всех существующих диалогов без поля** (миграция чтением; осознанное понижение барьера относительно v1, подтверждено пользователем — не считать регрессией). `needed` — авто только низкорискованные мутации (`write_memory`; `docker_action` кроме удаляющих `rm`/`rmi`; `write_file` с каноничным абсолютным путём вне системных и sensitive-путей), `exec` и `connect_server` — approve в любом режиме, кроме `never`. `never` (Full Access) — всё без подтверждений, включается **только** с `riskAcknowledged: true` в том же WS-фрейме `set_approval_mode` (иначе WS `error`, режим не меняется); UI — селектор у поля ввода панели агента + модалка `AgentAccessConfirm` с probe привилегий домашнего профиля (`GET /api/profiles/:id/privileges`; root/sudo/ошибка probe → усиленное предупреждение с обязательным чекбоксом «Я осознаю возможные риски»). Классификация — чистая `needsApproval()` в `src/ai/approval.ts` (неизвестный инструмент — fail-closed → approve); решение принимает `runLoop` **на каждый вызов** — смена режима действует на лету, висящий `tool_pending` не трогается. В `never` отключается только пауза на подтверждение: `redactSecrets`, allow-лист guard, таймауты и лимиты вывода неизменны. Авто-выполненный мутирующий вызов помечается `autoApproved` в `tool_start`. Детали — `docs/architecture.md`.
- Мульти-серверный режим: диалог привязан к домашнему профилю, остальные серверы подключаются (`attach_server`/`connect_server`, хранятся в `extraProfileIds`). Инструменты выполняются только на подключённых серверах (`resolveServer` в `agent.ts`); память и sudo-пароли — per-profile. Подробности — `docs/architecture.md`.
- `security_audit` — детерминированный белый список read-only команд (`src/services/security-audit.ts`), произвольный shell не принимает. Sudo-пароль приходит через WS `sudo_credentials`, хранится только в памяти сессии, не логируется, не сохраняется и не передаётся модели.
- Режим планирования (`planMode`, `src/ai/plan.ts`): запрос к API идёт без tools, `approve_plan` запускает обычный цикл с инструментами; шаги планирования не расходуют `AI_MAX_STEPS`. Язык сессии — параметр WS-подключения (`lang`, дефолт `ru`). Выводы инструментов и служебные заметки — на языке сессии: словарь `src/ai/strings.ts`, **ru-значения — дословно зафиксированные литералы (их менять нельзя: на них завязаны тесты)**, паритет ключей ru/en проверяет `server/test/ai-strings.test.ts`. Описания инструментов в `ai/tools.ts` двуязычны (`buildToolDefs(lang)`), ru-значения тоже заморожены (паритет — `server/test/agent-lang.test.ts`). Исключения: `guard.reason` — английский; заголовок-сентинел «Новый диалог» не переводится (persisted-данные).
- Учёт расходов: каждый платный вызов (`chat`/`plan`/`web_search`) с usage пишется в `data/ai-usage.json` (`src/ai/usage.ts`); ошибки журнала не роняют цикл агента; цены — `src/ai/pricing.ts` + оверрайд `data/ai-prices.json`. Подробности — `docs/architecture.md` (раздел «Учёт расходов AI»).
- Подсказка вероятного ответа `[[SUGGEST]]` (план — `docs/agent-suggest-plan.md`): маркер вырезается до персиста и контекста следующих ходов (`src/ai/suggest.ts`); модель не подсказывает согласие на необратимое; **автоотправки нет никогда — Enter всегда нажимает пользователь**. Механика — `docs/architecture.md`.

### Память агента (MEMORY.md)

- Для каждого профиля память хранится в `DATA_DIR/memory/<profileId>/MEMORY.md` (`src/ai/memory.ts`). Это локальная память приложения, к удалённому серверу отношения не имеет; имя файла — санитизированный `profileId`, выход за `memory/` невозможен. Запись атомарная (tmp+rename), чтение для контекста ограничено 64 КБ.
- Содержимое подгружается в системный промпт в начале каждой сессии.
- `read_memory` — read-only, автоматически; `write_memory` — мутирующий (в `needed`/`never` может выполняться автоматически — см. «Уровень доступа агента»; запись в любом случае проходит `redactSecrets`) и принимает полный новый текст файла (агент обязан сохранять прежние записи). Инструменты памяти нельзя заменять на `exec`/`write_file`.

## Неочевидные инварианты

Детали реализации каждого пункта — в `docs/architecture.md`; здесь — только правила.

- Одноразовые подсказки («did you know», план — `docs/feature-discovery-plan.md`): страница обязана вызвать `markTipSeen(id)` **и** скрыть баннер своим рендером — `TipBanner` проверяет флаг только при маунте; битый localStorage → подсказка показывается.
- Хранилища JSON (`profiles.ts`, `db-connections.ts`, `ai/dialogues.ts`, `ai/usage.ts`, `snippets.ts`): zod-валидация, атомарная запись tmp+rename. Битый JSON переименовывается в `*.corrupt-<timestamp>`, persist отказывается перезаписывать файл до рестарта — молчаливого затирания нет. Исключение — `ai/pricing.ts` (`ai-prices.json` — справочник: битый файл → warn + дефолты).
- Единая модель настроек (план — `docs/settings-model-plan.md`, эпики 22–23): источник правды — `data/settings.json`. Env (`APP_PASSWORD`, `AI_API_KEY/BASE/MODEL`) читается **один раз при первом старте** (`seedSettingsFromEnv()`, скрытая миграция) и дальше — никогда. Рантайм читает AI-конфиг только через `getAiSettings()`; `verifyPassword` — только хеш из settings, без env-фолбэка (битый формат — fail-closed); `updateSettings(patch)` — мерж-патч, null/undefined удаляет поле (возврата к env нет).
- Страница «Настройки» (`routes/settings.ts`, **с** `requireAuth`): ключ API наружу **никогда не возвращается** (только `apiKeySet`); смена пароля — только парой `currentPassword`+`newPassword`; AI-конфиг — только целиком, ключ write-only; `aiApiKey: null` — очистка ключа (агент недоступен); пустой патч → 400. Сессии при смене пароля не инвалидируются. Смена секретов после первого старта — только через эту модалку или правкой файла + рестарт.
- Веб-поиск (`ai/web-search.ts`): у пресета DeepSeek включён автоматически (константный `DEEPSEEK_SEARCH_BASE` — менять/выносить в настройки нельзя, только он поддерживает серверный `web_search`); у остальных провайдеров — только env `AI_SEARCH_API_BASE`/`AI_SEARCH_MODEL` (env-only).
- Onboarding (`routes/setup.ts`, без `requireAuth`): триггер — отсутствие `passwordHash` в settings; запись — **мерж поверх текущих settings** (посеянные AI-поля не затираются); доступен только пока required (409 после успеха), rate-limit общий с логином, после записи — авто-вход.
- Учёт расходов AI: стоимость фиксируется в момент вызова; `usage` НЕ кладётся в `ChatMessage` (иначе попадёт в persisted-диалог) — составной возврат `{message, usage?}`; привязка затрат — домашний профиль диалога + локальная дата; прерванный стрим не учитывается (итоги занижены на прерванные вызовы).
- SFTP — только promise-обёртки из `src/ssh/sftp.ts`, не сырые callback-методы ssh2.
- `src/ssh/manager.ts` — постоянные подключения на профиль, параллельные `getClient` делят один connect. **Ключ хоста проверяется** (`hostVerifier` → `services/known-hosts.ts`, TOFU): несовпадение обрывает подключение (без проверки подмена DNS забирала пароль профиля молча). `keyPath` открывается только внутри `KEYS_DIR`. `exec`: 60 с / 2 МБ, опциональный `stdin` (пароль sudo). `execStream`: `handle.code` резолвится на всех терминальных путях — потребитель вешает `.then` сразу.
- Docker по SSH (`src/services/docker.ts`): команда из `dockerCommand` профиля + `shq`-экранирование; команда контейнера в `run` оборачивается в `sh -c`. Compose — только v2 (`docker compose`), v1 отклоняется.
- Профили наружу отдаются **без секретов** (`toSafeProfile`): флаги `hasPassword`/`hasKeyPassphrase`; форма не подставляет секрет, пустое поле = «не менять». Update: непереданный секрет сохраняется; при смене `authType` новый секрет обязателен (то же у подключений БД). Экспорт бэкапа: `includeSecrets` по умолчанию выключен, с секретами обязателен `passphrase`. Замена `logPaths` — отдельный PUT без разрыва SSH-подключения.
- Подключения БД (эпик 12): пароль передаётся **первой строкой stdin** канала — не в argv, не в env; `\n`/`\r` в пароле отклоняются. Тумблер «только чтение» — серверный SET, защита от случайности, не от намеренного. Подробности — `docs/architecture.md`.
- Живой просмотр логов и follow-стримы: общий лимитер `services/stream-limits.ts` — 3 слота на профиль **суммарно по всем подсистемам** (tail, docker logs, journalctl, packages apply); слот снимается на любом пути завершения, идемпотентно. Backpressure — `createChunkGate` (дроп чанков с маркером), не пауза SSH-канала.
- Метрики/порты/cron/nginx — кэш 2 с на профиль. История нагрузки — in-memory, пишется хуком внутри `collectMetrics`: собственный опрос не нужен, историю кормят запросы `/api/metrics` и `/api/overview`.
- Алерты по порогам (эпик 20): сервер считает чистой функцией поверх кэша overview (новых SSH-вызовов нет), ответ — все правила; гистерезис живёт на клиенте (`web/src/alerts.ts`); настройки — localStorage, на сервере не персистятся. Не превращать в систему мониторинга.
- Вкладка «Nginx» (план — `docs/nginx-plan.md`): источник данных — только `nginx -T` (fallback на пофайловое чтение не делаем); reload — только после зелёного `nginx -t`; `nginx -t`/`-v` пишут в stderr — вывод читаем оттуда.
- SSH-туннели — in-memory реестр без персистентности; локальный конец слушает на `127.0.0.1`, диапазон `TUNNEL_PORT_MIN`–`TUNNEL_PORT_MAX`.
- Мутации crontab — только пользовательского (`crontab -`), с защитой от гонки через `expectedRaw` (409 при расхождении); системные файлы read-only.
- Службы systemd (эпик 13): имя unit'а валидируется regex `^[A-Za-z0-9@._:\-]+$` (плюс запрет `.`/`..`) до всего остального. Sudo — **прямая форма `sudo -S -p '' -- …` без `sh -c`**, пароль первой строкой stdin (зонд и классификация — общий `services/sudo.ts`); ретрай по access-denied безопасен. Ошибки: 400 — пользовательские причины, 502 — только транспорт. Sudo для журнала не делается; отказ journalctl без прав — пустой вывод с кодом 0 (UI показывает подсказку).
- Терминальные вкладки (эпик 15): лимит 4 живых сессий на профиль (бюджет SSH `MaxSessions`); `tabId` из WS-query, невалидный → `close(1008)`. Запись удаляется при выходе из shell. На фронте `close`-фрейм серверу шлётся **только по явному закрытию вкладки пользователем** — смена профиля размонтирует страницу, и безусловный close убивал бы все терминалы.
- «Что занимает» (эпик 16): команды du/find собирает сервис — конвейеры и `2>/dev/null` допустимы, guard `exec_readonly` их не видит. `du -x -d 1 -k`; stderr не глушится — отказы доступа дают `incomplete: {unreadable}`. Ошибки: 400 — пользовательские причины (включая таймаут du/find), 502 — только транспорт. Исполнители принимают `deps {execFn?, ...}` (паттерн systemd.ts).
- Действия над процессами (эпик 17): pid — каноничное целое 2..4194304 (**запрет 0/1/отрицательных обязателен**: `kill -TERM -1` кладёт всё); сигнал — whitelist-enum; `kill` **без `--`**; sudo — через `services/sudo.ts`; после мутации — `invalidateMetricsCache`. Инструмент агента не заводится (`kill`/`pkill` в deny-листе guard осознанно).
- Сохранённые команды (эпик 18): `POST /api/snippets/run` — **команда передаётся в exec как есть, без фильтрации и `shq`**: это ручной инструмент уровня терминала, защита — подтверждение в UI со списком целей. Все цели валидируются до первого exec; таймаут 120 с на профиль; вывод обрезается до 100 КБ на поток.
- Обновления пакетов (эпик 19): `apt-get update` не запускается (мутация индексов); у dnf/yum код 100 = есть обновления, не ошибка. Применение — **только стримом с подтверждением**: зонд `probeSudo` до открытия канала, прямая sudo-форма без `sh -c`, пароль первой строкой stdin, слот общего лимитера follow-стримов (429). Стрим применения не рвётся переключением вкладок.
- Bootstrap «Новый сервер (root + пароль)» (`services/bootstrap.ts`, план — `docs/bootstrap-plan.md`): жёсткий порядок «сначала ключ — потом sshd» — sshd не трогается, пока вход ключом не доказан отдельным подключением; reload только после зелёного `sshd -t`; провал после правки → откат; пароль живёт только в памяти запроса; ключ — отдельный ed25519 на сервер (0600, свой энкодер OpenSSH-формата).
- Перед сдачей изменений: `npm run build` в обоих каталогах и `npm test` — зелёные, `npm audit` без уязвимостей.
- Эти проверки автоматизированы хуком `pre-commit` (`scripts/pre-commit.sh`, ставится `bash scripts/install-hooks.sh`): eslint web, `tsc --noEmit` server, vitest, сборка web. Падает только на ошибках — `exhaustive-deps` остаются предупреждениями. Пропустить разово: `git commit --no-verify`. Проверяется рабочее дерево, а не индекс.

- `cd web && npm run lint` — eslint во фронтенде. Заведён ради `react-hooks/rules-of-hooks`: хук, вызванный после раннего `return`, даёт React #310 («Rendered more hooks than during the previous render») уже в браузере — ни `tsc`, ни тесты сервера этот класс не видят. Тестов у фронтенда нет, линтер — единственная автоматическая защита.

## Безопасность (кратко)

- Модель: однопользовательский сервис, localhost-only, пароль — scrypt-хеш в `data/settings.json`, httpOnly-cookie, rate-limit логина. Кросс-сайтовые запросы отсекаются по `Origin` (`util/origin.ts`) на `/api` и на WS-апгрейде: источник обязан быть петлевым, отсутствие заголовка (curl, тесты) допускается.
- Ошибки: наружу — общий текст, подробности — в лог. Все сторы в `data/` пишутся с правами 0600 (`ensureDirs()` чинит права файлов прежних версий).
- Секреты: SSH-пароли и пароли БД лежат открытым текстом в `data/*.json` — осознанный компромисс локального инструмента (тот же trust domain); volume наружу не публиковать; в браузер секреты не уезжают (`toSafeProfile`/`toSafeDbConnection`). Пароль БД не светится в argv/ps хоста: передаётся первой строкой stdin канала.
- Агент: мутирующие действия по умолчанию (режим `needed`) подтверждаются, кроме низкорискованных из `ai/approval.ts`; `never` — только с серверно валидируемым подтверждением рисков; остальные защиты неизменны во всех режимах — allow-лист `ai/guard.ts`, `redactSecrets` всего вывода инструментов (включая `write_memory`), таймауты, лимиты. Чтение sensitive-путей (`isSensitivePath` в `ai/redact.ts`) уходит на подтверждение (кроме `never`), хотя формально это чтение.
- SSH-туннели: локальный конец на `127.0.0.1` внутри контейнера доступен любому локальному процессу без авторизации (обходит `APP_PASSWORD`) — осознанное ослабление модели, приемлемое для однопользовательской машины.
