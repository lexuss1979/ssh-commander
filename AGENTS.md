# AGENTS.md — ssh-commander

Локальный веб-инструмент для управления удалённым Linux-сервером по SSH: терминал, файловый менеджер (SFTP), Docker Explorer и AI-агент. Запускается через Docker, слушает только `127.0.0.1`, защищён паролем. Интерфейс и системный промпт агента — на русском.

## Быстрые команды

```bash
# Production (основной способ запуска)
docker compose up -d --build        # пересборка обязательна после изменений кода
docker compose down                 # остановить

# Dev-режим в Docker: hot-reload без пересборки образа при изменении кода
scripts/docker-dev.sh up            # dev-образ (только npm ci) + запуск: API на :8081, web на :5173
scripts/docker-dev.sh logs          # логи обоих процессов
scripts/docker-dev.sh restart       # перезапуск контейнера
scripts/docker-dev.sh down

# Разработка
cd server && npm install && npm run dev   # API + WebSocket на :8080
cd web && npm install && npm run dev      # Vite на :5173, проксирует /api и /ws на :8080

# Сборка и тесты
cd server && npm run build && npm test    # tsc + vitest (unit)
cd web && npm run build                   # tsc && vite build → web/dist
```

Фронтенд собирается внутри Dockerfile автоматически — вручную собирать его для контейнера не нужно.

## Структура проекта

- `server/` — Node.js + TypeScript (ESM). Express + WebSocket (`ws`) + `ssh2`. Вход: `src/index.ts`.
- `web/` — React 18 + Vite + xterm.js. Вход: `src/main.tsx`, корневой компонент `src/App.tsx`. Сообщения чата агента рендерятся как markdown (`react-markdown` + `remark-gfm`, компонент `src/components/Markdown.tsx`). Layout в стиле VS Code: разделы профиля (Обзор/Терминал/Файлы/Docker/Порты/Cron) — верхним таббаром, левый сайдбар — навигация: сверху пункт «Серверы» (сводный дашборд, `.profile-list-item`), делимитер `.sidebar-divider`, ниже список площадок кнопками `.profile-list-item` с подсветкой активной (скролл при переполнении) и точкой доступности сервера (`status-dot`: зелёная — доступен, красная — недоступен, жёлтая — нет данных; опрос `/api/overview` раз в 10 с, на паузе при скрытой вкладке браузера); вкладки keep-alive (скрываются `display:none`, не размонтируются; страницы получают prop `visible`, фоновые эффекты на паузе при скрытии, xterm делает `fit()` при возврате); AI-агент — постоянная панель справа (drag-разделитель, сворачивание, состояние в `localStorage` `sc-agent-open`/`sc-agent-width`, на окнах < 900 px — оверлей), монтируется один раз на профиль (`key={profile.id}`), WS не рвётся при переключении вкладок и сворачивании панели. Редактор файлов — CodeMirror 6 (`@uiw/react-codemirror` + `@codemirror/language-data` + `theme-one-dark` + search, компонент `src/components/CodeEditor.tsx`, подключается через `React.lazy` отдельным чанком, тема синхронизирована с `data-theme` через MutationObserver, Ctrl+F) — используется в модалке редактирования FilesPage. Вкладка «Обзор» — `src/pages/OverviewPage.tsx` (метрики, polling 3 c только при видимой вкладке — тем же тиком грузится история нагрузки и рисуются графики `LoadChart` CPU/RAM из `components/Sparkline.tsx` в карточках «Процессор»/«Память», с мин/сред/макс и подписями времени; ось X — временная (частота опросов непостоянна), линия рвётся на null-значениях и гэпах > 3× медианного интервала — пауза опроса не выглядит сплошной линией; шкалы `Meter` и форматтеры `formatBytes/formatUptime/formatPct` экспортируются и переиспользуются). Страница «Серверы» (пункт в сайдбаре, стартовый экран) — `src/pages/ServersPage.tsx` (сводный дашборд всех профилей через `GET /api/overview`, polling 5 c только когда страница видима; карточка на профиль: статус, внешний IP (если определён), шкалы CPU/RAM/диск со спарклайнами истории нагрузки CPU/RAM (`Sparkline` из `components/Sparkline.tsx`, данные — bulk `GET /api/metrics-history` тем же poll-тиком), аптайм, контейнеры; клик — выбор профиля и переход на «Обзор»). Вкладка «Порты» — `src/pages/PortsPage.tsx` (polling 5 c только при видимой вкладке, фильтр по порту/адресу/процессу/контейнеру, scope-бейджи «наружу/локально/интерфейс»; аннотация опубликованных контейнерных портов «docker: имя» в колонке процесса хостовых слушателей; секция «Порты контейнеров» под основной таблицей — контейнер, IP, порт, протокол, доступ: «опубликован на :N» / «только сеть контейнера» / «сеть хоста»; контейнеры с host-сетью видны в основной таблице). Вкладка «Cron» — `src/pages/CronPage.tsx` (polling 5 c только при видимой вкладке): редактируемая таблица crontab SSH-пользователя (добавить/изменить/удалить/вкл-выкл через закомментирование строки; модалка с пресетами @reboot/@hourly/@daily/… и свободным выражением), read-only секции `/etc/crontab` и `/etc/cron.d/*`; человекочитаемое описание расписания (`human`) приходит с сервера; мутации возвращают свежий snapshot и применяются сразу, 409 (crontab изменился) — toast + reload. TerminalPage: палитра истории команд (Ctrl+R), чип контейнера + кнопка «Системный shell», «Спросить агента» (выделение или последние ~30 строк, ≤4 КБ; App держит стейт `agentRequest`, AgentPage авто-отправляет «Объясни этот вывод терминала: …» при готовом WS и свободном агенте, иначе prefill в поле ввода). DockerPage: колонки CPU/MEM (polling 3 c при видимой вкладке), prune-кнопки, секция Compose, кнопка терминала в строке контейнера. AgentPage: история диалогов — dropdown на всю ширину панели по кнопке «История» в тулбаре (в списке — название диалога и относительная дата через `formatRelativeDate` из `api.ts`, удаление по hover-кнопке, там же кнопка «Новый»); в тулбаре кнопка «Проверка безопасности» — модалка с необязательным sudo-паролем (не сохраняется и не передаётся модели); при запуске фронт шлёт WS `sudo_credentials` (если пароль введён) и auto-send сообщения с инструкцией выполнить `security_audit`.
- `Dockerfile` — multi-stage: `web-builder` → `server-builder` → `server-deps` (`npm ci --omit=dev`, в runtime попадают только прод-зависимости) → runtime `node:20-alpine`.
- `docker-compose.yml` — публикация `127.0.0.1:8080:8080`, volumes `./data:/data` и `./keys:/keys`.
- `docker-compose.dev.yml` — dev-сервис `ssh-commander-dev` (`target: dev` из Dockerfile): Vite + tsx watch в одном контейнере, исходники смонтированы bind-mount'ами, горячая перезагрузка при изменении `server/src` и `web/src` без пересборки образа. Изменение зависимостей (package.json/lock) требует `scripts/docker-dev.sh up` (пересборка dev-стадии).
- `scripts/docker-dev.sh` — обёртка над dev-compose: `up|down|restart|logs|build`.
- `docs/roadmap.md` — план развития (эпики нового функционала); реализация идёт последовательно, перед каждым эпиком — детальное планирование.
- `data/` — volume: `profiles.json` (профили серверов, пароли открытым текстом), `ai-dialogues.json` (история диалогов AI-агента) и `memory/<profileId>/MEMORY.md` (память агента по профилям).
- `keys/` — SSH-ключи, монтируются в контейнер в `/keys` (не копируются в образ). Ключи можно также импортировать через UI (форма профиля, «Импортировать…») — сохраняются с правами 0600.
- `server/test/` — unit-тесты (vitest) и ручные интеграционные сценарии (`*.manual.mjs`).

## Конфигурация (env)

Задаётся через `.env` (шаблон — `.env.example`), в контейнере — через `environment` в compose.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_PORT` / `APP_HOST` | `8080` / `0.0.0.0` | Порт и адрес HTTP/WS сервера |
| `APP_PASSWORD` | `admin` | Пароль входа в веб-интерфейс |
| `DATA_DIR` | `/data` (docker) | Каталог с `profiles.json`, `ai-dialogues.json` и `memory/` |
| `KEYS_DIR` | `/keys` (docker) | Каталог с SSH-ключами |
| `WEB_DIST` | авто-определение | Путь к собранному фронтенду |
| `AI_API_BASE` | `https://api.openai.com/v1` | Базовый URL OpenAI-совместимого API |
| `AI_API_KEY` | пусто | Ключ API; без него агент недоступен |
| `AI_MODEL` | `gpt-4.1-mini` | Модель агента |
| `AI_MAX_STEPS` | `30` | Лимит шагов цикла агента |
| `AI_TEMPERATURE` | `0.2` | Температура модели |
| `AI_SEARCH_API_BASE` | пусто | Anthropic-совместимая база веб-поиска для агента (у DeepSeek — `https://api.deepseek.com/anthropic`, тот же `AI_API_KEY`). Пусто — поиск выключен, инструмент `web_search` модели не объявляется |
| `AI_SEARCH_MODEL` | `deepseek-v4-flash` | Модель для веб-поиска (серверный инструмент `web_search_20260209`) |
| `TUNNEL_PORT_MIN` / `TUNNEL_PORT_MAX` | `10000` / `10049` | Диапазон портов для SSH-туннелей (локальный конец). В Docker compose публикуется на `127.0.0.1` |

`WEB_DIST`/`KEYS_DIR` при локальном запуске определяются относительно расположения модуля (работает и локальная раскладка `server/dist`, и docker-раскладка `/app/dist`); явный env всегда приоритетнее.

## Архитектура сервера

- `src/auth.ts` — вход по паролю, httpOnly-cookie `sc_session` (24 ч, in-memory), rate-limit 10 попыток / 15 мин на IP (счётчик сбрасывается при успешном входе, протухшие записи чистятся), проверка авторизации для REST и WS.
- `src/profiles.ts` — CRUD профилей в `profiles.json` (zod-валидация, атомарная запись через tmp+rename). Поля профиля: `name, host, port, username, authType (key|password), keyPath, keyPassphrase, password, dockerCommand (по умолчанию docker), note`. Путь к ключу — путь внутри контейнера (`/keys/...`); `keyPassphrase` — passphrase зашифрованного ключа (опционально, пробрасывается в ssh2). При update непереданный секрет (`password`/`keyPath`/`keyPassphrase`) сохраняется из существующего профиля; при смене `authType` новый секрет обязателен. Битый JSON хранилища переименовывается в `*.corrupt-<timestamp>`, а persist отказывается перезаписывать файл до рестарта — молчаливого затирания нет (то же в `ai/dialogues.ts`).
- `src/ssh/manager.ts` — постоянные SSH-подключения на профиль (кэш в памяти, авто-переподключение по `close`; параллельные `getClient` делят один connect, при ошибке подключения клиент закрывается и запись удаляется): `exec` (timeout 60 c, лимит вывода 2 МБ; опциональный `stdin` — пишется в канал с EOF, используется для подачи пароля в `sudo -S`), `execStream` (для `docker logs -f`; `close()` до получения канала закрывает канал сразу после его получения), `execRawChannel` (сырой канал: stdout-стрим + stdin + exit code, для tar-передач файлов), `openShell` (PTY), `getSftp`/`withSftp`.
- `src/ssh/sftp.ts` — promise-обёртки над callback-API SFTP (`readdir, stat, readFile, writeFile, mkdir, rmdir, unlink, rename, chmod`). Всегда использовать их, а не сырые callback-методы.
- `src/services/docker.ts` — docker CLI по SSH: команда собирается из `dockerCommand` профиля + экранированных аргументов (`shq`); `parseDockerJsonOutput` понимает NDJSON, JSON-массив и одиночный объект. Команда контейнера в `run` (`runContainerArgs`) оборачивается в `sh -c <shq(command)>` — многословная команда трактуется как shell-строка, а не имя бинаря. Compose поддерживается только v2 (плагин `docker compose`; standalone v1 отклоняется с понятной ошибкой), детект кэшируется на профиль.
- `src/services/metrics.ts` + `src/routes/metrics.ts` — метрики сервера для вкладки «Обзор» (`GET /api/metrics?profileId=`): CPU/mem/disk/uptime/load по SSH, кэш снимка 2 с на профиль.
- `src/services/metrics-history.ts` + `src/routes/metrics-history.ts` — история нагрузки для графиков (сэмпл — лёгкий срез снимка: `t, cpu, memPct, memUsedBytes, memTotalBytes, load1`): in-memory `Map<profileId, HistorySample[]>` без персистентности (после рестарта копится заново). Пишется хуком внутри `collectMetrics` — собственный опрос не нужен, историю кормят запросы `/api/metrics` и `/api/overview` (сайдбар опрашивает каждые 10 с при открытом UI); дедуп по timestamp (кэш снимка возвращает тот же промис) и минимальный гэп 2 с, лимиты 4320 сэмплов на профиль и 24 ч возраста (возраст проверяется и при записи, и при отдаче по wall clock — пока профиль недоступен и новых сэмплов нет, история всё равно стареет). Чистые функции `toSample`/`shouldAppend`/`trimSamples`/`decimate`; `clearHistory` вызывается при удалении профиля. Маршрут: `GET /api/metrics-history?profileId=` — `{timestamp, samples}` (≤360 точек, «Обзор»), без profileId — `{timestamp, profiles: [{id, samples}]}` (≤120 точек на профиль, спарклайны «Серверов»).
- `src/services/ports.ts` + `src/routes/ports.ts` — прослушиваемые порты для вкладки «Порты» (`GET /api/ports?profileId=`): `ss -tulpn` по SSH (фолбэк `netstat -tulpn`), чистый парсер `parseListeners` (определяет формат по строке, вычисляет scope public/loopback/interface), кэш 2 с на профиль. Без root имена чужих процессов недоступны — колонка процесса пустая. `src/services/container-ports.ts` — порты docker-контейнеров: `docker ps` + батч-`docker inspect`, парсинг `NetworkSettings.Ports` (runtime-биндинги, не строковый `Ports` из `docker ps`), кэш 2 с. Роут собирает хостовые и контейнерные порты параллельно (`Promise.all` + `.catch(() => null)` на контейнерной ветке); docker недоступен → поля `containers` нет (деградация); хостовые слушатели матчатся с опубликованными контейнерными портами по `(proto, hostPort, hostIp)` с wildcard для `0.0.0.0`/`::` — аннотация `container: {id, name}` закрывает дыру «безымянный docker-proxy без root».
- `src/services/cron.ts` + `src/routes/cron.ts` — cron-задачи для вкладки «Cron» (`GET /api/cron?profileId=`): пользовательский `crontab -l` (отсутствие — `null`, не ошибка), `/etc/crontab` и `/etc/cron.d/*` одной командой с маркерами `=== <файл>`; чистые функции `parseCrontab` (system-формат с колонкой user, `@keywords`, env-строки и комментарии отдельно, закомментированные записи → `enabled:false`, у записи `index` = номер строки), `describeSchedule` (русские описания частых расписаний), `validateCronFields`, `applyCrontabOp` (add/update/delete/toggle с защитой от гонки через `expectedRaw` → `CronConflictError`/409); кэш 2 с на профиль. Мутации (`mutateUserCrontab`) только пользовательского crontab: чтение заново без кэша → `applyCrontabOp` → запись целиком через `crontab -` (stdin канала). Системные файлы — read-only.
- `src/services/tunnels.ts` + `src/routes/tunnels.ts` — SSH-туннели (эквивалент `ssh -L`): in-memory реестр без персистентности (после рестарта туннелей нет). `createTunnel` поднимает `net.createServer()` на `127.0.0.1:localPort`, на каждое TCP-соединение — `client.forwardOut()` через `getClient`, двусторонний pipe socket↔channel. Валидация `validateTunnelParams` (чистая функция): порты 1–65535, `targetHost` до 253 символов `[a-zA-Z0-9._-]`, лимит 10 active туннелей на профиль (closed не считаются), дубль `(profileId, localPort)` → 409. `localPort: 0` → автоподбор свободного в диапазоне `TUNNEL_PORT_MIN`–`TUNNEL_PORT_MAX`. Лимит соединений на туннель — 10. Ошибка сервера (EADDRINUSE) → статус `closed` с ошибкой, туннель остаётся в реестре до `DELETE`. Маршруты: `GET /api/tunnels?profileId=` (список + `portRange`), `POST /api/tunnels` (создание, 409 при EADDRINUSE/конфликте), `DELETE /api/tunnels/:id`.
- `src/services/overview.ts` + `src/routes/overview.ts` — сводный дашборд всех профилей (`GET /api/overview`, без profileId): параллельный опрос (Promise.allSettled), guard-таймаут 8 с на профиль (упавший сервер → `ok:false` с ошибкой, ответ не висит), docker-счётчики через `docker ps -a --format json` (при недоступном docker — просто нет поля), внешний IP через `services/external-ip.ts` (curl к ifconfig.me/api.ipify.org, wget-фолбэк, строгая IPv4-валидация `parseExternalIp`, кэш на профиль: успех 10 мин / неудача 1 мин, никогда не бросает — при недоступности поля нет), кэш всего ответа 4 с. Агрегирующий маппинг — чистые функции `toOverviewEntry`/`countContainers`.
- `src/services/file-search.ts` — поиск файлов: `mode=name` (`find -iname`) и `mode=content` (`grep -rInF`), лимиты 500 результатов / 30 c.
- `src/services/security-audit.ts` — детерминированный аудит безопасности для инструмента агента `security_audit`: фиксированный белый список read-only команд по секциям (`auth, network, updates, activity, docker, filesystem`; чистые билдеры `commandsForSection`/`sudoWrap`/`findContainerIssues`), произвольный shell не принимает. Root-подсекции — через `sudo -S -p '' -- sh -c <shq(cmd)>` с паролем в stdin канала (не в командной строке); без пароля или при нерабочем sudo помечаются «пропущено: нет прав» (мягкая деградация). Docker-секция — через `services/docker.ts` (privileged, host network, монтирование docker.sock и корня ФС). Лимиты вывода: строки и символы на подсекцию + общий ~10 КБ (параметр `sections` для запроса по частям).
- `src/services/transfer.ts` — сборка tar-команд для скачивания/загрузки каталогов (`download-dir`/`upload-dir`), детект отсутствия `tar` с понятной ошибкой.
- `src/services/history.ts` + `src/routes/terminal.ts` — история shell-команд (`GET /api/terminal/history?profileId=&limit=`): форматы bash/zsh, дедуп, по умолчанию 100 / максимум 200.
- `src/services/keys.ts` + `src/routes/keys.ts` — `GET /api/keys` (список файлов в `KEYS_DIR` для выпадающего списка в форме) и `POST /api/keys?name=&overwrite=1` (импорт ключа из UI: raw body ≤ 64 КБ, проверка PEM/OpenSSH-заголовка, санитизация имени `[A-Za-z0-9._-]`, атомарная запись с правами 0600, без `overwrite=1` существующий файл не затирается — 409). Чтение содержимого ключей наружу не отдаётся — только имена.
- `src/services/profile-transfer.ts` — перенос профилей между машинами: `POST /api/profiles/export` (файл бэкапа; секреты — только при `includeSecrets=true`, с `passphrase` шифруется scrypt + AES-256-GCM; ключи вкладываются только из `KEYS_DIR` и только вместе с секретами) и `POST /api/profiles/import` (`{backup, passphrase?}`; всё валидируется до первой записи, конфликты имён — суффикс « (2)», существующие ключи не затираются, `keyPath` перепривязывается к текущему `KEYS_DIR`, профили без секрета попадают в `needSecrets` — секрет задаётся вручную через `importProfile` в `profiles.ts`, который не требует секрет при создании). Формат бэкапа версионируется (`app/version/encrypted`).
- `src/ws/terminal.ts` — терминальные сессии на профиль: буфер ввода до готовности shell, переживают перезагрузку вкладки (60 c после последнего отсоединения), удаляются по завершении процесса. Опциональный `container` в query — PTY-сессия `docker exec -it` в контейнер, ключ сессии `profileId::container` (системный shell и shell контейнера — разные сессии). WS-сообщение `restart` закрывает shell и SSH-подключение и открывает новый shell (применяются новые группы/права).
- `src/ai/` — агент: `client.ts` (Chat Completions, streaming SSE, аккумуляция tool_calls, таймаут соединения 120 c), `tools.ts` (определения инструментов + `READ_ONLY_TOOLS` + гейтинг `getToolDefs` — web_search объявляется модели только при настроенном поиске), `guard.ts` (deny-лист read-only команд), `agent.ts` (цикл, подтверждения, лимит шагов, системный промпт), `plan.ts` (режим планирования: `PLAN_MODE_INSTRUCTION`, `toolsForRequest`, `buildPlanRequestMessages`), `messages.ts` (санитизация истории сообщений), `memory.ts` (пер-профильная память MEMORY.md), `web-search.ts` (веб-поиск для агента — см. ниже).
- `src/ai/dialogues.ts` — хранение диалогов агента в `DATA_DIR/ai-dialogues.json` (zod-валидация, атомарная запись tmp+rename, кэш в памяти).
- `src/ai/web-search.ts` — веб-поиск для инструмента агента `web_search`: Anthropic-совместимый endpoint DeepSeek (`AI_SEARCH_API_BASE`, по умолчанию пусто — фича выключена) с серверным инструментом `web_search_20260209` (`max_uses` 3 на вызов), ключ общий с `AI_API_KEY`, модель — `AI_SEARCH_MODEL` (по умолчанию `deepseek-v4-flash`). Чистые функции: `buildSearchBody` (тело Messages-запроса), `parseSearchResponse` (текст + выполненные запросы + источники; `encrypted_content` и thinking-блоки игнорируются), `formatSearchOutput`, `sanitizeQuery` (лимит 400 символов), `isSearchConfigured`. `searchWeb` — fetch с таймаутом 90 с, никогда не бросает (ошибки возвращаются текстом). Основной клиент агента (OpenAI-формат) не меняется — поиск это отдельный read-only инструмент с собственным HTTP-вызовом; в `agent.ts` лимит 10 вызовов `web_search` за запуск цикла (сброс в начале `runLoop`), без конфигурации инструмент модели не объявляется вовсе.
- `src/routes/ai.ts` — REST для диалогов: `GET/POST /api/ai/dialogues`, `GET/DELETE /api/ai/dialogues/:id`.

## REST и WebSocket API

Все маршруты кроме `/api/auth/*` и `/api/health` требуют cookie-сессии.

- `POST /api/auth/login|logout`
- CRUD `/api/profiles`, `POST /api/profiles/test-connection` (разовое SSH-подключение по переданным полям без сохранения профиля; кэш соединений не затрагивается — кнопка «Проверить подключение» в форме), `POST /api/profiles/:id/reconnect` (закрывает SSH-подключение профиля; следующее обращение откроет свежее — применяются новые группы/права), `POST /api/profiles/export` и `POST /api/profiles/import` (перенос профилей между машинами, см. `services/profile-transfer.ts`), `GET /api/keys` (список имён), `POST /api/keys?name=&overwrite=1` (импорт ключа из UI, raw body)
- Диалоги агента: `GET /api/ai/dialogues?profileId=` (список-сводки), `POST /api/ai/dialogues` `{profileId}` (создать), `GET /api/ai/dialogues/:id` (полный диалог), `DELETE /api/ai/dialogues/:id`
- `GET /api/metrics?profileId=` — снимок метрик сервера (вкладка «Обзор»).
- `GET /api/metrics-history[?profileId=]` — история нагрузки: с profileId `{timestamp, samples: HistorySample[]}` (≤360 точек) для графиков «Обзора», без — `{timestamp, profiles: [{id, samples}]}` (≤120 точек на профиль) для спарклайнов «Серверов»; пока истории нет, отдаются пустые массивы.
- `GET /api/ports?profileId=` — прослушиваемые порты (вкладка «Порты»): `{timestamp, ports: [{proto, host, port, pid, process, scope, container?}], containers?: [{containerId, name, networkMode, ip, ports: [{containerPort, proto, hostIp, hostPort}]}]}`. Поле `containers` отсутствует при недоступном docker (деградация); `container` в хостовых слушателях — аннотация для опубликованных контейнерных портов.
- `GET /api/tunnels?profileId=` — список туннелей + диапазон портов: `{tunnels: [{id, profileId, localHost, localPort, targetHost, targetPort, status, error?, createdAt}], portRange: {min, max}}`. `POST /api/tunnels?profileId=` — создание `{localPort, targetHost, targetPort}` (409 при EADDRINUSE/дубле/лимите). `DELETE /api/tunnels/:id` — закрытие и удаление туннеля.
- `GET /api/overview` — сводный снимок по всем профилям (вкладка «Серверы»): `{timestamp, servers: [{id, name, host, port, username, ok, error?, externalIp?, metrics?, docker?: {containersTotal, containersRunning}}]}`.
- `GET /api/terminal/history?profileId=&limit=` — история shell-команд (палитра Ctrl+R в терминале).
- `GET /api/cron?profileId=` — cron-задачи (вкладка «Cron»): `{timestamp, username, userCrontab: {entries, env, comments, raw} | null, systemCrontab: {entries, env, comments} | null, cronD: [{file, entries}]}`; entry — `{index, raw, enabled, schedule, command, user?, human}`. Мутации crontab пользователя: `POST /api/cron/entries` `{schedule, command}` (201), `PUT /api/cron/entries/:index` `{expectedRaw, schedule, command}`, `DELETE /api/cron/entries/:index` `{expectedRaw}`, `POST /api/cron/entries/:index/toggle` `{expectedRaw}` — все возвращают свежий snapshot; 409 при расхождении `expectedRaw` (crontab изменился), 400 при невалидном расписании.
- `/api/files/list|read|write|mkdir|rename|chmod|delete|download|upload|search|download-dir|upload-dir` — `profileId` и `path` в query/body; upload — raw body (`express.raw`, лимит 200 МБ); download — стрим; search — `mode=name|content`; download-dir — tar.gz стрим; upload-dir — raw tar.gz → `tar -xzf`.
- `/api/docker/containers|images|volumes|networks`, действия контейнеров (`start|stop|restart|rm`), `pull`, `rmi`, `run`, `logs` (tail и follow-стрим), `GET /stats`, `POST /prune` `{target: containers|images|volumes|system}`, `GET /compose/status`, `GET /compose/ps`, `POST /compose/up|down`.
- WS `/ws/terminal?profileId=&cols=&rows=[&container=<id>]` — сообщения: клиент `input|resize|close|restart` (restart закрывает shell и SSH-подключение и открывает новый shell), сервер `output|connected|close|error`.
- WS `/ws/agent?profileId=&dialogueId=` — клиент `message {content, planMode?}|approve|reject|approve_plan|stop|sudo_credentials {password}`, сервер `dialogue|token|message|tool_pending|tool_result|plan_ready|running|done|error`. Диалог загружается в сессию при подключении и сохраняется по ходу каждого шага; если `dialogueId` не передан, сервер создаёт новый диалог и сообщает его id событием `dialogue`. `sudo_credentials` задаёт sudo-пароль для привилегированного `security_audit`: пароль хранится только в поле AgentSession (память), очищается в `stop()`/`onWsClose()`; не логируется, не сохраняется в диалог и не передаётся модели.

## AI-агент: правила подтверждений

Два класса инструментов:
- Read-only (выполняются автоматически): `exec_readonly, read_file, read_memory, list_dir, docker_ps, docker_logs, docker_inspect, security_audit, web_search` (последний — только при настроенном `AI_SEARCH_API_BASE`; запрос уходит во внешний поисковый API — приватный нюанс, отключается env целиком).
- Мутирующие (ждут approve/reject в UI): `exec, write_file, write_memory, docker_action`.

`exec_readonly` дополнительно фильтруется deny-листом в `guard.ts`: запрещены конвейеры/редиректы/подстановки, мутирующие команды (`rm, mv, cp, chmod, chattr, setfacl, dd, wipefs, tee, unlink, mkfs* и xfs_* по префиксу, systemctl, apt, docker ...`), мутирующие флаги `find` (`-delete, -exec, -execdir, -ok, -okdir`), интерпретаторы и прочее. Результат `exec`/`exec_readonly` всегда содержит exit code; ненулевой код возвращается модели как ошибка. Если расширяешь набор инструментов — обязательно:
1. добавь определение в `tools.ts`,
2. добавь имя в `READ_ONLY_TOOLS` (если read-only) и обработчик в `runTool` в `agent.ts`,
3. если инструмент исполняет произвольный shell — проверь, что он не попал в read-only класс без проверок guard.

`security_audit` — детерминированный аудит безопасности (см. `services/security-audit.ts`): произвольный shell не принимает, поэтому в guard не нуждается. Параметр `privileged` сервер подставляет сам: root-проверки выполняются, только если в сессии есть sudo-пароль (WS `sudo_credentials`, вводится в модалке «Проверка безопасности» в AgentPage); модель пароль не видит. После отчёта модель предлагает записать ключевые находки через `write_memory`.

Режим планирования (`planMode`, `src/ai/plan.ts`): клиент шлёт `message` с `planMode: true` — запрос к API идёт БЕЗ tools, модель возвращает текст плана, сервер отвечает `plan_ready` и ждёт. `approve_plan` запускает обычный цикл с инструментами (per-tool approve/reject сохраняется); правки плана — повторным `message` с `planMode: true`. Шаги планирования не расходуют `AI_MAX_STEPS`. В UI — переключатель «План» и PlanCard в AgentPage.

### Память агента (MEMORY.md)

- Для каждого профиля память хранится в `DATA_DIR/memory/<profileId>/MEMORY.md` (`src/ai/memory.ts`). Это локальная память приложения, к удалённому серверу отношения не имеет; имя файла формируется из `profileId` санитизацией (только `[A-Za-z0-9_-]`, fallback `default`) — выход за `memory/` невозможен.
- Содержимое MEMORY.md автоматически подгружается в системный промпт в начале каждой сессии; правила «когда читать, что и как записывать» заданы в промпте в `agent.ts` и дублируют контракт инструментов.
- `read_memory` — read-only, выполняется автоматически; `write_memory` — мутирующий, требует подтверждения и принимает полный новый текст файла (агент обязан сохранять прежние записи). Инструменты памяти нельзя заменять на `exec`/`write_file`.
- Запись атомарная (tmp+rename), чтение для контекста ограничено 64 КБ.

## Правила работы с кодом

- TypeScript strict; сервер — ESM, относительные импорты с расширением `.js`; фронтенд — `noUnusedLocals`, `noUnusedParameters`.
- Пути в API: абсолютные, нормализация `//` и хвостового `/`; операции удаления запрещают `/` и `..` (`src/util/path.ts`); рекурсивное удаление использует `rm -rf -- <shq(path)>`.
- Секреты: ключи, `.env` и `data/profiles.json` в git не попадают (`.gitignore`); не добавлять их в коммиты и не логировать содержимое.
- Docker-сборка: при изменении сервера/фронта контейнер пересобирается через `docker compose up -d --build`; `WEB_DIST` в Dockerfile задан явно — не удалять.
- Интерфейс: тёмная и светлая темы на CSS-переменных (`web/src/styles.css`, атрибут `data-theme` на `<html>`), переключатель в сайдбаре, выбор сохраняется в `localStorage`; русский язык; скроллируемые области используют `scrollbar-gutter: stable` против дёргания layout.
- Git: репозиторий инициализирован в корне проекта, ветка `main`.

## Безопасность (кратко)

Сервис однопользовательский: localhost-only, пароль из `APP_PASSWORD`, httpOnly-cookie, rate-limit логина. SSH-пароли лежат открытым текстом в `data/profiles.json` — это осознанный компромисс локального инструмента, volume наружу не публиковать. Мутирующие действия агента никогда не выполняются без подтверждения; deny-лист read-only команд консервативен — лучше отказать, чем пропустить. SSH-туннели: локальный конец слушает на `127.0.0.1` внутри контейнера, доступен любому локальному процессу без авторизации (обходит `APP_PASSWORD`). Для однопользовательской машины приемлемо (как и терминал), но это ослабление модели безопасности — туннель даёт доступ к удалённым сервисам всем, кто может подключиться к `127.0.0.1:<порт>`.
