# Анализ: мульти-серверный режим агента

Статус: анализ (не план реализации). Задача — развернуть пункт бэклога
«Мульти-серверный режим агента» (`docs/roadmap.md`, Backlog): понять, что и как
можно сделать, зафиксировать варианты и точки разрыва до детального планирования.

## Целевой сценарий

Пользователь настраивает zabbix-server на сервере A и хочет подключить к нему
серверы B и C как zabbix-агенты — в рамках одного диалога с агентом:

1. Агент узнаёт, какие серверы есть в профилях (новый read-only инструмент
   `list_servers` — имена/host/username, без секретов).
2. Собирает факты по B и C (`exec_readonly` на каждом: ОС, пакетный менеджер,
   нет ли уже агента).
3. Узнаёт адрес zabbix-server'а (`exec_readonly` на A).
4. Ставит и настраивает zabbix-agent2 на B и C (`exec` — мутация, подтверждение
   на каждый сервер, в конфиге — адрес сервера A).
5. Регистрирует хосты в zabbix (API через `exec` на A или оставляет пользователю).
6. Проверяет результат (read-only), даёт отчёт по каждому серверу, предлагает
   записать находки в память профилей B и C.

Ключевые требования из сценария: общий контекст (модель помнит, что нашла на A,
работая с B), явная адресация команд конкретным серверам, понятные подтверждения
(пользователь видит, ЧТО и ГДЕ выполнится), отчётность по серверам.

## Фактическая база (что есть сейчас)

- `AgentSession` держит один `Profile` (`agent.ts:61-65`); `runTool` использует
  `this.profile` в 12 местах (`agent.ts:422-556`) без параметра сервера.
- Реестр сессий `Map<profileId, AgentSession>` (`agent.ts:559-588`): одна
  активная сессия на профиль, при переподключении вытесняется.
- Схема инструментов (`tools.ts:10-185`) не содержит параметра «сервер» — модель
  не знает, что серверов может быть несколько.
- Диалог жёстко привязан к профилю: `profileId` обязателен в zod-схеме
  (`dialogues.ts:48`), список фильтруется по профилю, `attachAgent` игнорирует
  чужой диалог (`agent.ts:572-577`).
- Подтверждения: `tool_pending {callId, name, args}` без идентификации сервера;
  цикл строго последовательный, решения сериализуются по callId.
- sudo-пароль — один на сессию (`agent.ts:59`). Память — per-profile файл,
  подгружается в системный промпт один раз при создании сессии (`agent.ts:88-91`).
- Фронт: панель агента монтируется с `key={profile.id}` (`App.tsx:418`) — смена
  профиля в сайдбаре рвёт WS и теряет чат.

Что НЕ является препятствием:

- `ssh/manager.ts` уже держит одновременные подключения к разным профилям
  (кэш по profileId, все функции принимают `Profile` параметром).
- `guard.ts` и `plan.ts` — чистые функции, от профиля не зависят.
- `memory.ts` — функции параметризованы profileId, менять не нужно (только вызовы).

## Ключевые архитектурные решения

### 1. Как модель адресует сервер (главный вопрос эпика)

**Вариант A — параметр `server` в каждом SSH-инструменте (рекомендуется).**
Во все инструменты, работающие по SSH, добавляется необязательный параметр
`server` (имя или id профиля; по умолчанию — домашний профиль диалога). Модель
явно указывает сервер в каждом вызове.

- Плюсы: stateless, невозможно «забыть, где я»; fan-out получается бесплатно —
  модель эмитит N tool_calls с разным `server` в одном шаге; guard и классы
  инструментов не меняются.
- Минусы: +несколько токенов на вызов; нужна валидация имени сервера с понятной
  ошибкой (и перечислением допустимых) — иначе модель будет опечатываться.

**Вариант B — «текущий сервер» + инструмент `switch_server`.**
Схемы инструментов не трогаем, сессия хранит текущий профиль.

- Плюсы: минимальные изменения в tools.ts.
- Минусы: скрытое состояние — модель легко путается, какой сервер активен,
  особенно в длинном диалоге; fan-out (одна команда на N серверов) не выразить;
  в истории диалога не видно, где выполнялась команда, без доп. разметки.

**Вариант C — fan-out: `server: "all"` или список.**
Один вызов — много серверов, результат агрегируется.

- Плюсы: красиво ложится на «применить план по серверам».
- Минусы: усложняет подтверждения (одна карточка на группу? на сервер?),
  агрегацию результатов и обработку частичных ошибок; можно получить позже
  поверх варианта A (модель сама эмитит N вызовов — тот же эффект).

Рекомендация: A как ядро; C не делать отдельно — достигается батчем tool_calls.

**Решено (обсуждение): вариант A** — параметр `server` (имя профиля,
необязательный; по умолчанию домашний) во всех SSH-инструментах + read-only
инструмент `list_servers` (имена, `user@host`, без секретов). Валидация имени
с ошибкой с перечислением доступных серверов. В `tool_pending`/`tool_result`
и ToolCard — бейдж сервера.

### 2. Идентичность сессии: сессия = диалог, а не профиль

Сейчас пара «сессия ↔ профиль» зашита с двух сторон: реестр
`Map<profileId, …>` на сервере и `key={profile.id}` на фронте. В мульти-серверном
диалоге смена активного профиля в сайдбаре не должна рвать WS.

- Реестр сессий переключается на ключ `dialogueId`; «домашний» профиль остаётся
  у диалога (владелец, память по умолчанию, фильтр истории).
- Панель агента на фронте перестаёт зависеть от `activeProfile.id`: монтируется
  один раз, при смене профиля в сайдбаре живёт. Вопрос UI: показывать ли в шапке
  чипы серверов диалога (см. п.5).

### 3. Диалоги: домашний профиль + дополнительные

Неинвазивно: `profileId` остаётся обязательным (домашний профиль), добавляется
`extraProfileIds?: string[]` в zod-схему (`.optional()` — старые
`ai-dialogues.json` валидны без миграции). Проверка в `attachAgent` ослабляется
до «домашний совпал, остальные существуют». REST-список по-прежнему фильтрует по
домашнему профилю.

### 4. Подтверждения

Цикл последовательный, решения по callId — протокол решений менять не нужно.
Обязательное изменение: в `tool_pending`/`tool_result` и в ToolCard прокидывать
имя сервера, иначе пользователь не понимает, что подтверждает. Открытый вопрос:
при батче из N одинаковых команд на разные серверы — N отдельных карточек
(просто, по одной на сервер) или одна групповая карточка с пер-серверными
решениями (красивее, сложнее протокол). Для первой версии достаточно N карточек
с бейджем сервера.

### 5. Область видимости серверов в диалоге

Два варианта:

- **Агент видит все профили** (кроме, возможно, явно скрытых): проще, ноль нового
  UI; read-only инструменты выполняются автоматически на любом сервере, но это
  чтение, и каждый вызов виден в ленте.
- **Пользователь явно добавляет серверы в диалог** (чипы в шапке панели):
  безопаснее и понятнее («в этом диалоге мы про A, B, C»), но это новый UI и
  серверный протокол (`attach_server`/`detach_server`, событие `servers`).

Гибрид: по умолчанию все профили, чипы — как явное ограничение. Вопрос на
обсуждение.

**Решено (обсуждение): «3b-lite»** — `list_servers` видит все профили (чтобы
агент мог предложить), а выполнение инструментов — только на подключённых к
диалогу серверах. Домашний профиль подключён всегда. Подключение сервера:
вручную чипом «+» в шапке панели ИЛИ по запросу агента — карточка «Подключить
<сервер> к диалогу?» с Подтвердить/Отклонить (тот же механизм approve/reject,
что у мутаций, новый протокол решений не нужен). Попытка вызова на
неподключённом сервере отклоняется с понятной ошибкой для модели.

### 6. Per-profile данные сессии

- **sudo-пароль**: `Map<profileId, password>` в сессии вместо одного поля;
  WS `sudo_credentials` получает `profileId`. Модель паролей по-прежнему не видит.
- **Память**: остаётся per-profile (это заметки о конкретном сервере). В системный
  промпт подгружаются блоки всех профилей диалога с подписями серверов (лениво —
  при первом обращении к серверу, чтобы не раздувать промпт). В `read_memory`/
  `write_memory` добавляется опциональный `server` (по умолчанию — домашний).

### 7. «Спросить агента» из терминала

Сейчас вывод терминала профиля X попадает в агента профиля X. При глобальном
агенте в текст сообщения нужно явно добавлять источник («Вывод терминала с
сервера X: …»), иначе модель не узнает, откуда контекст.

## Точки разрыва (где зашита однопрофильность)

1. `AgentSession.profile` + `runTool` без параметра сервера — `agent.ts:61-65, 422-556`.
2. Схемы инструментов без `server` и системный промпт в единственном числе —
   `tools.ts:10-185`, `agent.ts:67-87`.
3. Реестр сессий по profileId + `key={profile.id}` на фронте —
   `agent.ts:559-588`, `App.tsx:418`.
4. Диалог: `profileId` как владелец/фильтр — `dialogues.ts:48, 108-120`,
   `routes/ai.ts:12-38`, `agent.ts:572-577`.
5. Подтверждения без идентификации сервера — `agent.ts:332`, ToolCard в AgentPage.
6. sudo-пароль и память в единственном экземпляре — `agent.ts:59, 88, 451-465`.

## Открытые вопросы (нужны решения до планирования)

1. ~~Адресация: параметр `server` (A) / текущий сервер (B) / fan-out (C)?~~
   **Решено: A.**
2. ~~Глобальная панель агента vs диалог «при профиле»~~ **Решено: гибрид.**
   Диалог навсегда привязан к домашнему профилю (ментальная модель «профиль =
   свои диалоги» не ломается, чипы серверов — в шапке диалога). Панель агента
   монтируется keep-alive на каждый посещённый профиль (по образцу keep-alive
   вкладок, `display:none`) — переключение профиля не рвёт WS, агент продолжает
   работать в фоне. В сайдбаре у профиля — индикатор активности агента
   (работает / ждёт подтверждения), по образцу `status-dot`. Серверный
   detach/reattach сессии (пережить перезагрузку вкладки: `ws close` ≠ `stop()`,
   снапшот состояния при переподключении, TTL на висящие подтверждения) —
   отдельный поздний этап.
3. ~~Область видимости: все профили vs явное добавление серверов в диалог?~~
   **Решено: 3b-lite (см. п.5 выше).**
4. ~~Подтверждения: карточка на сервер vs групповая карточка при батче?~~
   **Решено: карточка на вызов с бейджем сервера** (протокол approve/reject по
   callId не меняется); групповые карточки не делаем.
5. Явный протокол подключения сервера к диалогу — да, следует из 3b-lite:
   чип «+» в шапке + approve-карточка по запросу агента; событие `servers`
   для синхронизации шапки. Ленивое подключение по первому tool call не
   используется.
6. ~~Мульти-серверный диалог в истории~~ **Решено:** показывается в истории
   домашнего профиля (как сейчас), в списке — бейдж «+N серверов».

## Предварительная поэтапность (если эпик пойдёт в работу)

1. Серверное ядро: мульти-профильная сессия (домашний + ленивое подключение),
   параметр `server` в инструментах, `list_servers`, реестр по dialogueId,
   имя сервера в `tool_pending`/`tool_result`, Map sudo-паролей.
2. Протокол и хранение: `extraProfileIds` в диалогах, память всех профилей в
   промпте, параметр `server` в инструментах памяти.
3. Фронтенд: глобальная панель (без `key={profile.id}`), бейдж сервера в
   ToolCard, источник в «Спросить агента», sudo-модалка с указанием сервера.
4. Тесты: маршрутизация вызовов по серверам, валидация имени сервера, обратная
   совместимость диалогов, подтверждения с бейджем; live-сценарий «zabbix на
   двух sshd-контейнерах» в manual-тестах.
