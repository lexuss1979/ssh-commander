# План: эпик 20 — алерты по порогам

> Эпик 20 из `docs/roadmap.md` (Tier 3): узнавать про «диск кончился»
> и «сервер недоступен», не разглядывая вкладку.
> Статус: реализовано (2026-08-23). Дата плана: 2026-08-23.
> Правки по ревью: `message` заполняется всегда (алерт в зоне гистерезиса
> показывает текущую цифру); фоновый опрос в скрытой вкладке — только при
> включённых браузерных уведомлениях (отклонение 4 сужено: уведомления по
> умолчанию выключены, опрос «впустую» никому не нужен); клиентский merge
> покрыт тестами раннером сервера (`server/test/alerts-merge.test.ts`).
> Сервер + фронтенд. Новых зависимостей нет.
>
> **Пять осознанных отклонений от формулировки roadmap**, все — следствие
> одной вещи: гистерезис на клиенте требует знать текущее **значение**
> правила, а не только факт срабатывания.
>
> 1. **Ответ `GET /api/alerts` — состояния всех правил**
>    (`{kind, subject?, active, value, threshold, severity, message}`),
>    а не только сработавшие `{profileId, kind, severity, message}[]`:
>    чтобы молчать до «порог минус дельта», клиент должен видеть значение
>    ниже порога, а не отсутствие алерта.
> 2. **Параметры — отдельные числа `disk`/`mem`/`load` в query** вместо
>    `thresholds=…`; фильтр `profileId` не нужен — колокольчик глобальный,
>    вычисление возвращает правила всех профилей сразу.
> 3. **`server-down` — булево правило** (`value` 0/1, `threshold` 1,
>    дельта 0): срабатывание и снятие по переходу, числовой гистерезис
>    неприменим.
> 4. **Опрос при скрытой вкладке продолжается, пока алерты включены**
>    (сейчас — пауза, `App.tsx:164`): браузерные уведомления нужны ровно
>    тогда, когда вкладка неактивна; браузер сам троттлит скрытые таймеры
>    до ~1/мин — это и есть честный ритм фоновой проверки. Алерты
>    выключены — прежняя пауза без изменений.
> 5. **Первая синхронизация и смена настроек — тихий re-baseline**
>    (сброс активного набора): иначе F5 и смена порогов дают залп
>    уведомлений, а поднятие порога не снимает уже активный алерт —
>    гистерезис держал бы его по старому порогу.

## Контекст: что уже есть

- **Сайдбар уже опрашивает всё нужное**: `App.tsx:163-186` — тик раз в
  `SERVER_STATUS_POLL_MS` (10 с) вызывает `fetchOverview()`, из ответа
  берутся только `{ok, error}` для статус-точек профилей. Метрики
  (`metrics.cpu/memory/disks/loadAverage`, все поля допускают `null`,
  `services/metrics.ts:5-44`) приходят **тем же ответом и выбрасываются**.
- `collectOverview()` (`services/overview.ts:125`) — кэш 4 с на промисе:
  параллельные потребители в пределах TTL делят один опрос SSH (зонд
  профиля — до 8 с, `PROFILE_TIMEOUT_MS`). Отсюда бесплатно: `/api/alerts`
  в том же тике не добавляет ни одного SSH-вызова и не кормит
  `metrics-history` лишними сэмплами.
- Тест-раннер есть только на сервере (`web/package.json` — dev/build/
  preview). Правило проекта — unit-тесты на всю новую логику — отсюда
  решение roadmap: вычисление правил на сервере, во фронте только
  stateful-клей (переходы, уведомления).
- localStorage-паттерн настроек — `loadAgentWidth`/`loadAgentOpen`
  (`App.tsx:35-51`), ключи `sc-*`.
- Модальные окна — `.modal-overlay`/`.modal`/`.modal-header`/`.modal-body`/
  `.modal-actions` (`styles.css:1120+`), паттерн `ProfileModal`.
- В сайдбаре уже есть неблокирующий индикатор поверх пункта профиля —
  `agent-dot` (`App.tsx:333-342`): точка активности агента рядом с именем.

## Решение

### 1. Сервис `server/src/services/alerts.ts`

Чистые функции, SSH не трогают, кэша своего нет (использует кэш overview
на уровне роута).

```ts
export interface AlertThresholds {
  diskPercent: number;   // 50..99
  memPercent: number;    // 50..99
  loadPerCore: number;   // 0.5..16
}
export const DEFAULT_ALERT_THRESHOLDS: AlertThresholds =
  { diskPercent: 90, memPercent: 90, loadPerCore: 2 };

export type AlertKind = 'server-down' | 'disk' | 'memory' | 'load';

export interface AlertRuleState {
  profileId: string;
  kind: AlertKind;
  /** Точка монтирования (kind='disk'). */
  subject?: string;
  severity: 'crit' | 'warn';
  active: boolean;
  /** server-down: 0/1; disk/memory: %; load: load1/cores (2 знака). */
  value: number;
  /** server-down: 1; disk/mem: %; load: на ядро. */
  threshold: number;
  /** Только при active=true — текст для списка/уведомления. */
  message: string | null;
}

export function evaluateAlertRules(
  overview: OverviewResponse,
  thresholds: AlertThresholds,
): AlertRuleState[]
```

Правила (на профиль из `overview.servers`):

- **server-down** (severity `crit`): `active = !e.ok`, `value = e.ok ? 0
  : 1`, `threshold = 1`; сообщение при active — `Сервер недоступен:
  ${e.error ?? 'нет данных'}`.
- **disk** (`warn`): по каждому `disks[]` с `usedPercent !== null`;
  `active = usedPercent >= diskPercent` (граница включительно),
  `subject = mount`, сообщение `Диск «/» занят на 93.4% (порог 90%)`.
  Диск с `usedPercent === null` состояния не получает вовсе.
- **memory** (`warn`): `memory.usedPercent !== null` → `active =
  usedPercent >= memPercent`; `Память занята на 91.2% (порог 90%)`.
  `null` → состояния нет.
- **load** (`warn`): только если `loadAverage !== null` и `cpu.cores` —
  целое > 0: `value = round2(load1 / cores)`, `active = value >=
  loadPerCore`; сообщение с исходными числами: `Load 4.2 при 2 ядрах
  (2.1/ядро, порог 2)`. Ядер нет → правила нет (делить не на что,
  roadmap-кейс «деление на cores при неизвестном числе ядер»).

`ok: true` без `metrics` (тип допускает) → только server-down-состояние.
Severity фиксирована по kind: crit — только недоступность; пороги простые,
двухуровневых warn/crit не заводим (риск roadmap «не превращать в систему
мониторинга»).

### 2. Маршрут `server/src/routes/alerts.ts`

Монтирование: `app.use('/api/alerts', requireAuth, alertsRouter)` в
`src/index.ts` (паттерн соседей, `index.ts:38-52`).

`GET /api/alerts?disk=&mem=&load=` — zod-схема query по паттерну
`routes/files.ts:247` (`z.coerce.number()` + диапазоны + дефолты):

```ts
const alertsQuerySchema = z.object({
  disk: z.coerce.number().min(50).max(99).default(90),
  mem:  z.coerce.number().min(50).max(99).default(90),
  load: z.coerce.number().min(0.5).max(16).default(2),

```

Невалидное (`disk=abc`, `disk=10`, `load=0`) → 400 с текстом zod.
Валидное → `const overview = await collectOverview()` (кэш 4 с — новых
SSH-вызовов нет), ответ:

```ts
{ timestamp: overview.timestamp,
  thresholds: AlertThresholds,   // эффективные, с дефолтами — echo
  rules: AlertRuleState[] }
```

### 3. Фронтенд: опрос и состояние (`App.tsx`)

Существующий эффект статус-точек расширяется (не дублируется):

- **Один тик — два запроса параллельно**: `Promise.allSettled([
  fetchOverview(), alertsEnabled ? fetchAlerts(settings) : null ])`.
  Параллельность обязательна: `/api/alerts` должен прийти на сервер,
  пока жив кэш overview (4 с) — последовательный вызов после медленного
  ответа (зонд мёртвого сервера до 8 с) порождал бы второй опрос.
- Статус-точки — как раньше из первого результата; отказ — «оставляем
  последний снимок» (существующий catch), 401 уводит на логин глобально.
- Из второго — `mergeAlertStates(activeRef.current, rules, Date.now())`;
  `activeRef` + стейт `activeAlerts: ActiveAlert[]` (для колокольчика и
  чипов профилей). Отказ запроса алертов — прежний набор без изменений,
  без mass-resolve.
- **Видимость**: guard эффекта `if (!authed) return; if (!pageVisible &&
  !settings.enabled) return;` — при включённых алертах опрос идёт и в
  скрытой вкладке (троттлится браузером до ~1/мин), при выключенных —
  прежняя пауза.
- **Зависимости эффекта**: `[authed, pageVisible, settings.enabled]` —
  только тумблер, не пороги. Сами пороги эффект читает из ref
  (`settingsRef.current`, обновляется при сохранении): попади они в deps,
  каждое изменение числа в модалке пересоздавало бы таймер и сбивало
  ритм тика. Ref-паттерн здесь же закрывает и re-baseline — сохранение
  настроек пишет ref, чистит `activeRef` и сбрасывает `syncedOnce`.
- **Тихая первая синхронизация**: ref `syncedOnce`; первый успешный merge
  кладёт активные алерты в список, но `fired` игнорирует (F5 не
  спамит уведомлениями).
- **Re-baseline при смене настроек**: сохранение настроек очищает
  `activeRef` и сбрасывает `syncedOnce` — следующий опрос строит набор
  заново с новыми порогами, молча. Иначе поднятие порога не снимало бы
  алерт (гистерезис по старому порогу) и любая смена порогов
  разбалансировала бы переходы.
- Logout — сброс `activeAlerts`/`syncedOnce` (паттерн соседних состояний
  в `handleLogout`).

### 4. Гистерезис: `web/src/alerts.ts` (новый модуль)

Весь клиентский код алертов в одном файле, без компонентной логики:

```ts
export interface AlertsSettings { enabled: boolean; disk: number; mem: number; load: number; notify: boolean }
export const DEFAULT_ALERTS_SETTINGS = { enabled: true, disk: 90, mem: 90, load: 2, notify: false };
export function loadAlertsSettings(): AlertsSettings;   // localStorage 'sc-alerts', толерантное чтение по полям
export function saveAlertsSettings(s: AlertsSettings): void;

export interface ActiveAlert { key; profileId; kind; subject?; severity; message; value; threshold; since: number }

/** Дельта снятия по kind: пока value > threshold − delta, алерт держится. */
export const ALERT_CLEAR_DELTA: Record<AlertKind, number> =
  { 'server-down': 0, disk: 5, memory: 5, load: 0.5 };

export function alertKey(r: {profileId; kind; subject?}): string;  // `${profileId}:${kind}:${subject ?? ''}`

export function mergeAlertStates(prev: Map<string, ActiveAlert>, rules: AlertRuleState[], now: number):
  { next: Map<string, ActiveAlert>; fired: ActiveAlert[]; resolved: ActiveAlert[] }
```

Семантика merge (единственная нетестируемая сервером логика — 3 ветки,
сознательно минимальная):

- правило было активным (`key in prev`): `effActive = rule.active ||
  rule.value > rule.threshold − ALERT_CLEAR_DELTA[kind]`. Держится —
  обновляем value/message/threshold, `since` сохраняем; снялся → в
  `resolved`. Дельта 0 у server-down вырождает условие в `rule.active`.
- правило новое: `rule.active` → `ActiveAlert {since: now}` в `fired`;
  неактивное — пропуск.
- ключи из `prev`, которых нет в `rules` (профиль удалён, диск
  отмонтирован, load-правило исчезло из-за неизвестных ядер) → `resolved`,
  молча. Вселенная состояний определяется ответом.

Зона нечувствительности: активация по `>=` порога, снятие по `<= порога −
дельта` — на границе 90% алерт не мигает каждые 10 с (кейс roadmap).
Клиентского порога «максимальное время алерта» нет — снимется первым
тиком после ухода значения.

**Подсветка проблемного профиля**: в `profile-list-item` рядом с именем —

**Браузерные уведомления** (только на `fired` после первой синхронизации):

- Условия: `settings.notify && Notification.permission === 'granted' &&

- Тумблер при включении сам вызывает `Notification.requestPermission()`

- `new Notification(profileName, { body: message, tag: alertKey })` —
  тег даёт браузерную дедупликацию повторных всплесков;
  `onclick` → `window.focus()` + переход к профилю.

## Отклонённые альтернативы

- **Вычисление на клиенте из уже приходящего overview** — метрики в
  ответе есть, но во `web/` нет тест-раннера, а правило проекта требует
  unit-тесты на новую логику; серверная `evaluateAlertRules` тестируется
  фиксстурами (аргумент roadmap, принимаем).
- **POST с отдачей клиентом предыдущего состояния, чтобы считать
  гистерезис на сервере** — тестируемо, но превращает stateless-роут в
  протокол с раунд-трипом состояния ради трёх строк клиента; отклонено.
- **CPU-процент как правило** — между опросами в 10 с скачки CPU
  неинформативны, устойчивую нагрузку покрывает `load1/cores`; roadmap
  CPU и не просил.
- **Двухуровневые пороги (warn 90 / crit 95)** — удвоение настроек и
  UI ради градации, которой нет в задачах; crit остаётся у
  недоступности.
- **Слить статус-опрос сайдбара в `/api/alerts`** (брать ok/error из
  server-down-правил) — при выключенных алертах понадобился бы второй
  режим роута; два целевых запроса в одном тике проще и не дороже
  (общий кэш).
- **SSE/WS-пуш алертов** — опрос уже существует и переиспользует кэш;
  пуш — новая инфраструктура ради экономии одного запроса в 10 с.
- **Напоминания (повторные уведомления каждые N минут)** и **история
  алертов** — прямое нарушение рамки roadmap «не превращать в систему
  мониторинга».
- **Скрывать колокольчик при выключенных алертах** — теряется единственный
  вход в настройки; кнопка остаётся, деградирует до приглушённой.

## Тесты

`server/test/alerts.test.ts` (новый, чистые фикстуры без моков):

- server-down: недоступный профиль — active, severity crit, value 1,
  threshold 1, сообщение содержит текст ошибки; доступный — active false,
  value 0; `ok:true` без `metrics` → единственное состояние — server-down;
- disk: несколько дисков — один за порогом, другой нет (по состоянию на
  каждый mount), subject = mount; граница включительно (90.0 при 90 →
  active); `usedPercent: null` → состояния нет;
- memory: за порогом / под / `null` → состояния нет;
- load: `load1 4.2, cores 2` → value 2.1, active при пороге 2; округление
  до 2 знаков (4.3/3 → 1.43); `cores: null` или `loadAverage: null` →
  состояния нет;
- несколько профилей в одном overview — правила всех;
- `DEFAULT_ALERT_THRESHOLDS` = `{90, 90, 2}`.

`server/test/alerts-route.test.ts` (новый, паттерн `file-tail-route.test.ts`:
express-приложение с роутером, `vi.mock('../src/services/overview.js')` на
фикстуру ответа):

- 200 без параметров — дефолты в `thresholds` (echo), форма `rules`;
- `?disk=95&mem=85&load=1.5` — параметры применены (влияют на active
  фикстуры);
- `disk=abc` → 400; `disk=10` → 400; `load=0` → 400.

Ручной сценарий (стенд: сервер + тестовый sshd):

- после входа колокольчик в сайдбаре, пустой список, чипов нет;
- порог диска временно «текущая занятость − 1» (но не ниже 50 — минимум
  схемы и инпута) → в течение ~10 с
  алерт в списке, чип у профиля, счётчик в бейдже;
- возврат порога к 90 → смена настроек сделала тихий re-baseline, алерт
  снят; порог = текущее значение − 2 → алерт держится (гистерезис), не
  мигает при колебаниях значения в зоне порог−5…порог;
- остановить sshd-контейнер → crit «Сервер недоступен» в течение ~18 с
  (тик 10 с + зонд 8 с), статус-точка тоже красная; запуск → алерт снят
  переходом ok;
- включить уведомления (разрешение по клику), свернуть вкладку, уронить
  sshd → уведомление пришло (скрытая вкладка опрашивает, браузер
  троттлит до ~1/мин), клик по уведомлению фокусирует окно и открывает
  «Обзор» профиля;
- F5 при активных алертах → список восстановлен тихо, без уведомлений;
- выключить алерты → опрос в скрытой вкладке не идёт (как раньше),
  колокольчик приглушён, настройки доступны;
- curl: `GET /api/alerts?disk=10` → 400; без параметров — дефолты.

## Риски

- **Работает только при открытой вкладке** — осознанное ограничение
  roadmap; сильнее: при включённых алертах скрытая вкладка опрашивает с
  браузерным троттлингом (~1/мин после нескольких минут) — задержка
  уведомления до минуты, честно.
- **Флап SSH** (ok↔error на плохой сети) → повторные crit-уведомления:
  дельта для булева правила невозможна, принимаем; массово не
  транслируется — уведомления только при `document.hidden`.
- **Один медленный зонд**: мёртвый сервер держит ответ overview до 8 с —
  алерт недоступности приходит не мгновенно, а в пределах тик+зонд;
  таймаут зонда уже существует, не новый риск.
- **Отсутствие полей метрик** (`null`): правило просто не оценивается —
  для load без ядер это постоянное состояние (не временное), алерт
  снимается отсутствием правила во вселенной ответа; для диска/памяти
  `null` на практике означает сломанный снимок всего профиля → там будет
  server-down.
- **Профиль удалён при активном алерте** — ключ исчезнет из ответа,
  алерт снимется молча; отдельной чистки не нужно.
- **Два окна браузера** — независимые наборы алертов и два уведомления
  на одно событие (тег `Notification` частично схлопнет); существующее
  поведение всех клиентских подсистем, не ухудшаем.
- **Клиентский merge без unit-тестов** (нет раннера во фронте) —
  компенсировано: логика сведена к одной чистой функции в изолированном
  модуле, вся математика правил — на сервере под тестами.
