# План: эпик 15 — несколько терминалов на сервер

> Эпик 15 из `docs/roadmap.md` (Tier 1). Дата плана: 2026-08-23.
> Статус: реализовано (2026-08-23), правки по ревью внесены.
> Сервер + фронтенд, новых зависимостей нет.
>
> **Два осознанных отклонения от формулировки roadmap**, оба — следствие
> заметки из плана эпика 14 (`docs/file-tail-plan.md`, раздел «Бюджет
> SSH-каналов»): при взятии 15 в работу пересчитать сумму каналов и,
> возможно, ограничить терминалы сильнее.
>
> 1. **Лимит 4 одновременных терминала на профиль, а не 8** — бюджет
>    `MaxSessions` (см. шаг 1). 8 терминалов физически не лезут.
> 2. **Стабильный `tabId` из localStorage вместо позиционного `index`
>    0..7** — позиция вкладки меняется при закрытии соседей, и после F5
>    «восстановленные по позиции» вкладки не совпадают с живыми сессиями:
>    плодятся дубли, старые умирают в grace. Стабильный id держит
>    соответствие вкладка↔сессия сколь угодно долго.

## Контекст: что уже есть

- `server/src/ws/terminal.ts` — реестр `Map<sessionKey, TerminalSession>`:
  ключ `sessionKey(profileId, container?)` (`ws/terminal.ts:186`) — один
  системный shell + по одному на контейнер, вторую сессию того же рода не
  открыть. Grace 60 c после отсоединения последнего аттачмента
  (`detach`), переиспользование записи при повторном attach, явный
  `destroy` по WS-сообщению `close`. Контейнерная сессия — тот же PTY,
  внутрь пишется `exec docker … sh -c 'exec bash || exec sh'`.
- `server/src/index.ts:120` — подъём `/ws/terminal`: `profileId`, `cols`,
  `rows`, `container` из query, без валидации чисел, кроме cols/rows.
- `server/src/routes/terminal.ts` — REST подсистемы (сейчас только
  `GET /history`), роутер уже под `requireAuth`.
- `web/src/pages/TerminalPage.tsx` — один xterm + один WS, effect по
  `[profile.id, sessionKey, showError, containerId]`; тулбар (статус,
  История Ctrl+R, «Спросить агента», «В чат ▾», «Обновить сессию»),
  палитра истории поверх терминала. При `display:none` — `fit()` по
  возврату `visible`.
- `web/src/App.tsx` — `TerminalPage` смонтирован keep-alive с
  `key={profile.id}`, проп `container={terminalContainer}`; DockerPage
  через `onExecContainer` **заменяет** системный shell контейнерным
  (системный в это время живёт только grace 60 c, потом умирает).
  Паттерн «запрос + consumed» уже есть: `sqlInsert` у DatabasesPage.
- Бюджет SSH-каналов на профиль (одно соединение в `ssh/manager.ts`):
  постоянный SFTP (1) + shell терминалов + follow-стримы (лимит 3,
  `services/stream-limits.ts`) + транзитные разовые exec (метрики и др.).
  OpenSSH `MaxSessions` по умолчанию 10; переполнение сегодня вылезает
  невнятным «Channel open failure».
- `web/src/styles.css` — готовые классы `.tabs` / `.tab` / `.tab.active`
  (строки ~1308) для внутренних вкладок.

## Решение

### 0. Бюджет SSH-каналов (фундамент для лимита)

Постоянные потребители канала одного профиля после эпика:

| Потребитель | Каналов |
|---|---|
| SFTP (`conn.sftpPromise`) | 1 |
| Терминальные вкладки | T |
| Follow-стримы (общий лимитер, эпик 14) | до 3 |
| **Итого постоянных** | **T + 4** |

При `MaxSessions = 10` остаётся `6 − T` слотов на транзитные exec'и
(метрики, снимки портов/служб, чтение файлов). `T = 8` (число из
roadmap) даёт перебор уже в спокойном состоянии; `T = 4` оставляет
запас 2 на транзит. Отсюда:

- `MAX_TERMINAL_SESSIONS_PER_PROFILE = 4` — суммарно системных и
  контейнерных, на профиль;
- число отдаётся фронту из `GET /api/terminal/sessions`, UI дизейблит
  «+» при достижении — серверный отказ остаётся защитой (как 429 у
  follow-лимитера).

Сниженный `MaxSessions` на конкретном сервере админом из бюджета не
выводим — как и сегодня, отказ придёт ошибкой открытия канала в
терминал (error-фрейм), это существующее поведение для всех подсистем.

### 1. Сервер: `server/src/ws/terminal.ts`

- Ключ сессии: `sessionKey(profileId, container, tabId)` →
  `` `${profileId}::${container ?? 'host'}::${tabId}` ``. Чистая функция,
  под unit-тест.
- `attachTerminal(ws, profile, cols, rows, container, tabId,
  containerName?)`:
  - **tabId**: целое 0..9999. Параметр отсутствует в query → дефолт 0 —
    бесшовный деплой: уже открытая вкладка старого клиента продолжает
    работать с единственной сессией `…::host::0`. Параметр есть, но
    невалиден (не-число, дробное, отрицательное, > 9999) →
    `ws.close(1008, 'Invalid tabId')` без создания сессии.
  - **containerName** — только отображение (заголовок вкладки после F5,
    когда имя восстанавливается из серверной сессии); в ключ не входит,
    в shell-команду не попадает (исполняется только `container`-id через
    `dockerCommand`+`shq`, как сейчас). Ограничение — строка ≤ 200
    символов, длиннее обрезается.
  - Существующая сессия по ключу → attach без проверок лимита (это
    переподключение вкладки, не новый канал).
  - Новая сессия → проверка лимита: число **живых** записей профиля
    (`shell !== null || spawning` — именно они держат SSH-канал; grace-
    сессии без аттачментов считаются, shell ещё жив; записи с
    `shell === null` — exit внутри shell — канал освободили и не
    считаются) ≥ `MAX_TERMINAL_SESSIONS_PER_PROFILE` →
    `ws.send({type:'error', data: 'Слишком много терминалов (максимум
    4) — закройте другие вкладки'})` + `ws.close(1013, 'Too many
    terminals')`, сессия не создаётся. Клиентский обработчик error-фрейма
    уже пишет текст в xterm и ставит статус «ошибка» — новых веток на
    фронте не нужно.
- `TerminalSession`: поле `tabId` и `containerName` (для списка),
  метод `isAlive()`.
- **Уборка мёртвых записей (обязательна, иначе утечка).** Сегодня выход
  из shell (`exit`) оставляет запись в `sessions` навсегда:
  `channel.on('close')` (`ws/terminal.ts:49-53`) только обнуляет
  `this.shell` и закрывает аттачменты, а `sessions.delete` живёт лишь в
  `destroy()`. С единственным ключом на профиль это незаметно (запись
  переиспользуется следующим attach), с ключом по вкладке — мапа копит
  запись на каждый `exit`, и эти призраки всплывают в
  `/api/terminal/sessions`: после чистки localStorage UI восстановит из
  них вкладки к несуществующим shell'ам. Поэтому в обработчике `close`
  канала после `cleanupAttachments()` — `sessions.delete(this.sessionKey)`
  (аттачменты сервер в этот момент уже закрыл, реанимировать нечего;
  клиент по close-фрейму переподключается тем же tabId и получает свежую
  запись).
- `listTerminalSessions(profileId)` →
  `{tabId, container: string | null, containerName: string | null}[]` —
  живые записи профиля (после уборки выше мёртвых в мапе не остаётся,
  поле `alive` не нужно).
- Grace, переиспользование, `restart`, буфер `pendingInput`,
  контейнерный `exec` — без изменений; всё работает на новом ключе как
  есть (завет roadmap: «Grace-таймер и переиспользование не меняются»).

### 2. Сервер: `server/src/index.ts`

В ветке `/ws/terminal`: чтение `tabId` и `containerName` из query по
правилам шага 1 (отсутствие tabId → `undefined` → дефолт внутри
`attachTerminal`), проброс в `attachTerminal`. Валидация чисел — как
существующий `cols`/`rows` (безопасный фолбэк), кроме табличных правил
шага 1.

### 3. REST: `GET /api/terminal/sessions`

`server/src/routes/terminal.ts` + zod-схема `?profileId=` (паттерн
`/history`): 404 на неизвестный профиль, иначе
`{sessions: SessionInfo[], limit: 4}`. Импорт `listTerminalSessions` и
константы из `../ws/terminal.js` — новая зависимость routes → ws-модуль;
реестр живёт там, отдельный модуль реестра ради одного импорта —
переусложнение. Циклов нет (`ws/terminal.ts` routes не импортирует).

### 4. Фронтенд: TerminalPage → таббар + TerminalView

Декомпозиция `web/src/pages/TerminalPage.tsx`:

- **`TerminalTab`** (`web/src/types.ts`):
  `{ id: number; container?: { id: string; name: string } }`.
- **`TerminalView`** (в том же файле) — текущий терминальный блок почти
  без изменений: xterm + WS + тулбар + палитра истории. Изменения против
  нынешнего кода:
  - пропы `{profile, tab, active, visible, showError, onAskAgent,
    onStatus(tabId, status)}` вместо `container`/`onExitContainer`;
    `containerId = tab.container?.id`;
  - WS URL: `…&tabId=<tab.id>` (+ `&container=&containerName=` для
    контейнерной);
  - статус репортится вверх колбеком `onStatus` — точка в заголовке
    вкладки; текст статуса и чип контейнера остаются в тулбаре (он
    рендерится внутри активной вкладки);
  - `fit()` — по `active` (переключение внутренней вкладки) и по
    `visible` (возврат на терминальную вкладку приложения) — оба случая
    нынешнего `display:none`;
  - cleanup effect'а: `{type:'close'}` перед `ws.close()` шлётся **только
    при явном закрытии вкладки пользователем** — по ref-флагу
    (`closeOnUnmountRef`), который выставляет обработчик «✕» перед
    удалением вкладки из стейта. Безусловная отправка на любом unmount'е
    была бы регрессом: `TerminalPage` смонтирован с `key={profile.id}`
    (`App.tsx:425`), то есть переключение профиля размонтирует страницу —
    сегодня сессия переживает это grace-таймером (вернулся в течение
    60 c — тот же shell с запущенным процессом), а безусловный `close`
    убивал бы все терминалы профиля при каждом переходе. F5 и закрытие
    окна браузера React-cleanup не вызывают вовсе — там grace как
    раньше. Кнопка «Системный
    shell» уходит (вкладки сосуществуют), «Обновить сессию», «История»
    (host-вкладки), «Спросить агента», «В чат» — без изменений, действуют
    на свою вкладку.
- **`TerminalPage`** — стейт вкладок:
  - `tabs: TerminalTab[]`, `activeTabId: number | null`, `nextId`
    (монотонный счётчик, живёт в localStorage — вкладка сохраняет id на
    всю жизнь);
  - **localStorage** `sc-terminal-tabs:<profileId>`:
    `{tabs, nextId, activeId}`. Чтение с валидацией: массив объектов,
    целые id ≥ 0, `container` с строковыми id/name — мусорные элементы
    отбрасываются; `nextId = max(maxId + 1, сохранённое)`; пусто/бито →
    одна вкладка `{id: 0}`. Запись — при каждом изменении tabs/activeId.
  - **сверка с сервером** при монтировании: `fetchTerminalSessions` →
    серверные сессии, которых нет среди вкладок (по `tabId` +
    `container`), добавляются как вкладки (имя контейнера — из
    `containerName` сессии); итог обрезается до `limit` из ответа —
    хвост режется из локальных вкладок без серверной сессии. Так после
    чистки localStorage / другого браузера живые сессии не остаются
    невидимыми зомби до grace;
  - таббар: переиспользовать `.tabs`/`.tab`, кнопка вкладки = заголовок
    (host: `shell N`, N = `tab.id + 1` — стабильно и уникально;
    контейнерная: имя контейнера, title = id) + статус-точка + «✕»
    (закрытие: выставить `closeOnUnmountRef` вкладки и
    удалить её из tabs; cleanup TerminalView по флагу шлёт `close`-фрейм
    → destroy на сервере, grace не занимается); «+» —
    новая host-вкладка, disabled при `tabs.length >= limit` с подсказкой;
  - все вкладки смонтированы keep-alive (как внешние вкладки App):
    неактивные — `display:none`, каждая держит свой WS. Это осознанный
    расход бюджета: до 4 каналов на профиль, лимит шага 0 им управляет;
    ленивое подключение (WS только у активной) отвергнуто — уход с
    терминальной вкладки убивал бы сессии через grace 60 c, что хуже
    нынешнего поведения;
  - закрываются все вкладки → пустое состояние `.empty-state` с кнопкой
    «Открыть терминал» (эквивалент «+»).

### 5. Фронтенд: App.tsx + DockerPage — контейнер вкладкой

- Убрать `terminalContainer` / `onExitContainer`.
- `terminalOpenRequest: {id: string; name: string} | null` +
  `onOpenRequestConsumed` — паттерн `sqlInsert` у DatabasesPage:
  `onExecContainer` в DockerPage → `setTerminalOpenRequest({id, name})` +
  `setTab('terminal')`.
- TerminalPage effect на `openContainerRequest`: вкладка этого
  контейнера уже есть → активировать её; нет → добавить
  `{id: nextId++, container}` и активировать; вызвать consumed.
- Смена профиля сбрасывает `terminalOpenRequest` (запрос мог остаться от
  прошлого профиля — контейнер чужого сервера).

### 6. Фронтенд: api.ts, styles.css

- `fetchTerminalSessions(profileId)` → `{sessions, limit}` (паттерн
  `fetchTerminalHistory`).
- `.terminal-tabs` на базе существующих `.tabs`/`.tab`: статус-точка
  внутри вкладки (переиспользовать `status-dot`), «✕» с hover-danger
  (паттерн чипов логов эпика 14), `scrollbar-gutter: stable` при
  переполнении.

## Отклонённые альтернативы

- **8 терминалов (число roadmap)** — не лезет в `MaxSessions = 10`
  вместе с SFTP и follow-лимитом эпика 14 (заметка в file-tail-plan
  прямо требовала пересчёта).
- **Позиционный index 0..7 (формулировка roadmap)** — нестабилен: закрытие
  средней вкладки сдвигает индексы соседей, F5-восстановление по
  позициям не сходится с живыми сессиями, плодятся дубли. Стабильный
  `tabId` из localStorage решает это ценой одного счётчика.
- **Серверная генерация id сессии** — клиент был бы вынужден сверять
  id до отрисовки вкладок, дороже localStorage-счётчика при тех же
  свойствах.
- **Ленивые WS (канал только у активной внутренней вкладки)** — уход с
  терминальной вкладки приложения убивал бы сессии grace-таймером;
  противоречит keep-alive-духу layout (эпик 0) и ухудшает текущее
  поведение переживания сколь угодно долгого отсутствия.
- **Общий реестр каналов для терминалов + follow-стримов** — один лимит
  на всё звучит строго, но режимы жизни разные (терминал — часы,
  follow — минуты): взаимное вытеснение запутывает. Два независимых
  лимита (4 и 3) с общим запасом транзита проще и предсказуемее.
- **Перенос реестра сессий из `ws/terminal.ts` в отдельный модуль ради
  чистоты импорта из routes** — переусложнение; прямой импорт функции
  без цикла достаточно.

## Тесты

`server/test/terminal-ws.test.ts` (новый): `vi.mock` на
`../src/ssh/manager.js` (фейковый `openShell` → `ShellSession` с
каналом-EventEmitter, `closeProfileConnection` — заглушка; паттерн мока
`helpers/fake-ssh2.ts`, но здесь достаточно мока менеджера — ssh2 не
нужен) + фейковый WS (EventEmitter с `send`/`close` и записью вызовов):

- `sessionKey`: host/container × tabId, стабильность формата;
- валидация tabId: отсутствует → дефолт 0 и сессия создана; невалидный
  (не-число, дробный, отрицательный, > 9999) → close(1008), запись не
  создана;
- лимит: 4 живые сессии → пятая новая получает error-фрейм + close(1013);
  повторный attach к существующей поверх «полного» лимита проходит;
- exit внутри shell (эмит `close` канала) → запись удалена из мапы
  (`listTerminalSessions` её не отдаёт), слот освобождён — новая сессия
  того же tabId проходит и создаёт свежую запись;
- WS-сообщение `close` → destroy → слот освободился, следующая сессия
  создаётся;
- `listTerminalSessions`: поля tabId/container/containerName, фильтр по
  профилю, мёртвых записей в выдаче нет.

`server/test/` без изменений по составу, но прогон всего набора —
регресс (маршрут `/sessions` добавляется в `routes/terminal.ts`).

Ручной сценарий (`server/test/integration.manual.mjs`, расширить):

- две вкладки: независимый ввод и вывод, вывод не пересекается;
- закрытие средней из трёх — соседние вкладки продолжают работать
  (стабильность tabId: их сессии не пересоздались);
- F5: вкладки восстановлены, живые сессии подхвачены (хвост вывода
  продолжает приходить), буферы xterm пустые — ожидаемо;
- чистка localStorage при живых сессиях → вкладки восстановлены из
  `/api/terminal/sessions`;
- терминал контейнера из Docker Explorer: добавляется вкладкой,
  системный shell продолжает жить; повторный клик того же контейнера —
  активируется существующая вкладка;
- пятая вкладка: «+» задизейблена; при обходе (удаление вкладки из
  DevTools-стейта) сервер отвечает ошибкой в терминал;
- `exit` в одной вкладке — «сессия завершена», соседние живы,
  «Обновить сессию» поднимает shell в той же вкладке;
- закрытие окна браузера целиком → через 60+ с сессии сняты (нет
  зомби-каналов).

## Риски

- **Два окна браузера одновременно**: одинаковые localStorage-ключи дают
  одинаковые tabId — окна прицепляются к одним сессиям, ввод дублируется
  в оба. Это существующее поведение (сегодня оба окна делят одну
  сессию), не ухудшается; документируем, не решаем.
- **Краш клиента / обрыв без close-фрейма**: слоты заняты до grace 60 c
  — до 4 «висящих» терминалов блокируют новые на минуту; сообщение об
  ошибке понятное, состояние само сходится.
- **`MaxSessions` снижен админом сервера**: отказы «Channel open failure»
  при меньшем числе вкладок — вне бюджета приложения (как сегодня для
  любых каналов); текст ошибки виден в терминале.
- **localStorage повреждён** → старт с одной вкладки, живые сессии
  вернутся сверкой `/api/terminal/sessions`.
- **Смена профиля** размонтирует TerminalPage (`key={profile.id}`): без
  флага «закрыто пользователем» cleanup убил бы сессии всех вкладок —
  отсюда правило «close-фрейм только по ✕» (шаг 4); при возврате в
  пределах grace 60 c shell'ы прежние, буферы xterm пустые (как сегодня).
- **follow-стримы + 4 терминала + SFTP = 8 постоянных**: транзитным
  exec'ам остаётся 2 слота — при всплеске параллельных запросов возможны
  редкие отказы канала; кэши 2 с на профиль (метрики/порты/cron) держат
  параллелизм низким.
