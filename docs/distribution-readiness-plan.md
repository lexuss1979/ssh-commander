# План: установка из образа и подготовка к продвижению

Статус: реализация подготовлена, CI в GitHub прошёл. Релиз `v0.1.1` и публикация GHCR ожидают согласования владельца. План и реализация: 2026-09-10.

Ниже сохранён согласованный объём. Фактические результаты и оставшиеся шаги записаны в конце; подготовленный workflow не означает, что образ уже опубликован.

## Цель и границы

Пользователь скачивает проверенный готовый образ, запускает приложение без Git и локальной сборки, подключает сервер по существующему руководству. На GitHub видны автоматические проверки и понятен порядок обращения с проблемами и уязвимостями.

Сохраняем позиционирование: **личный AI DevOps**, который помогает запустить проект на VPS и разобраться в проблемах. Ручные инструменты дополняют агента, но не заменяют главное сообщение. Существующие README и ролики целиком не переделываем.

В объём входят:

- CI на push и pull request.
- Публикация готовых образов в GHCR для `linux/amd64` и `linux/arm64`.
- Установка из образа, обновление и безопасное сохранение пользовательских данных.
- `SECURITY.md`, `CONTRIBUTING.md`, шаблоны bug/feature, приватный канал сообщений об уязвимостях.
- Короткий блок доверия в README ru/en и два настоящих PNG-скриншота.
- Подготовка одного PR в awesome-ssh как отдельный необязательный шаг, без автоматической отправки.

Не входят: шифрование хранилищ, переработка аутентификации, новые функции агента, телеметрия, большой сайт документации, пересъёмка роликов, массовые анонсы, статьи и обещания новых возможностей в roadmap. Не повышать версию до `1.0.0` ради продвижения.

## Этап 1. CI

1. Изучить `AGENTS.md`, `Dockerfile`, package.json/lock-файлы обоих модулей и `scripts/pre-commit.sh`. Не добавлять новый набор проверок, расходящийся с локальными командами.
2. Добавить workflow на push в `main` и `pull_request`. Обеспечить возможность использовать те же проверки при выпуске образа, например через reusable workflow.
3. Через `npm ci` установить зависимости; выполнить сборки server/web, `npm test` сервера, `npm run lint` web и оба `npm audit --audit-level=low`. Unit-тестам не нужны реальный SSH, sudo-пароли или платный AI API. Ошибку сети при audit не выдавать за отсутствие уязвимостей.
4. Проверить текущую совместимость runtime и actions по официальным источникам. Не совмещать задачу с несвязанным обновлением major-версий зависимостей. Actions закрепить на проверенных полных commit SHA с понятными комментариями о версиях.
5. Для обычного CI достаточно `contents: read`; не передавать секреты и право публикации в PR-проверки. Не использовать `pull_request_target` для исполнения кода из PR.
6. Добавить ограничение времени и отмену устаревших CI-запусков одной ветки. Политику отмены публикации образов определить отдельно: не прерывать уже начатую публикацию общим правилом CI.

Приёмка: зелёный запуск на GitHub с видимыми результатами всех проверок; проверено поведение PR-workflow без секретов. Бейдж в README добавляется только для реально существующего workflow. Сам по себе зелёный бейдж не является гарантией безопасности продукта.

## Этап 2. Образы GHCR

1. Целевое имя: `ghcr.io/lexuss1979/ssh-commander`. Проверить, не существует ли пакет, его владельца, права и связь с репозиторием. Ничего существующего не перезаписывать вслепую.
2. Выпускать образ из точного релизного коммита после успешных проверок этого же коммита. Предпочтительный триггер — тег формата `vX.Y.Z`; автоматический запуск на произвольной ветке или PR не должен публиковать образы. Продумать ручной повтор неудавшегося выпуска без пересоздания тега.
3. Для публикации использовать `GITHUB_TOKEN` с `packages: write` только в нужном job. Не заводить и не сохранять личный registry-токен, если стандартного механизма достаточно.
4. Собирать `linux/amd64` и `linux/arm64`, публиковать общий manifest. Архитектура относится к компьютеру, где запущен ssh-commander, а не к управляемому по SSH серверу. Не обещать поддержку 32-битного ARM.
5. Проверить сборку и запуск обеих архитектур. Если ARM проверен через эмуляцию, явно зафиксировать это; не выдавать такую проверку за тест на физическом Raspberry Pi или Mac. QEMU и native runner выбирать по доступности и фактическому времени сборки.
6. Теги: точная версия, например `0.1.1`, и `latest` только для успешно проверенного стабильного выпуска. Не обновлять `latest` из prerelease. Точную опубликованную версию не пересобирать с другим содержимым; сохранять digest и соответствующий Git SHA.
7. Добавить OCI-метаданные: source repository, revision, version, license. Образ не должен содержать исходные секреты, `data/`, `keys/`, `.env`, `promo/`, историю Git или devDependencies runtime. Проверить `.dockerignore`; исключить локальные артефакты из build context там, где это необходимо.
8. Отдельно проверить публичность GHCR-пакета: публичность репозитория не достаточное доказательство. Убедиться в анонимном pull обеих платформ с пустым временным Docker credential config, не разлогинивая пользователя глобально.

Приёмка: manifest содержит обе платформы; скачанный по версии/digest образ запускается на изолированном стенде, отдаёт интерфейс и `/api/setup/status`; первоначальная настройка проходит без реального AI-ключа. Зафиксированы ссылки на workflow, пакет, digest и исходный коммит.

## Этап 3. Установка и обновление

Консервативный вариант: сохранить существующий `docker-compose.yml` для production-сборки из исходников и добавить самостоятельный **`docker-compose.release.yml`** для готового образа. Dev-режим оставить отдельным и рабочим. Не создавать цепочку overrides, требующую Git-клона ради простой установки.

1. Release Compose использует конкретную выпущенную версию образа, не только плавающий `latest`. Публикация панели и SSH-туннелей остаётся только на `127.0.0.1`; volumes `./data:/data` и `./keys:/keys`, runtime-настройки и парольный onboarding сохраняются.
2. Предложить путь без Git: создать отдельную папку, скачать этот Compose из конкретного тега/релиза как `compose.yaml`, выполнить `docker compose up -d`. Дать корректные варианты команд для PowerShell и Linux/macOS. Использовать только существующие публичные URL; не направлять установку релизной версии на случайный текущий `main`.
3. Обновить Quick start в README ru/en и оба getting-started: готовый образ — основной путь, сборка из исходников остаётся доступной по отдельной инструкции. Не потерять пояснение, что приложение запускается локально, а SSH-адрес VPS указывается отдельно.
4. Описать обновление: резервная копия `data/` и `keys/`, проверка release notes, осознанная смена версии образа, `docker compose pull`, затем `docker compose up -d`. `.env` после первого запуска не меняет уже сохранённые AI-настройки и пароль приложения.
5. Не обещать, что откат образа всегда откатит данные. Для несовместимого изменения формата могут понадобиться бэкап и отдельная процедура. Не предлагать удаление volumes как способ обновления.
6. Проверить как чистую установку, так и переход с source-build на image-based запуск на тестовых данных. Исключить одновременный доступ двух экземпляров к одному каталогу данных и конфликты имени контейнера/портов.
7. Актуализировать команды и инварианты в `AGENTS.md` и связанных инструкциях, которые затронет новый способ установки. Код приложения менять только при обнаруженном блокере этого пути, не добавлять попутные рефакторинги.

Приёмка: установка из пустой папки проходит без Git и Node/npm на машине пользователя; локальные данные сохраняются после пересоздания контейнера; старый source-build и dev-режим не сломаны. Для каждого заявленного способа запуска зафиксировать фактически выполненную проверку, не подменять Windows/macOS-тест проверкой только на Linux.

## Выпуск и контроль объёма

Предлагаемая следующая версия — `v0.1.1`, номер и момент публикации подтвердить с владельцем. Новые workflows и release Compose не могут задним числом появиться в `v0.1.0`; не изменять старый тег и не маркировать новый исходный код старой версией образа.

Порядок: локальная реализация → CI в GitHub → согласование следующего выпуска → тег и GHCR-публикация → анонимный pull и smoke-проверки → проверка всех публичных инструкций. Если новый путь устанавливается только после публикации пакета, не объявлять его проверенным до этого. При сбое остановиться, указать точный этап и не выдавать частичный выпуск за завершённый.

Перед сдачей выполнить предусмотренные `AGENTS.md` сборки, тесты, lint и audit, проверку ссылок и финальный Gitleaks. Нельзя маскировать ошибку отключением проверки, ослаблением SSH guard или расширением доступа приложения в сеть. Временные контейнеры/данные убрать, рабочую установку пользователя сохранить.

По завершении обновить статус этого плана и записать факты: коммиты, версия, workflow runs, digest, платформы и ограничения тестирования, публичные ссылки, остаточные проблемы. Незапущенные или заблокированные проверки отметить отдельно. Внешние посты в этот этап не входят.
