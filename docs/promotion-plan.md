# Первый публичный запуск ssh-commander

Обновлено 2026-09-10. Решение автора: готовить `v0.1.0`, публиковать проект и переходить к продвижению. Статус самого релиза проверяется на GitHub; этот план не означает, что публикация уже состоялась.

## Сообщение

**Твой личный AI DevOps: помогает запустить проект на VPS и разобраться, если что-то сломалось.**

Новичку помогает начать, опытному специалисту помогает быстрее исследовать сервер и выполнить задачу. Агент работает через SSH: пользователь не переносит команды и вывод между отдельным чатом и консолью. Изменения требуют подтверждения.

Главное демо: `new-vps` → просьба настроить Nginx → подтверждения → HTTP 200 → открытая страница. Диагностика заполненного диска остаётся вторым примером. Новые кейсы не блокируют выпуск.

Приложение бесплатно, MIT. Серверы и AI API оплачиваются отдельно; свой ключ или совместимый собственный endpoint. Не обещаем фиксированную стоимость, безошибочность, автономное дежурство или уникальность относительно всех конкурентов. Личные переписки, имена, скриншоты расходов и цитаты не публикуем без согласования; типовые задачи можно описывать без привязки к человеку.

## Выпуск v0.1.0

1. Проверить чистый Git, сборки server/web, серверные тесты, lint и оба npm audit. Повторить Gitleaks на всей достижимой истории финального коммита, включая merge-diff. Результаты и ограничения проверки: [publication-readiness.md](publication-readiness.md).
2. Проверить доступ владельца к GitHub, существующие теги и релизы. Сохранить финальный changelog, создать аннотированный тег на проверенный коммит, отправить тег и опубликовать GitHub Release. Не передвигать опубликованный тег.
3. Обновить About и топики; перевести репозиторий в public. Не менять права других репозиториев или глобальные настройки аккаунта.
4. Без авторизации проверить README ru/en, GIF/MP4, страницу релиза и клонирование репозитория. Убедиться, что инструкция установки указывает на существующий тег.
5. Только после этих проверок переходить к внешним анонсам. Тексты и метаданные выпуска хранятся в локальном `promo/`; публикация постов согласуется отдельно.

## Первая неделя

**Первый выход:** один небольшой анонс в знакомом автору сообществе про VPS/Linux/homelab, где разрешены авторские проекты. Ролик, задача обычными словами, ссылка на репозиторий, честное описание оплаты и ограничений. Один призыв: попробовать свою задачу на тестовом сервере и рассказать, что получилось или где застряли.

**Следующие 2–3 дня:** отвечать на вопросы, собирать воспроизводимые проблемы установки и первого подключения. В первую очередь исправлять препятствия на пути к первой выполненной задаче. Не расширять список функций ради запуска.

**Второй выход:** после разбора первых проблем подготовить Show HN. Ссылка ведёт на доступный проект, который можно запустить; автор объясняет личную мотивацию и участвует в обсуждении. Не просить друзей голосовать или писать комментарии. Основание: [правила Show HN](https://news.ycombinator.com/showhn.html), проверены 2026-09-10.

r/selfhosted остаётся кандидатом на отдельный анонс: перед отправкой вручную проверить действующие правила сообщества и ограничения самопромо. [Страница правил](https://www.reddit.com/r/selfhosted/about/rules) при автоматической проверке 2026-09-10 не отдала текст правил; разрешённость поста пока не подтверждена.

Не отправлять все анонсы в один день: оставить время на ответы и исправления. Хабр, каталоги и подборки отложить до первых результатов. Платную рекламу и ежедневное ведение соцсетей не планируем.

## Что считать результатом

Вести короткие заметки без секретов и приватных логов: источник знакомства, удалось ли запустить приложение и подключить сервер, первая задача и её результат, вернулся ли человек с новой задачей. Данные только из добровольной обратной связи; телеметрию в приложение для этого не добавляем.

Критерий полезности первого запуска: несколько людей самостоятельно дошли до результата, известны основные препятствия, есть повторное использование. Звёзды и просмотры учитывать как интерес, а не как число активных пользователей. Число API-запросов не равно числу решённых задач.
