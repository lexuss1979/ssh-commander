# Очередь сообщений агента (issue #6)

## Задача

Пользователь должен иметь возможность писать агенту во время выполнения: корректировать текущую задачу (`steer`), оставить следующее сообщение в очереди и удалить ещё не применённое сообщение. Параллельные циклы в одном диалоге запрещены.

## Модель сообщений

В `Dialogue` добавляется опциональное поле `messageQueue`. Элемент:

```ts
{
  id: string;
  content: string;
  kind: 'steer' | 'queue';
  planMode?: boolean;
  createdAt: number;
}
```

Очередь персистится в `ai-dialogues.json` и возвращается в детали диалога. Отсутствие поля читается как пустая очередь, старые файлы не переписываются. Максимум — 20 ожидающих сообщений на диалог; размер одного сообщения ограничен схемой хранилища (32 000 символов).

Ожидающий элемент — ещё не пользовательский ход: его нет в `messages`, он не попадает в контекст модели и не создаёт расходов. При применении сначала одной store-first записью сохраняются новый обычный `role: 'user'` и оставшаяся очередь, затем элемент удаляется из памяти сессии и отправляется клиентам событием `message`. Сбой persist оставляет и память, и стор в прежнем состоянии. Удалённый до этой точки элемент никогда не попадёт ни в историю, ни в API-запрос.

## Семантика отправки

WS-фрейм `message` получает `delivery: 'steer' | 'queue'` (по умолчанию `queue`). В простое оба варианта ведут себя как прежняя обычная отправка: очередь не нужна. Во время выполнения сообщение сохраняется в очереди, второй цикл не запускается.

### Steer

- Steer корректирует **текущую** задачу и обгоняет обычные queued-сообщения.
- Не прерывает текущий API-запрос, выполняющийся инструмент или ожидание approve/reject.
- Безопасная граница — после текущего ответа модели и всех его tool results (выполненных или отклонённых), но до следующего API-запроса. Если ответ без инструментов уже получен, steer применяется до `done`.
- Если к одной границе накоплено несколько steer, они применяются в порядке отправки. Обычная очередь при этом остаётся на месте.
- Steer продолжает текущий цикл и не сбрасывает счётчик `AI_MAX_STEPS`. Если бюджет уже исчерпан, элемент остаётся в очереди и после терминального `done` запускается как новый пользовательский ход со свежим бюджетом.
- `planMode` у steer не меняет режим текущего цикла. Во время составления плана steer добавляется как правка и запускает следующий planning-запрос без инструментов.

### Обычная очередь

- Queued-сообщения не прерывают текущую задачу.
- После терминального состояния текущего цикла первый оставшийся элемент автоматически запускается как новый пользовательский ход. Между queued-сообщениями соблюдается FIFO.
- Автозапуск возможен только при живом сокете и отсутствии `planPending`: без клиента очередь остаётся persisted до attach, а готовый план не снимается следующим сообщением.
- Новый ход получает новый бюджет `AI_MAX_STEPS`; `planMode` элемента определяет `runPlan` или `runLoop`.
- Автозапуск относится только к явно отправленным пользователем сообщениям. Синтетического автопродолжения после `stepLimitReached` не появляется: issue #5 по-прежнему требует нажатия «Продолжить», если очередь пуста.

## Delete и Stop

WS `delete_queued {id}` удаляет только ожидающий элемент. Операция идемпотентна: уже применённый/удалённый id не даёт ошибки, клиентам просто рассылается актуальный снимок. Применённое сообщение остаётся в истории.

Пользовательский `stop` означает остановку всей работы диалога: прерывается текущий цикл, pending approve разрешается `aborted`, очередь очищается. Это исключает неожиданный запуск следующего сообщения сразу после «Стоп». Пока остановка не завершилась, новые enqueue отклоняются локализованной ошибкой и не сохраняются.

Ошибка API завершает текущий цикл; явно поставленные пользователем сообщения затем обрабатываются по тем же правилам. Каждый такой запуск был инициирован пользовательским Enter, а не автоповтором неуспешного API-запроса.

## WS и reconnect

Сервер рассылает полный снимок:

```ts
{ type: 'message_queue', items: QueuedAgentMessage[] }
```

Снимок отправляется после enqueue/delete/apply/clear и при подключении. Полный снимок вместо дельт устраняет расхождения после гонок.

Реестр остаётся одним на домашний профиль, но повторное подключение к **тому же диалогу и языку** присоединяет сокет к существующему `AgentSession`: текущий цикл не останавливается. Все подключённые сокеты получают события и изменения очереди. Новому подключению дополнительно отправляются `running`, `plan_ready`, активный `tool_start` и текущий `tool_pending`, чтобы восстановить UI. Отсоединение одного сокета не останавливает сессию; когда не остаётся подключений, sudo-пароли очищаются, pending approvals разрешаются `aborted`, а следующий queued-цикл не запускается до attach.

Переключение профиля на другой диалог или смену языка по-прежнему останавливает прежнюю сессию, но с `clearQueue: false`: введённые сообщения сохраняются. Старые сокеты закрываются, сессия становится retired и больше не принимает клиентские фреймы. Это сохраняет существующую модель «один активный диалог на профиль».

## UI

Во время выполнения поле ввода остаётся доступным. Основная кнопка отправляет `steer`, вторая — `queue`. Над полем отображается очередь с типом, текстом и кнопкой удаления. В ленту пользовательское сообщение попадает только при применении сервером, а не оптимистично при enqueue.

Pending approve остаётся на своём прежнем месте и не блокирует набор/постановку сообщений. Steer не заменяет решение approve: пользователь должен явно подтвердить или отклонить висящий вызов.

## Мультисерверность и расходы

Очередь принадлежит диалогу, поэтому домашний и дополнительные серверы, approval mode и маршрутизация инструментов не меняются. Каждый применённый элемент использует уже существующий учёт `chat`/`plan` и `web_search`; ожидание и удаление бесплатны.

## Проверки

- enqueue во время удержанного API-запроса не создаёт второй цикл;
- FIFO обычной очереди и приоритет steer;
- delete до применения исключает текст из всех последующих запросов;
- steer после tool results и после approve;
- stop очищает очередь и не запускает следующий элемент;
- reconnect к тому же диалогу сохраняет цикл, синхронизирует два сокета и текущий approve;
- восстановление персистентной очереди и REST-детали диалога;
- planning-запросы остаются без tools;
- стандартные сборки, серверные тесты и web lint.
