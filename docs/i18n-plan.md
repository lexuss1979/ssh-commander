# План: локализация интерфейса (i18n) — английский, перспектива китайского

> **Статус: РЕАЛИЗОВАНО (фазы 1–2) в ветке `i18n`** — UI на словарях
> ru/en с переключателем в сайдбаре, `AI_LANG` + английский промпт
> агента. Исполнение велось по runbook `docs/i18n-execution-plan.md`;
> отложенные фазы 3 (zh) и 4 (серверные ошибки на коды) остаются
> открытыми. Ниже — исходный текст плана с решениями обсуждения:
> локализация имеет смысл **только** в сценарии публикации проекта
> (личный инструмент — ROI около нуля); целевой язык — **английский**,
> русский остаётся; **китайский в v1 не делаем** (обоснование ниже), но
> архитектура словарей должна позволять добавить его одним файлом позже.

## Зачем

Публикация на GitHub для англоязычной self-hosted/homelab-аудитории
практически требует английского UI: README может быть идеальным, но
продукт, открывающийся русским интерфейсом, не пройдёт первые 15 секунд
знакомства. Каждая новая фича добавляет захардкоженных строк — чем раньше
вынос, тем дешевле.

## Текущее состояние (кратко)

- Никакой i18n-инфраструктуры нет: все строки захардкожены по-русски прямо
  в JSX и TS.
- Масштаб: кириллица в ~29 файлах `web/src` (≈500–700 UI-строк) и в ~70
  файлах `server/src` (там преимущественно комментарии — их не трогаем).
- Три слоя русского текста с разной судьбой (см. ниже).
- Прецедент переключателя с persist: тема — атрибут `data-theme` на
  `<html>` + `localStorage` (`web/src/styles.css`, переключатель в
  сайдбаре). Язык делаем по той же схеме.
- Прецедент тестирования клиентского модуля серверным раннером:
  `web/src/alerts.ts` покрыт `server/test/alerts-merge.test.ts` — ту же
  схему используем для проверки паритета словарей.

## Цели и не-цели v1

**Делаем (v1):**

- Слой 1 — UI-строки фронтенда: вынос в словари `ru`/`en`, переключатель
  языка в сайдбаре (рядом с темой), выбор в `localStorage` (`sc-lang`),
  дефолт из `navigator.language` (`ru*` → ru, иначе en).
- Слой 3 — язык агента: env `AI_LANG` (`ru` по умолчанию, `en`); системный
  промпт и инструкция `[[SUGGEST]]` — два варианта текста. Содержимое
  диалогов и `MEMORY.md` не переводится (это данные пользователя).
- README на английском (по плану продвижения — это пререквизит публикации,
  здесь не дублируем).

**Не делаем в v1 (осознанно):**

- **Слой 2 — серверные сообщения об ошибках.** Тексты 400/502 («Неверный
  sudo-пароль», «Превышено время ожидания...»), сообщения алертов, находки
  security-аудита, ошибки bootstrap генерируются на сервере по-русски и
  показываются как есть. Полноценный перевод = перевод сервера на коды
  ошибок (`{code}` + маппинг на клиенте) — рефакторинг обработки ошибок
  почти во всех routes/services, самая рискованная часть (трогает живые
  пути ошибок). В v1 принимаем как известное ограничение: UI английский,
  тексты ошибок могут быть русскими. Отдельная фаза 2 — только если
  появится внешняя аудитория, которой это мешает.
- **Китайский (zh).** Обоснование: аудитория self-hosted OSS
  англодоминантна (r/selfhosted, HN, awesome-листы, обзорщики — всё на
  английском); китайские разработчики массово пользуются англоязычными
  репозиториями. Цена третьего языка — не разовая: каждая новая UI-строка
  навсегда ×3, а качество машинного zh-перевода без носителя проверить
  нечем. Архитектура словарей (ниже) делает добавление zh одним файлом —
  вернёмся, если появится спрос или контрибьютор-носитель.
- Без новых зависимостей: react-i18next не берём — проект избегает тяжёлых
  зависимостей, а нужный объём (словарь + `t()` + контекст) — ~100 строк
  своего кода.

## Архитектура (фронтенд)

- `web/src/i18n/ru.ts`, `web/src/i18n/en.ts` — плоские словари
  `{ 'files.title': 'Файлы', ... }`. Ключи — пространства по страницам
  (`files.*`, `docker.*`, `agent.*`, `common.*`).
- `web/src/i18n/index.ts`:
  - тип ключа — `keyof typeof ru` (tsc ловит опечатки и пропуски — критично,
    т.к. тестов у фронтенда нет);
  - `t(key, params?)` — интерполяция `{name}`-плейсхолдеров;
  - `LangProvider` + `useT()` (React context), переключение — setState +
    `localStorage`, без перезагрузки.
- Переключатель в сайдбаре по образцу темы (иконка, ru/en).
- Форматирование дат/чисел: где сейчас зашит `ru-RU` — от языка интерфейса.

## Процесс выноса строк

Механический, файл за файлом (29 файлов), от маленьких к большим. На
каждый файл: строки → словарь ru, перевод → en. Объективный критерий
завершения: `grep \p{Cyrillic} web/src` оставляет только комментарии и
словарь `ru.ts`.

## Сервер (слой 3)

- `AI_LANG` в `config.ts` (дефолт `ru`), документация в AGENTS.md/.env.example.
- Системный промпт агента (`agent.ts`) и `PLAN_MODE_INSTRUCTION` (`plan.ts`)
  — выбор текста по `AI_LANG`; правила `[[SUGGEST]]` сохраняются в обоих
  вариантах.
- Тесты: выбор промпта по `AI_LANG` — unit в существующем раннере.

## Тесты

- `server/test/i18n.test.ts` (прецедент `alerts-merge.test.ts` — клиентский
  модуль серверным раннером): паритет ключей ru/en (объекты равны по
  множеству ключей), интерполяция плейсхолдеров, дефолт языка.
- `npm run lint` + `tsc` в web: типизированные ключи делают пропуск
  строки ошибкой компиляции.
- Ручной критерий: проход по всем вкладкам в обоих языках — ни одной
  русской строки в UI при en (ошибки сервера — известное исключение).

## Риски

- «Тысяча порезов»: пропущенная строка остаётся русской — косметика, ловится
  финальным grep'ом и ручным проходом.
- Сломанная интерполяция в переведённой строке — минимизируется плоскими
  ключами и тестом плейсхолдеров.
- Рассинхрон словарей при будущих фичах — тест паритета ключей падает при
  добавлении строки только в один словарь.
- Keep-alive вкладки и WS-панель агента: язык — стейт React, переключение не
  должно рвать соединения (тот же инвариант, что у темы).

## Фазы и оценка

| Фаза | Содержание | Оценка |
|---|---|---|
| 1 | Инфраструктура i18n + вынос UI (ru/en) + переключатель | 2.5–3 дня |
| 2 | `AI_LANG` + английский системный промпт | 0.5 дня |
| 3 (отложена) | zh — один файл словаря, когда будет спрос/носитель | ~1 день |
| 4 (отложена) | Серверные ошибки на коды + перевод на клиенте | 1–2 дня |

Итого v1 (фазы 1–2): ~3–3.5 дня, преимущественно монотонная работа с
низким техническим риском.
