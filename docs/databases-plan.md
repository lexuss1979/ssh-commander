### Что меняется концептуально

- Итерация 1: инстанс = обнаруженный контейнер, креденшалы — из его
  env (надежда на официальные образы).
- Итерация 2: **подключение = сохранённая сущность с креденшалами**
  (как подключение в DBeaver/TablePlus). Discovery контейнеров
  остаётся, но лишь автозаполняет форму (движок, контейнер, подсказка
  пользователя из `POSTGRES_USER`/`MYSQL_USER`). Пароль вводит человек
  один раз, дальше работает сохранённое подключение.

### Хранилище подключений

- `DATA_DIR/db-connections.json` — массив подключений, паттерны
  `profiles.ts`: zod-валидация, атомарная запись tmp+rename,
  corrupt-guard (`*.corrupt-*` + отказ persist до рестарта), пароль
  открытым текстом (тот же trust domain, что и `profiles.json` с
  SSH-паролями — осознанный компромисс локального инструмента).
- Поля: `id, profileId, name, engine (postgres|mysql), target
  {kind: 'container', containerId} | {kind: 'host', host, port},
  username, password, defaultDatabase?, createdAt, updatedAt`.
- `kind: 'host'` в модели сразу, но реализация — v2.x: требует
  установленный CLI-клиент на хосте (psql/mysql), детект — кнопкой
  «Проверить подключение» (понятная ошибка «клиент не найден»).
  Контейнерный kind — основной: клиент гарантирован внутри образа.
- Частичный update секрета — как у профилей: непереданный `password`
  сохраняется из существующей записи.

### Передача пароля (ключевой технический пункт)

Пароль пользователя нельзя брать из env контейнера (его там нет или он
протух), а `docker exec -e PGPASSWORD=...` светит пароль в argv/ps на
хосте. Решение — **первая строка stdin**:

```
docker exec -i <c> sh -c 'IFS= read -r PGPASSWORD; export PGPASSWORD;
exec psql -U <user> -d <db> -X -v ON_ERROR_STOP=1 --csv'
```

stdin канала: `<пароль>\n<SQL>`. `read` забирает первую строку, psql
получает остаток. Пароль не попадает ни в argv, ни в env хоста, ни в
логи. MySQL аналогично (`MYSQL_PWD`). `IFS=` и `-r` обязательны
(пробелы по краям и бэкслеши в пароле). Ограничение: пароль не может
содержать перевод строки — документируем. Двойное shq-экранирование
(ssh → docker → sh -c) — под unit-тестами, как в итерации 1.

## Зачем

Работа с БД на управляемом сервере сегодня — два неудобных полюса:

- **Терминал**: `docker exec -it <c> psql -U postgres -d db` — вывод
  без таблиц, столбцами не скопировать, длинный запрос не набрать
  удобно, истории запросов нет.
- **Туннель + десктоп-клиент** (DBeaver и т.п.): тяжёлый путь на каждую
  машину, отдельные подключения, а туннель ещё надо поднять (хотя эпик
  10b это и закрыл).

Середины нет: лёгкой SQL-консоли прямо в инструменте — «выбрал базу,
написал SELECT, увидел таблицу». Это и есть фича.

## Принцип: без избыточности (не-цели)

- **Не клон DBeaver**: без управления пользователями и привилегиями,
  без ER-диаграмм, без визуального редактирования строк, без миграций.
- **Без нативных драйверов** (npm postgres/mysql) и прямых TCP к БД:
  всё через SSH exec + CLI-клиент, уже стоящий на сервере или в
  контейнере. Никаких новых портов и учёток БД в приложении —
  аутентификация ровно та, что у CLI-клиента на месте (в контейнерах
  официальных образов обычно локальный trust).
- **Без постоянных соединений**: один запрос = один exec. Сессионные
  `SET` не переживают запрос — документируем и не имитируем.
- **Движки v1**: PostgreSQL, MySQL/MariaDB. Redis/Mongo и прочие NoSQL —
  отдельный разговор (не SQL; см. открытые вопросы).
- SQL пишет **пользователь**, как в терминале: вкладка — удобство,
  а не новая граница безопасности.

## Что умеет v1 (минимум)

1. **Обнаружение инстансов** на профиле: docker-контейнеры по образу
   (postgres/mysql/mariadb) + слушающие порты 5432/3306 из вкладки
   «Порты» как подсказка («похоже на PG»). Обновление по кнопке, кэш 2 с
   (паттерн `ports.ts`).
2. **Обзор инстанса** (must-have автора): движок и **версия** (тег
   образа + `SELECT version()`/`SELECT @@version`), **список баз с
   размерами** (`pg_database_size` / `information_schema`), **число
   таблиц** на базу. Запросы — теми же каналами, что и SQL-консоль.
3. **Выбор базы** (список баз инстанса) и **список таблиц**; клик по
   таблице — prefill `SELECT * FROM … LIMIT 100`.
4. **Редактор SQL** — CodeMirror с sql-режимом (зависимость уже в
   проекте, `@codemirror/language-data`; подключать через тот же
   `React.lazy`-чанк, что и редактор файлов). Выполнение — Ctrl+Enter.
5. **Результат таблицей**: колонки, строки, счётчик, время выполнения;
   ошибка — mono-блоком со stderr клиента и exit code.
6. **Тумблер «только чтение»** (по умолчанию включён) — серверный
   guard, не UI-эвристика: перед текстом запроса выполняется
   `SET default_transaction_read_only = on` (PG) /
   `SET SESSION TRANSACTION READ ONLY` (MySQL). Это закрывает и
   `WITH ... DELETE`, которые keyword-эвристика не ловит. Выключение —
   осознанное действие пользователя.
7. **Скачивание дампа** (must-have автора): `pg_dump | gzip` /
   `mysqldump | gzip` → стрим на скачивание (.sql.gz), механика по
   паттерну `transfer.ts`/`execStream`. Восстановление из дампа — v2.
8. **«Спросить агента»** рядом с редактором (must-have автора): агент
   генерирует SQL по текстовому запросу (контекст — схема: список таблиц
   и колонок), результат вставляется в редактор, **выполняет пользователь**.
   Никаких новых инструментов агента и утечки данных БД — только текст.
9. **Лимиты**: таймаут запроса, лимит вывода (как у `exec`), обрезка
   строк в гриде UI с пометкой «показаны первые N».

## Кандидатная архитектура (по паттернам проекта)

- `server/src/services/db-discovery.ts` — детект инстансов
  (docker ps + данные `container-ports.ts`, порты из `ports.ts`);
  чистые функции маппинга.
- `server/src/services/db-query.ts` — чистые билдеры команд и парсеры
  вывода, всё под unit-тесты:
  - PG: `docker exec -i <id> psql -U <user> -d <db> -X -v ON_ERROR_STOP=1
    --csv` + SQL в **stdin канала** (не в командной строке — нет лимита
    длины и проблем экранирования); вывод — CSV, парсится чистой
    функцией;
  - MySQL/MariaDB: `docker exec -i <id> mysql -u <user> <db> --batch
    --raw` + SQL в stdin; вывод — TSV с `\t`/`\n`/`\\`-escape внутри
    значений — парсер обязан разэкранировать;
  - списки баз/таблиц — теми же каналами (`psql -l`-эквивалент через
    `psql --csv -c` по information_schema, `SHOW DATABASES` /
    `SHOW TABLES` у mysql);
  - аргументы через `shq`, read-only флаг — доп-statement перед текстом.
- `server/src/routes/db.ts`: `GET /api/db/instances?profileId=`,
  `GET /api/db/overview?profileId=&instanceId=` (версия, базы с размерами,
  число таблиц),
  `GET /api/db/databases?profileId=&instanceId=`,
  `GET /api/db/tables?profileId=&instanceId=&database=`,
  `POST /api/db/query {profileId, instanceId, database, sql, readOnly}` →
  `{columns, rows, rowCount, durationMs, truncated}` либо
  `{error: {message, stderr, exitCode}}`,
  `GET /api/db/dump?profileId=&instanceId=&database=` → стрим .sql.gz.
- Фронтенд: вкладка таббара «Базы данных» (keep-alive, prop `visible`,
  без polling — всё по кнопке), левая колонка (инстансы → базы →
  таблицы), правая — редактор + грид. Грид простой (без виртуализации —
  лимит строк и так режет выдачу).

## Открытые вопросы к брейншторму

1. **Мутации**: достаточно ли тумблера «только чтение» (серверный
   флаг), или нужен ещё confirm-диалог на не-SELECT при выключенном
   тумблере? Лишний confirm на каждое UPDATE может мешать тому, кто
   пришёл именно писать.
2. **Native (не-docker) БД**: peer-auth у нативного postgres (нужен
   `sudo -u postgres`), пароли (PGPASSWORD/stdin). Включать в v1 или
   v1 = только контейнеры, native потом?
3. **Несколько statement'ов** за один запуск: разрешать (stdin это
   позволяет, PG с ON_ERROR_STOP=1 остановится на первом же) или
   жёстко «один запрос — один запуск»?
4. **История запросов**: localStorage на профиль (как тема) или не
   нужна в v1?
5. **Экспорт**: CSV из грида — клиентски, дёшево, наверное да;
   скачивание дампов (pg_dump/mysqldump → tar.gz) — v2?
6. **Инструмент агента** `db_query` (read-only SELECT): давать модели
   доступ к данным БД — отдельное решение по приватности; напрашивается,
   но это +1 read-only инструмент в класс автоматических.
7. **Позиция в таббаре**: после «Docker» («Обзор Терминал Файлы Docker
   Базы данных Порты Cron»)?
8. **Лимиты**: таймаут запроса — 60 с как у `exec` или больше для
   тяжёлых аналитических; максимум строк выдачи — 500? 1000?
9. **NoSQL (Redis/Mongo)**: нужен ли вообще просмотр ключей/коллекций,
   или честно говорим «терминал и туннели»? Если да — это отдельный
   мини-эпик, не часть SQL-консоли.
10. **Названия/детект**: считать ли инстансом контейнер с нестандартным
    образом, но портом 5432 (`postgres:`-совместимые типа timescale,
    postgis)? Список образов расширяемый?

### Ответы на открытые вопросы

1. **Мутации: тумблер без confirm** (ок?). Тумблера «только чтение»
   достаточно, confirm на не-SELECT не нужен — принцип уже заявлен
   («SQL пишет пользователь, как в терминале»), терминал тоже не
   переспрашивает. Тумблер — защита от случайности, не от намеренного
   действия. Уточнения:
   - состояние тумблера не персистить — каждая монтировка вкладки
     начинается с ON (выключение = осознанное действие в рамках сессии);
   - честно задокументировать границу: prepend
     `SET default_transaction_read_only = on` пользователь может снять
     первым же statement'ом (`SET ... = off; DROP ...`). Это не дыра,
     а граница применимости — защита от случайности. Запасной вариант
     жёстче — оборачивать SQL в `BEGIN READ ONLY; ... COMMIT;`
     (mid-transaction `SET default_transaction_read_only` не действует
     на текущую транзакцию — приятное свойство PG), но ломает
     пользовательские `BEGIN`/`COMMIT`. v1 — prepend.
2. **Native БД: v1 — только контейнеры** (ок?). Peer-auth нативного PG
   требует `sudo -u postgres` (отдельная история с sudo-паролем),
   PGPASSWORD — только через env в командной строке (видно в ps).
   Docker-centric инструмент закрывает контейнерами ~90% случаев.
   Слушатели 5432/3306 без контейнера — текстовая подсказка «похоже на
   нативную СУБД, в v1 не поддерживается», без интерактива.
3. **Несколько statement'ов: разрешать, дисплей честный.** stdin
   поддерживает естественно; PG с `ON_ERROR_STOP=1` останавливается на
   первой ошибке, mysql в batch-режиме абортится по умолчанию (без
   `--force`). Проблема — отображение: два SELECT'а дают два CSV-блока
   вперемешку с command tags (`INSERT 0 5`), надёжно разделить нельзя.
   Решение: грид показывает **первый** result set, рядом — сворачиваемый
   mono-блок «полный вывод» (сырой stdout). Основной сценарий (один
   SELECT) покрыт идеально, остальное не теряется.
4. **История запросов: да, в v1.** «Истории запросов нет» — одна из двух
   болей, ради которых фича делается. localStorage
   `sc-db-history-<profileId>`, последние 50, дедуп сверху, палитра по
   паттерну Ctrl+R из терминала. Серверная персистентность не нужна —
   инструмент одномашинный.
5. **Экспорт: CSV клиентски — опционально; скачивание дампов — в v1**
   (решение автора, см. ниже). CSV из грида — Blob + download.
   `pg_dump | gzip` через `execStream` → HTTP-стрим переиспользует
   механику `transfer.ts`. Восстановление из дампа — v2. У pg_dump
   нюанс версий клиент/сервер — в контейнере совпадают, ещё один
   аргумент за docker-only.
6. **Агент: в v1 — только генерация SQL в редактор** (решение автора,
   см. ниже). Агент пишет запрос текстом (контекст — схема), выполняет
   человек. Самостоятельный инструмент `db_query` для модели — фаза B:
   гарантия read-only должна быть технической (классификация statement'ов
   или READ ONLY-транзакция с отказом), иначе модель может «помогая»
   записать данные. Плюс приватность (данные БД уходят во внешний API) —
   явно opt-in, не тихое добавление в автоматический класс.
7. **Позиция в таббаре: после Docker.** «Обзор Терминал Файлы Docker
   Базы данных Порты Cron» — инстансы и есть контейнеры, Порты/Cron в
   конце.
8. **Лимиты: таймаут 120 с, 1000 строк.** Запрос к БД тяжелее
   shell-команды, 60 с мало для аналитики. Грид без виртуализации с
   1000×10 строками нормален, обрезка с пометкой «показаны первые N».
   Но таймаут канала убивает `docker exec`-клиент, а запрос на сервере
   БД продолжает жить — см. statement_timeout в находках.
9. **NoSQL: честно «терминал и туннели».** Redis-ключи — другой UX
   (дерево, не таблица); если понадобится — отдельный мини-эпик.
10. **Детект: список репозиториев как константа + чистый матчер.**
    `matchDbEngine(imageRef)` — чистая функция: разбор референса образа
    (отрезать registry), матч по расширяемому списку (`postgres`,
    `timescale*/timescaledb`, `postgis/postgis`, `mysql`, `mariadb`,
    `bitnami/*` …). Контейнер с портом 5432/3306, но неопознанным
    образом — в подсказки, не в инстансы.

### Находки из кода (в черновике не было)

- **~~Креденшалы не спрашивать — они уже в inspect.~~ ОПРОВЕРГНУТО
  практикой (причина отката итерации 1):** env контейнера часто не
  содержит актуальных креденшалов → Access denied. В итерации 2 пароль
  задаёт пользователь (см. план выше). Архивное описание:
  `container-ports.ts`
  тянет батч-`docker inspect`, `Config.Env` отдаёт `POSTGRES_USER` /
  `POSTGRES_DB` / `MYSQL_ROOT_PASSWORD` / `MYSQL_USER` /
  `MYSQL_DATABASE`. Для официальных образов — zero-credential
  подключение:
  - PG: локальный unix-сокет в официальном образе — `trust`, пароль не
    нужен; юзер из `POSTGRES_USER` (дефолт `postgres`);
  - MySQL: локально пароль нужен, но передаётся без раскрытия в argv ни
    на одном слое: `docker exec -i <c> sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD"
    exec mysql -u root ...'` — пароль разворачивается из env самого
    контейнера, в командной строке сервера его нет (сегодня он и так
    виден в `docker inspect` любому с docker-доступом — тот же trust
    domain). Двойное shq-экранирование (ssh → docker → sh -c) —
    обязательно под unit-тесты.

  Это убирает форму «введите пароль» из UI: выбрал контейнер — сразу
  работаешь.
- **Осиротевшие запросы.** Таймаут канала убивает наш `docker exec`, но
  запрос на сервере БД продолжает выполняться. Лечение — серверный
  таймаут: PG — `docker exec -e PGOPTIONS='-c statement_timeout=115s'`
  (env, не argv), MySQL — prepend
  `SET SESSION max_execution_time=...` (только SELECT, MySQL 5.7+;
  MariaDB — `max_statement_time`). Двухуровневый таймаут: 115 с внутри
  БД + 120 с канал как страховка.
- **Charset у MySQL.** Без `--default-character-set=utf8mb4` кириллица
  приезжает битой. Обязательно в билдер. PG в официальных образах
  UTF-8 по умолчанию.
- **NULL в mysql --batch.** NULL выводится строкой `NULL` — неотличим
  от значения `'NULL'`. Не чинится, фиксируем как известное ограничение.
- **Обрезанный CSV.** `SELECT *` без LIMIT на большой таблице упрётся в
  maxOutput 2 МБ посреди строки — парсер обязан выбросить неполную
  последнюю строку и выставить `truncated: true`. Обязательный кейс в
  тестах парсера.
- **Схемы PG.** Список таблиц — из `information_schema.tables` по всем
  схемам (не только search_path), системные схемы фильтровать,
  показывать `schema.table`.

### Мелочи, за которые голосуют

- Кнопка «EXPLAIN» рядом с выполнением — prefill-шаблон
  `EXPLAIN (ANALYZE, BUFFERS)` перед выделением/текстом.
- Скрывать системные БД: `information_schema, performance_schema, sys,
  template0, template1`.
- Лимит длины SQL в zod — 64 КБ.
- Ручной интеграционный сценарий по паттерну `multi-server.manual.mjs`:
  тестовый sshd + контейнеры `postgres:16-alpine` и `mysql:8`.

### Решения автора (2026-08-20, подтверждено)

1. **Мутации: тумблер «только чтение», по умолчанию ON** (№1).
   Confirm на не-SELECT не делаем — терминал тоже не переспрашивает.
2. **v1 строго docker-only**, native — v2 (№2). Подтверждено.
3. **Агент в v1 только ПИШЕТ запрос** (№6): кнопка «Спросить агента»
   рядом с редактором, сгенерированный SQL вставляется в редактор,
   выполняет пользователь. Инструмент `db_query` (модель сама читает
   данные) — фаза B с техническим read-only enforcement и явным
   opt-in по приватности.
4. **Дампы: в v1 — только скачивание** (№5, уточнено автором).
   `pg_dump | gzip` / `mysqldump | gzip` → стрим .sql.gz. Восстановление
   из дампа (деструктивно) — v2.
5. **Обзор инстанса — must-have v1** (новое от автора): версия движка,
   размеры баз, число таблиц.
6. История запросов (№4) — желательна в v1 (localStorage, последние 50),
   но не блокер: при ужатии scope выносится первой.
7. Остальные позиции брейншторма (позиция в таббаре после Docker,
   лимиты 120 с / 1000 строк, честный дисплей нескольких statement'ов,
   детект по расширяемому списку образов, находки про креденшалы из
   inspect / statement_timeout / charset / NULL / обрезанный CSV /
   схемы PG) — приняты как написано выше.

### Что НЕ входит в v1

- Нативные (не-docker) СУБД, NoSQL (Redis/Mongo).
- Восстановление из дампа.
- Инструмент агента `db_query` (модель сама выполняет запросы).
- Управление пользователями/привилегиями, ER-диаграммы, миграции,
  визуальное редактирование строк.
- CSV-экспорт грида — копеечный, по остаточному принципу.
