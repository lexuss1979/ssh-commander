# Опциональный доступ из LAN через HTTPS

По умолчанию приложение остаётся локальным: Compose публикует HTTP/WS и SSH-туннели только на `127.0.0.1`. LAN-режим — расширение доверенной зоны одного пользователя, не многопользовательский сервис. Не публикуйте его в интернете. SSH/БД-пароли и AI-ключ в data/ не зашифрованы; доступ к панели даёт возможность управлять всеми настроенными серверами.

## Конфигурация

| Переменная | Дефолт | Назначение |
|---|---|---|
| `APP_ACCESS_MODE` | `local` | `proxy` включает сетевую политику; неизвестное значение останавливает запуск |
| `APP_TRUSTED_ORIGINS` | пусто | В `proxy` обязателен список точных HTTPS Origin через запятую, например `https://commander.home.arpa,https://commander.home.arpa:8443`. Без путей, завершающего `/`, wildcard, userinfo |

Origin — схема, имя/IP и порт **страницы в браузере**, не адрес backend и не `wss://`. В proxy-режиме loopback Origin автоматически не добавляются. Origin проверяется на всех `/api` и при upgrade обоих `/ws/terminal`, `/ws/agent`; чужой и `null` Origin → 403. Для GET/HEAD без Origin браузерный Referer проверяется по тому же списку; отсутствие обоих заголовков → 403. Единственное исключение: GET `/api/health` без Origin от loopback TCP-peer. curl должен явно передать разрешённый Origin и cookie, защищённые API/WS по-прежнему требуют сессию. Origin не удостоверяет клиента: небраузерная программа может подделать его.

Сессионная cookie в proxy-режиме имеет `Secure`, `HttpOnly`, `SameSite=Lax`. TLS заканчивается на proxy; HTTP между proxy и backend допустим только на изолированном локальном канале. Приложение не определяет HTTPS по `X-Forwarded-Proto`, не доверяет `Forwarded`, `X-Forwarded-For` или `X-Forwarded-Host`; Express `trust proxy` выключен. Лимит логина поэтому общий для клиентов одного proxy; отдельный лимит по реальному TCP-IP можно добавить на proxy.

## Запуск из исходников

1. Завершите onboarding локально и задайте сильный уникальный пароль. Либо задайте `APP_PASSWORD` при **первом** старте с новым data/. После создания settings.json env-пароль игнорируется. Proxy-режим не запускается без сохранённого пароля: сетевого onboarding нет.
2. В `.env` добавьте:
   ```dotenv
   APP_ACCESS_MODE=proxy
   APP_TRUSTED_ORIGINS=https://commander.home.arpa
   ```
3. Выполните `docker compose up -d --build`. Backend и туннельные порты оставьте на loopback; `APP_HOST=0.0.0.0` внутри контейнера не означает публикацию наружу.
4. Установите nginx на **том же Docker-хосте**. Адаптируйте [пример](examples/lan-proxy.nginx.conf): локальный IP хоста, имя, сертификат и разрешённые клиентские IP/CIDR. Проверьте `nginx -t`, затем примените конфигурацию. Сертификат должен быть доверенным клиентскому браузеру (внутренний CA или подходящий сертификат). Настройте локальный DNS/hosts. UI открывайте только через HTTPS, WS будет использовать WSS.
5. Firewall разрешает 443 только выбранным IP/подсетям; запрещает внешние соединения к 8080 и туннельным портам. Проверьте правила Docker и маршрутизацию IPv6: публикация Docker может обходить обычные INPUT/UFW-правила. Не включайте port forwarding на роутере.

`docker-compose.release.yml` передаёт те же переменные, но закреплённый образ 0.1.3 ещё **не содержит** эту реализацию. До выпуска новой версии используйте сборку из изменённых исходников; после выпуска осознанно обновите тег.

Если proxy работает в отдельном контейнере, `127.0.0.1` относится к нему самому. Используйте отдельную приватную Docker-сеть с backend **без опубликованного HTTP-порта**, доступную только proxy и приложению. Не заменяйте маппинг на `0.0.0.0:8080`. При proxy на другой машине нужен защищённый канал (VPN/TLS) и firewall, допускающий backend только от proxy; приведённый пример этот вариант не покрывает.

IP-allowlist nginx действует для REST, статики и WS до upgrade. Она использует TCP-peer. Нельзя наследовать `real_ip_header`/широкий `set_real_ip_from`, иначе поддельный X-Forwarded-For может изменить адрес для allow/deny. Пример предполагает один прямой proxy, без балансировщиков перед ним. Не переписывайте Origin в доверенное значение — это отключает CSRF-защиту.

## Проверка перед использованием

- С разрешённого клиентского IP: HTTPS UI, вход, список профилей и WSS терминал/агент работают; без сессии защищённые запросы дают 401.
- С запрещённого IP: HTTPS `/`, `/api/health`, API и WS handshake дают 403 на nginx. Повторите с поддельными `Forwarded`/`X-Forwarded-*` — результат не меняется.
- С разрешённого IP и действующей сессией, но чужим/отсутствующим Origin: API и оба WS handshake дают 403 backend. Другой порт и HTTP Origin также запрещены.
- С любой LAN-машины прямой 8080 и диапазон SSH-туннелей недоступны; проверьте IPv4 и IPv6.

Автотест `server/test/network-access.test.ts` поднимает настоящий entry point и проверяет REST/оба WS, сессию, cookie и поддельные proxy-заголовки. Проверка nginx CIDR/TLS/firewall требует реального окружения: серверный тест её не заменяет. В локальном режиме отсутствие Origin сохраняет прежнюю семантику; некорректные URL, схемы кроме HTTP(S) и `0.0.0.0` больше не считаются доверенными источниками.

Браузерная политика `no-referrer` блокирует GET без Origin в proxy-режиме; используйте стандартную same-origin Referrer-Policy. Ссылки на SSH-туннели в UI всё ещё указывают на localhost браузера: LAN-режим не переносит туннели на клиентскую машину.
