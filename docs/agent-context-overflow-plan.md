# План эпика: управление контекстом диалога (защита от превышения лимита токенов)

> **Статус: реализовано, 2026-10-12.** Проблема из эксплуатации: длинный диалог упёрся
> в лимит контекста модели — провайдер ответил HTTP 400
> «maximum context length is 1048576 tokens. However, you requested
> 1048783 tokens», и диалог стал необратимо нерабочим: каждый следующий
> запрос несёт ту же раздутую историю. До реализации у приложения не было
> учёта размера контекста. Ключевая идея: бюджет контекста — обязанность
> сервера: оценка токенов, проактивное сжатие истории для запроса и
> реактивное восстановление по ошибке провайдера.

## Симптом

```
⚠️ AI API error 400: {"error":{"message":"This model's maximum context
length is 1048576 tokens. However, you requested 1048783 tokens
(1048783 in the messages, 0 in the completion)..."}}
```

После этого диалог «мёртв»: любое новое сообщение падает так же. Помогает
только новый диалог — история теряется.

## Состояние до реализации (кратко)

- История диалога растёт **неограниченно**: `saveDialogueMessages`
  (`server/src/ai/dialogues.ts:262`) персистит всё, сессия при attach
  поднимает всё обратно (`agent.ts:167-171`). Никаких лимитов на число
  сообщений, байты или токены нет.
- Каждый API-запрос тащит **полную историю**: `runLoop` (`agent.ts:620-627`)
  и `runPlan` (`agent.ts:550-557`) отдают `sanitizeMessages(this.messages)`
  целиком. `buildResponsesBody` (`responses.ts:28`) — то же для Responses
  API («The history stays local: every request carries the full context»).
- Единственный существующий тормоз роста — обрезка одного вывода инструмента
  до `MAX_TOOL_OUTPUT = 12000` символов (`agent.ts:72`, `truncate()`),
  причём в контекст уходит уже обрезанный текст. Но 30 шагов × до ~12 КБ
  на вызов × неограниченное число ходов — сумма не ограничена.
- Постоянная надбавка на каждый запрос: системный промпт + блок памяти
  (до 64 КБ, `memory.ts`) + определения инструментов (`tools.ts` ~22 КБ
  текста ≈ 6–8 тыс. токенов).
- Токены считаются только для биллинга (`usage` в `client.ts`), размер
  **входящего** запроса нигде не оценивается.
- Ошибка 400 всплывает из `client.ts:280-283` как есть и убивает ход
  (`agent.ts:634-641`) — без попытки восстановления.

## Цели и не-цели

**Цели:**

- Старая история не блокирует продолжение диалога: запрос влезает в
  оценочный бюджет, история сжимается/выталкивается предсказуемо. Если
  обязательные инструкции, инструменты и текущий ход не помещаются,
  возвращается понятная локальная ошибка без запроса к провайдеру.
- Ошибка провайдера о превышении лимита обрабатывается автоматически:
  сжать сильнее и повторить, а не убивать ход.
- UI и персист не ломаются: пользователь видит полную историю диалога,
  сжатие касается только того, что уходит в API.

**Не делаем (осознанно):**

- **Не суммаризуем историю вызовом LLM** (отдельный платный запрос на
  сжатие): v1 обходится детерминированным сжатием. Суммаризация —
  возможный следующий эпик.
- **Не переписываем персистнутую историю** при сжатии: `ai-dialogues.json`
  и экран диалога остаются полными. Сжатие — только «вид для запроса».
- Не делаем точный токенизатор (нет зависимости от tiktoken и т.п.) —
  достаточно консервативной оценки с запасом.

## Принятые решения

1. **Оценка токенов — эвристика, новый модуль `server/src/ai/context.ts`.**
   Чистая функция `estimateTokens(messages, tools)`: символьная оценка
   `ceil(UTF8(JSON(message)) / 3)` (с запасом для ru/en-смеси) +
   фиксированная надбавка на сообщение (role, tool_calls-обвязка,
   `tool_call_id` ≈ 10 токенов) + размер сериализованных tool-определений.
   Учитываются аргументы tool_calls и непрозрачные `responsesContext`.
   Это эвристика, а не гарантированная верхняя граница токенизации;
   расхождения с провайдером обрабатывает реактивный путь.
2. **Бюджет — настраиваемый, с безопасным дефолтом.** Новый env
   `AI_CONTEXT_LIMIT` (дефолт `120000` токенов; подбирается под модель).
   Из бюджета вычитается резерв на completion:
   `min(COMPLETION_RESERVE = 16000, floor(limit / 4))`. Адаптивный резерв
   оставляет положительный входной бюджет и при малых лимитах.
   Результаты инструментов учитываются при подготовке следующего шага.
   Переменная передаётся в production/dev/release Compose.
3. **Проактивное сжатие — «вид для запроса», ярусами.** Перед каждым
   вызовом API (и в `runLoop`, и в `runPlan`) сообщения прогоняются через
   `fitToContext(messages, tools)` из `context.ts`. Ярусы, по нарастанию
   агрессивности, пока оценка не влезет в бюджет:
   - **Ярус 1 — усадка старых выводов инструментов:** у tool-сообщений
     старше последних K обменов (K = 10) контент обрезается до 500 символов
     с пометкой `[…усечено для экономии контекста]`. Свежие выводы не
     трогаем — модель опирается на них.
   - **Ярус 2 — вытеснение старых обменов:** удаляем самые старые связки
     «user → assistant(+tool_calls) → tool…» целиком (sanitize-совместимо:
     вырезается всегда полный обмен, висячих `tool_calls` не образуется).
     Системный промпт (индекс 0) неприкосновенен; первое user-сообщение
     диалога по возможности сохраняется (задаёт контекст задачи).
   - **Ярус 3 — аварийный:** если даже один свежий хвост не влезает (гигантское
     system+memory), усекается блок памяти в системном промпте по точным
     границам, записанным при сборке промпта, затем — честная ошибка
     с указанием причины. Текущий пользовательский ход, аргументы и
     свежие tool-результаты не обрезаются. Инструкции плана сохраняются.
   Инвариант: результат `fitToContext` — валидная последовательность
   (прогон через `sanitizeMessages` на выходе как страховка).
4. **Реактивное восстановление по 400.** В `client.ts` распознаём ошибку
   переполнения (тело ответа матчится по `maximum context length` /
   `context_length_exceeded` / `context window` / `too many tokens`) —
   бросается типизированный `ContextOverflowError`. `agent.ts` ловит его,
   **удерживает входной бюджет сессии** (половина оценки отклонённого
   запроса, не ниже 1024; оценка уже не превышает бюджет сессии) и
   повторяет тот же шаг с пересжатым видом. Одна попытка на шаг; повторный
   400 — обычная ошибка в UI. Если сокращение невозможно, повтор не
   выполняется. Успех на произвольной модели не гарантируется: локальная
   оценка приблизительна. SSE-ошибки не повторяются, чтобы не дублировать
   уже показанный ответ. После переподключения бюджет берётся из env заново.
5. **Персист не меняется.** В `ai-dialogues.json` пишется полная история
   (как сейчас). Сжатый вид строится заново на каждый запрос — дешёвая
   чистая функция, без состояния, кроме `sessionBudget` из решения 4.
   Побочный плюс: обрезка для запроса не трогает `responsesContext`
   (зашифрованный reasoning-контекст Go-моделей живёт в assistant-сообщениях
   и вытесняется вместе с ними целиком — иначе невалидный ввод для
   Responses API).
6. **Прозрачность для пользователя.** При срабатывании яруса 2 (или
   реактивного сжатия) в UI уходит служебная WS-заметка (`notice`-событие,
   строки словаря ru+en: «часть ранней истории исключена из контекста
   запроса») — иначе модель «забывает» начало диалога молча, и это выглядит
   как регрессия. Новые ключи в `strings.ts` (существующие ru-значения не
   трогаем — заморожены тестами).

## Шаги реализации

1. `server/src/ai/context.ts` (новый): `estimateTokens()`,
   `fitToContext(messages, tools, budget)`, распознавание обменов для
   яруса 2. Чистые функции, без импорта сервисов.
2. `server/src/config.ts`: `ai.contextLimit` из `AI_CONTEXT_LIMIT`
   (дефолт 120000). `.env.example` + таблица env в `AGENTS.md` и
   `docs/architecture.md`.
3. `server/src/ai/client.ts`: распознавание 400-переполнения →
   `ContextOverflowError` (до generic-ветки `client.ts:280-283`).
4. `server/src/ai/agent.ts`: перед каждым `streamChatCompletion` —
   `fitToContext(this.messages, …, this.sessionBudget)`; catch
   `ContextOverflowError` → уменьшение входного бюджета + один повтор шага
   (без инкремента `steps` поверх уже посчитанного); WS-заметки о сжатии.
   `sessionBudget` инициализируется из `config.ai.contextLimit` за вычетом
   адаптивного резерва. Общий метод `requestCompletion` обслуживает оба режима.
5. `server/src/ai/plan.ts`: `buildPlanRequestMessages` применяется **до**
   `fitToContext`, чтобы инструкции плана тоже учитывались в бюджете.
6. `server/src/ai/strings.ts`: ключи заметок о сжатии (ru+en).
7. Фронтенд: рендер `notice`-события в ленте диалога (слабый серый стиль,
   как у служебных заметок). Строки — в `web/src/i18n/ru.ts`+`en.ts`
   (паритет гарантируют типы и `server/test/i18n.test.ts`).
8. Тесты:
   - `server/test/context.test.ts` (новый): оценка монотонна и консервативна;
     ярус 1 усекает только старые tool-выводы; ярус 2 вырезает обмены
     целиком (нет висячих tool_calls — проверка через `sanitizeMessages`);
     системный промпт и первый user сохраняются; аварийный ярус.
   - `server/test/client.test.ts`: тело 400 с «maximum context length» →
     `ContextOverflowError`; прочие 400 — прежняя generic-ошибка.
   - Агентский тест: диалог-«бочка» (синтетически раздутая история) не
     порождает запрос больше бюджета; реактивный 400 → повтор шага с
     уполовиненным бюджетом.

## Проверка

- `cd server && npm run build && npm test` — зелёные, `npm audit` чист.
- Ручной сценарий: искусственно занизить `AI_CONTEXT_LIMIT` (например,
  40000; 4000 может не вместить даже инструкции и tools) и вести диалог
  с инструментами: после нескольких ходов в ленте
  появляется заметка о сжатии, агент продолжает работать. В автоматических
  тестах раздутая история, HTTP overflow и stop проверяются через настоящий
  AgentSession и HTTP-клиент с моковым провайдером; платный живой API для
  этих проверок не нужен.
- Регрессия: существующие сценарии (`agent.manual.mjs`, мульти-серверный
  мануал) проходят без изменений поведения на коротких диалогах (сжатие
  не срабатывает, заметок нет).
