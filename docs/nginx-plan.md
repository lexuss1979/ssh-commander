# План эпика: вкладка «Nginx» — сайты сервера

> **Статус: план эпика.** Выращен из черновика требований (та же история
> правок файла); открытые вопросы черновика закрыты в разделе
> «Принятые решения». Форма — паттерн «Cron»/«Порты»/«Базы данных»:
> discover по SSH → парсинг чистыми функциями → вкладка с polling →
> точечные мутации за confirm'ом.

## Зачем

Сервер с сайтами на nginx — самый частый сценарий этого инструмента, но
сейчас чтобы ответить на вопрос «какие сайты держит сервер и всё ли у них
в порядке», нужно идти в терминал и читать конфиги руками. Вкладка даёт
ответ одним взглядом: список server-блоков, что они слушают, куда
проксируют, живы ли сертификаты, цел ли конфиг.

## Цели и не-цели v1

**Не делаем (осознанно):**

- Редактор конфигов — карточка сайта ссылается на файл, FilesPage уже
  умеет редактировать.
- Просмотр логов (tail access/error) — v2, UX отдельный.
- Метрики (stub_status, connections) — v2+.
- Создание/удаление сайтов — это конструктор конфигов, другой продукт.
- Enable/disable сайтов (symlink в sites-enabled) — кандидат в v2.
- Apache/Caddy/Traefik — если nginx не найден, показываем честное пустое
  состояние, не угадываем.
- Sudo для reload — v1 выполняет reload от SSH-пользователя как есть,
  ошибка прав показывается честно (см. «Принятые решения», п. 4).
- Инструмент агента (`nginx_sites` read-only) — отдельное решение по
  приватности (данные уходят во внешний API), как было с `db_query`;
  не в v1.

## Принятые решения (закрывают открытые вопросы черновика)

1. **Источник данных — только `nginx -T`.** Раскрытые `include`,
   маркеры `# configuration file <путь>` приписывают каждый блок его
   файлу. Отключённые сайты (в `sites-available` без симлинка) в `-T`
   не попадают — v1 показывает только активные, это честно. Fallback на
   пофайловое чтение `sites-enabled/*` при permission denied **не
   делаем**: частичный конфиг без раскрытия include вводит в заблуждение
   сильнее, чем явная ошибка. Ошибка чтения — mono-блоком в шапке.
2. **Discovery: native первым, контейнер — best-effort.** Порядок:
   `command -v nginx` → fallback `/usr/sbin/nginx -v` → docker. Матчинг
   контейнера: репозиторий образа в белом списке (`nginx`,
   `nginxproxy/nginx-proxy`, `jc21/nginx-proxy-manager`, `openresty/openresty`
   — через `imageRepository` из `db-discovery.ts`, переиспользуем)
   **плюс** подстрока `nginx` в имени образа или контейнера (ловит
   self-built `web-nginx` и т.п.). Известный промах: контейнер с nginx
   под совсем чужим именем/образом не найдётся — принимаем, это
   задокументировано в пустом состоянии («nginx в контейнере с
   нестандартным образом не обнаруживается»).
3. **Оба источника сразу — один снапшот с массивом `sources[]`.**
   UI рисует секции с заголовком источника («nginx (хост)», «контейнер
   nginx-proxy»); переключатель не делаем — секции проще и покрывают
   редкий случай без лишнего состояния.
4. **Reload и права.** `nginx -t` и `nginx -T` — plain exec (конфиги
   обычно world-readable). Reload — plain `nginx -s reload`
   (native) / `docker exec <id> nginx -s reload` (контейнер); системно
   `systemctl reload` не используем — единая механика сигнала мастеру
   проще и работает одинаково везде. Непривилегированный пользователь
   получит Permission denied — показываем stderr как есть, без sudo-обёрток
   и без скрытых эвристик. Sudo-пароль в confirm-модалке (механика
   `exec` с `stdin` для `sudo -S` уже есть в `ssh/manager.ts`) —
   отдельная итерация v2, в v1 не блокирует: типовые сценарии инструмента
   (root или sudo-capable деплой-пользователь) работают.
5. **Сертификаты: файл + локальный парсинг, без удалённого `openssl`.**
   PEM вычитывается байтами (`cat` native / `docker exec <id> cat`
   контейнер, одной батч-командой на все уникальные пути с маркерами
   `=== <путь>` — паттерн `/etc/cron.d`), парсится локально через
   `crypto.X509Certificate` (Node 20, `validTo`). Удалённый `openssl`
   не требуется — в alpine/distroless-образах его может не быть, а срок
   сертификата — центральная ценность вкладки, она не должна зависеть от
   состава образа. `s_client`-проверка **не делаем**: без правильного
   SNI (`-servername`) она показывает дефолтный сертификат и врёт для
   мультисайтовых серверов; файл — источник истины конфига, его и
   проверяем. Файл недоступен → колонка «недоступен», не ошибка вкладки.
6. **Группировка: http/https-пара одного сайта = две строки.** Проще,
   честнее; `listen` у сайта — массив (IPv4 + IPv6, несколько портов).
7. **`proxy_pass` берётся из `location /`**, иначе из первого location
   с `proxy_pass`; в строке дополнительно показываем число location'ов.
   `ssl_certificate`, заданный на http-уровне (общий сертификат),
   парсится как дефолт и применяется к server-блокам без своего — иначе
   центральная колонка пуста у половины реальных конфигов. Остальная
   наследуемость (root на http-уровне и т.п.) — не отслеживаем.
8. **Парсер v1 — только верхнеуровневые server-блоки.** `upstream`,
   `map`, `geo`, `if`, `stream {}` — игнорируются молча (парсер
   консервативен: непонятное поле — `null`/пропуск, не ошибка). Тесты
   обязаны доказать, что парсер не падает на конфиге с этими блоками.
9. **Название вкладки — «Nginx»** (по аналогии с «Docker»), позиция в
   таббаре — между «Базы данных» и «Порты».
10. **Polling 5 с** как у соседних вкладок (только при видимой вкладке),
    серверный кэш снапшота 2 с на профиль. Сертификаты — отдельный кэш
    10 мин на профиль: срок годности не меняется за секунды, не гоняем
    `cat` каждый тик. Инвалидация по изменению набора путей сертификатов
    в снапшоте (новый сайт → дочитываем сразу).

## Архитектура сервера

### `server/src/services/nginx-parser.ts` — чистые функции

- `parseNginxDump(text: string): ParsedNginxConfig` — разбор вывода
  `nginx -T`:
  - раскадровка по маркерам `# configuration file <путь>:` — каждый
    server-блок получает `file`;
  - brace-matching блоков (учёт `}` в строках/кавычках не требуется:
    считаем скобки лексически, комментарии `#` до конца строки срезаем);
  - верхнеуровневые `server {}` внутри `http {}`; http-уровень —
    только для дефолта `ssl_certificate`;
  - из server-блока: `server_name` (все имена, wildcard как есть),
    все `listen` (адрес/порт/`ssl`/`default_server`/IPv6 `[::]:443`),
    `root`, `ssl_certificate`, location-блоки (только верхний уровень
    вложенности) с `proxy_pass`;
  - `map`/`upstream`/`geo`/`if`/`stream` — пропуск.
- `toSiteEntry(block, httpDefaults): NginxSite` — маппинг в строку
  таблицы: `target: {kind: 'proxy'|'static'|'unknown', value}` (см.
  решение 7), `locationsCount`, `isDefault`.
- `certInfoFromPem(pem: string): {notAfter: Date; daysLeft: number}` —
  локальный парсинг через `crypto.X509Certificate`; битый PEM → `null`.
- `parseCertBatch(output: string): Map<path, pem>` — раскадровка
  батч-вывода по маркерам `=== <путь>`.

Всё чистое, без I/O — под unit-тесты (паттерн `cron.ts`/`ports.ts`).

### `server/src/services/nginx.ts` — I/O и кэши

- Билдеры команд (чистые, под тесты):
  - `buildDumpCmd(source)` — `<bin> -T` / `docker exec <id> nginx -T`;
    для контейнера через `dockerExec(profile, ['exec', id, 'nginx', '-T'])`
    (экранирование `dockerCommand` + `shq` уже внутри `docker.ts`);
  - `buildTestCmd(source)`, `buildReloadCmd(source)`;
  - `buildCertBatchCmd(source, paths)` — `for f in ...; do echo "=== $f";
    cat -- "$f"; done` с `shq` на каждый путь.
- `discoverNginx(profile): Promise<NginxSourceRef[]>` — решение 2;
  детект нативного бинаря кэшируется на профиль (как compose-детект в
  `docker.ts`), контейнерный список живёт в общем кэше снапшота (2 с) —
  состав контейнеров может меняться.
- `getNginxSnapshot(profile): Promise<NginxSnapshot>` — оркестрация:
  discovery → параллельно по источникам `nginx -T` + `nginx -t`
  (`Promise.allSettled`, упавший источник → секция с ошибкой, снапшот
  не падает) → парсинг → сбор уникальных путей сертификатов → батч-чтение
  (через отдельный кэш 10 мин, решение 10) → сборка `NginxSite[]`.
  Версия nginx — из `nginx -v` (пишет в stderr!) один раз на снапшот
  источника. Кэш 2 с на профиль — паттерн `discoverDbContainers`
  (Map с `{at, promise}`, удаление записи при reject).
- `nginx -T` вызывается с `maxOutput: 8 МБ` (дефолт exec — 2 МБ; реальный
  дамп с сотнями сайтов может превысить). Превышение → понятная ошибка
  «конфиг слишком большой», не молчание.
- `nginx -t` и `nginx -v` пишут в **stderr** — вывод читаем оттуда
  (`ExecResult` отдаёт оба потока). Для `-t` показываем `stderr + stdout`.
- `testAndReload(profile, source)` — guard reload'а на сервере: сначала
  `nginx -t`; при неуспехе reload **не выполняется**, ответ 409 с выводом
  теста. Guard технический, не обещание UI.

### `server/src/routes/nginx.ts`

- `GET /api/nginx?profileId=` →
  `{ timestamp, sources: NginxSourceSnapshot[] }`, где
  `NginxSourceSnapshot = { type: 'native'|'container', containerId?,
  containerName?, version: string|null, configTest: {ok, output},
  sites: NginxSite[] }`, `NginxSite = { file, serverNames: string[],
  isDefault, listens: [{addr, port, ssl}], target: {kind, value},
  locationsCount, cert: {path, notAfter, daysLeft} | {path, error} | null }`.
  nginx не найден нигде → `{ timestamp, sources: [] }` (200, пустое
  состояние — решение UI, не 404).
- `POST /api/nginx/test {profileId, source}` → `{ok, output}`;
  `source`: `'native'` или `container:<id>` (валидируется против
  актуального discovery — нельзя адресовать произвольный контейнер).
- `POST /api/nginx/reload {profileId, source}` → `{ok, output}`; 409 с
  выводом `nginx -t`, если тест красный.
- Регистрация в `index.ts`: `app.use('/api/nginx', requireAuth, nginxRouter)`.

### Типы

`NginxSite`, `NginxSourceSnapshot` и т.д. — в `server/src/types.ts` рядом
с остальными контрактами API (как делают cron/ports).

## Web

- `web/src/api.ts` — интерфейсы (зеркало серверных типов, с JSDoc-комментами
  как у `CronSnapshot`) и функции `fetchNginx(profileId)`,
  `testNginx(profileId, source)`, `reloadNginx(profileId, source)` через
  общий хелпер `api<T>`.
- `web/src/pages/NginxPage.tsx` — паттерн CronPage:
  - prop `visible`, polling 5 с только при видимой вкладке и видимой
    странице браузера;
  - шапка на источник: имя, версия, бейдж `nginx -t` (зелёный «конфиг
    цел» / красный с текстом ошибки), кнопки «Проверить конфиг» и
    «Перезагрузить» (reload — confirm-модалка; при 409 показывает вывод
    `nginx -t` в mono-блоке);
  - таблица сайтов: server_name (с бейджем `default_server`), listen
    (адрес:порт + SSL-отметка), «куда смотрит» (proxy → upstream,
    static → root; `+N location` если их несколько), сертификат
    (`осталось N дн.`; ≤ 14 дней — жёлтое, просрочен — красное;
    `недоступен` — серое), файл конфига;
  - пустые состояния: «Nginx не обнаружен» (с оговоркой про нестандартные
    образы, решение 2), ошибка чтения конфига — mono-блок в шапке секции;
  - keep-alive: страница монтируется в `App.tsx` как остальные вкладки
    (`display:none`, не размонтируется).
- `web/src/App.tsx` — `Tab` + `TABS`: `'nginx'` с label «Nginx» между
  «Базы данных» и «Порты»; рендер-слот как у соседних страниц.
- Стили — существующие классы таблиц/бейджей (`styles.css`), новые —
  только если соседние вкладки не покрывают (бейдж default_server,
  подсветка срока сертификата — кандидаты на общие `.badge-*`).

## Тесты

- `server/test/nginx.test.ts` (vitest):
  - парсер дампа: реалистичный `nginx -T` в стиле Debian (nginx.conf +
    `sites-enabled/*` через маркеры файлов), `conf.d`, proxy и static
    сайты, несколько `listen` (IPv4+IPv6, `443 ssl`, `default_server`),
    wildcard `server_name`, `proxy_pass` в `location /` и несколько
    location'ов, `ssl_certificate` на http-уровне (дефолт применяется),
    конфиг с `upstream`/`map`/`if`/`stream` — парсится без ошибок,
    блоки игнорируются;
  - `certInfoFromPem`: валидный PEM (фикстура — самоподписанный
    сертификат, сгенерированный заранее и лежащий в тесте строкой),
    битый PEM → `null`;
  - `parseCertBatch`: маркеры, несколько файлов, отсутствующий файл
    (cat пишет ошибку в stderr — в stdout секции нет);
  - билдеры команд: native/контейнер, `shq` на путях с пробелами;
  - дедуп путей сертификатов перед батчем;
  - guard reload: `testAndReload` не вызывает reload при красном тесте
    (мок exec).
- `server/test/nginx.manual.mjs` — ручной интеграционный сценарий:
  тестовый sshd (linuxserver/openssh-server, как в
  `integration.manual.mjs`) + nginx в контейнере на том же хосте
  (официальный образ с смонтированным конфигом и самоподписанным
  сертификатом): discovery находит контейнер, снапшот содержит сайт,
  срок сертификата посчитан, `test` и `reload` работают.

## План реализации (итерации)

1. **Парсер + билдеры + unit-тесты** (`nginx-parser.ts`, чистые билдеры
   из `nginx.ts`) — без роутов, зелёный `npm test`.
2. **Discovery + снапшот + `GET /api/nginx`** (без сертификатов), кэши.
3. **Сертификаты**: батч-чтение + локальный парсинг + кэш 10 мин,
   интеграция в снапшот.
4. **NginxPage + api.ts + таббар** — таблица, шапки, пустые состояния.
5. **test/reload**: эндпоинты + guard + кнопки с confirm и выводом 409.
6. **Финал**: ручной сценарий, `npm run build` в обоих каталогах,
   `npm test`, `npm audit`; обновить `AGENTS.md` (структура, REST-список,
   раздел тестирования) и отметить эпик в `docs/roadmap.md`.

Каждая итерация — самостоятельно зелёная (build + test); UI после
итерации 4 уже полезен без кнопок.

## Оценка

Парсер + тесты ~1 день, discovery + снапшот ~0.5, сертификаты ~0.5,
вкладка ~0.5–1, test/reload с guard'ом ~0.5. Итого v1 ~3 дня.
Логи / enable-disable / sudo для reload / инструмент агента — отдельные
итерации v2, каждая со своим планом.

## Риски

- **Разнообразие реальных конфигов** — главный риск. Снимается
  консервативным парсером (непонятное → `null`) и тестами на реальных
  дампах; худший случай — пустые колонки у части сайтов, не падение.
- **Контейнерный discovery с нестандартным образом** — известный промах,
  задокументирован в пустом состоянии (решение 2).
- **Reload у непривилегированного пользователя** — честная ошибка в v1,
  sudo-итерация в v2 (решение 4).
- **Гигантский конфиг** — `maxOutput` 8 МБ + явная ошибка при превышении.
