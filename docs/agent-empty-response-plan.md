# План эпика: устойчивость агента к пустым ответам AI API

> **Статус: реализовано (2026-10-12).** Проблема из эксплуатации: пользователь регулярно
> получает «⚠️ AI API завершил ответ без текста и вызовов инструментов.
> Повторите запрос.» — цикл агента обрывается, хотя в большинстве случаев
> это транзиентная особенность провайдера, и простой повтор запроса
> решает проблему. Ключевая идея: пустой ответ — это **восстановимая
> ситуация**, которую сервер обязан пережить сам (авто-ретрай с классификацией
> причины), а не перекладывать на пользователя.

## Симптом

В панели агента вместо ответа — ошибка:

```
⚠️ AI API завершил ответ без текста и вызовов инструментов. Повторите запрос.
```

Цикл завершается (`done` не приходит, приходит `error`), сообщение
пользователя уже сохранено в диалоге. Повторная отправка вручную обычно
проходит — то есть сбой транзиентный.

## Исходное состояние (до реализации)

- `server/src/ai/client.ts:136` — `assertNonemptyMessage()` бросает
  `apiEmptyResponse`, если у ответа нет ни `content`, ни `tool_calls`.
  Вызывается из трёх мест: `normalizeMessage` (нестриминговый JSON-ответ,
  `client.ts:148`), `normalizeResponse` (Responses API, `client.ts:158`) и
  финал SSE-стрима (`client.ts:407`).
- Стриминговый парсер **не читает `finish_reason`** (`client.ts:341-367`):
  из чанка берётся только `delta.content` и `delta.tool_calls`. Поэтому
  пустой ответ из-за `content_filter`, `length` и «провайдер просто отдал
  пустышку» сейчас неотличимы.
- `delta.reasoning_content` (reasoning-модели DeepSeek и совместимые) тоже
  игнорируется: модель могла «отмыслить» ход, но видимый `content` пуст —
  для нас это пустой ответ.
- Ретрай есть **только для транспортных сбоев** fetch (DNS/TCP/TLS, один
  повтор через 2 с, `client.ts:256-278`). HTTP-ошибки и пустые ответы не
  ретраятся.
- Ошибка всплывает в `runLoop` (`agent.ts:634-641`) и `runPlan`
  (`agent.ts:566-573`) → WS `error` → конец хода. Никакого второго шанса.
- Тесты: `server/test/client.test.ts` уже проверяет `apiEmptyResponse`
  (ru-строки заморожены — на них завязаны тесты, менять существующие
  значения нельзя, добавлять новые ключи можно).

## Вероятные причины

1. **Транзиент провайдера** — под нагрузкой API (наблюдалось у DeepSeek)
   честно завершает стрим (`[DONE]`), но с пустым выбором. Это основной
   случай «сегодня часто».
2. **`finish_reason: 'content_filter'`** — провайдер вырезал ответ
   модерацией; ретрай тем же контекстом иногда помогает, иногда нет.
3. **`finish_reason: 'length'` с нулём видимого текста** — весь бюджет
   completion ушёл в скрытый reasoning.
4. **Reasoning-only ответ** — весь вывод ушёл в `reasoning_content`,
   которое мы не читаем.

## Цели и не-цели

**Цели:**

- Пустой ответ переживается автоматически: прозрачный ретрай без участия
  пользователя в подавляющем большинстве случаев.
- Причины различимы: в логе сервера и (при финальном отказе) в тексте
  ошибки — `content_filter` и `length` не должны маскироваться под
  «пустой ответ».
- Ретрай не ломает инварианты: лимит шагов `AI_MAX_STEPS`, журнал расходов,
  stop-кнопка.

**Не делаем (осознанно):**

- Не «чиним» пустой ответ подстановкой заглушки в историю («модель
  промолчала») как regular-ход: это загрязняет контекст и путает модель.
- Не зацикливаем ретрай: максимум 2 повтора, дальше — прежняя ошибка.
- Не показываем reasoning-текст модели в UI (отдельная тема, не цель эпика).

## Принятые решения

1. **Классификация пустого ответа в клиенте.** Стриминговый парсер
   запоминает последний `finish_reason` (и `reasoning_content`-трафик —
   факт наличия, не текст). Пустой финал бросает не generic-ошибку, а
   типизированную: `EmptyResponseError { finishReason, hadReasoning }`.
   Для Responses API — аналогично по `response.incomplete_details` /
   пустому `output`.
   JSON-ответ Chat Completions без `choices` или сообщения также считается
   пустым и повторяется по общим правилам: вместо прежнего `AI API returned no message`
   после исчерпания попыток возвращается локализованный `apiEmptyResponse`.
   `normalizeMessage` удаляет `reasoning_content` и из успешных JSON-сообщений:
   этот текст не попадает в persisted-историю и контекст следующих запросов.
2. **Авто-ретрай на уровне `streamChatCompletion`-вызова** (обёртка в
   `client.ts`, чтобы покрыть и `runLoop`, и `runPlan`, и план-режим):
   пустой ответ → повтор того же запроса, до 2 раз, паузы 2 с и 5 с,
   уважая `opts.signal` (stop/abort отменяет и паузу — механика как у
   существующего `delay()`). Каждый повтор логируется в консоль сервера
   с `finishReason` и sessionId. Шаг цикла (`steps`) ретрай **не расходует**:
   вызов ещё не дал результата, это тот же шаг.
3. **Исключения из ретрая:** `finish_reason: 'content_filter'` при повторе
   подряд (первый раз ретраим — фильтры флапают, второй подряд — бессмысленно
   жечь токены тем же контекстом); отказ после исчерпания ретраев. Финальная
   ошибка различает случаи новыми строками словаря (`apiEmptyResponse`
   остаётся как fallback и не меняется — тесты):
   - `content_filter` — «ответ отрезан фильтром контента провайдера»;
   - `length` — «ответ не уместился в лимит completion».
4. **Биллинг:** каждый вызов, вернувший `usage`, пишется в журнал как и
   сейчас (пустые ответы с usage — тоже платные, скрывать расход нельзя).
   Уточнение по результатам ревью: одной суммы в успешном возврате недостаточно —
   она теряется при окончательной ошибке или stop. Поэтому `onUsage(usage, model)`
   сообщает агенту о каждой завершённой попытке сразу; `requestCompletion`
   записывает отдельную строку журнала для каждой попытки. Результат по-прежнему
   содержит суммарный usage, но агент повторно его не записывает. Снимок модели
   и настроек фиксируется до первой попытки. Прерванный поток не учитывается.
5. **Без изменения протокола WS:** фронтенд ничего не узнаёт о ретраях
   (стрим просто придёт позже). Никаких новых событий.

## Шаги реализации

1. `server/src/ai/client.ts`:
   - В SSE-парсере сохранять `finish_reason` последнего чанка с `choices`
     и флаг «был `reasoning_content`».
   - Завести `class EmptyResponseError extends Error` с полями
     `finishReason?: string`, `hadReasoning: boolean`; бросать его вместо
     голого `Error(apiEmptyResponse)` во всех трёх точках (`normalizeMessage`,
     `normalizeResponse`, финал стрима).
   - Обёртка `withEmptyRetry()` вокруг ядра: ловит `EmptyResponseError`,
     ретраит по правилам решения 2–3, мержит usage. Существующий
     транспортный ретрай остаётся внутри, независимо.
2. `server/src/ai/strings.ts`: новые ключи `apiContentFiltered`,
   `apiLengthTruncated` (ru+en, паритет проверяет `ai-strings.test.ts`).
   Финальный выбор строки — по `finishReason` после исчерпания ретраев.
3. `server/src/ai/agent.ts`: общий `requestCompletion` передаёт `onUsage`;
   запись суммарного usage из `runLoop`/`runPlan` удалена во избежание дублей.
   Catch уже показывает `err.message`. Лог клиента содержит sessionId,
   номер попытки, finishReason, hadReasoning и решение о повторе; текста reasoning нет.
4. Тесты `server/test/client.test.ts`:
   - стрим, завершившийся пустым ответом, затем нормальным → вызов
     резолвится ответом, ретрай был ровно один;
   - три пустых подряд → ошибка, ровно 2 повтора (3 запроса);
   - `finish_reason: 'content_filter'` дважды → специализированная ошибка,
     один ретрай;
   - abort во время паузы ретрая → проброс abort, без лишнего вызова;
   - мерж usage при ретрае.
5. Дополнительные проверки: JSON и Responses/SSE, локализация ru/en,
   сохранение расходов при stop/ошибке следующей попытки, фиксированная модель,
   отсутствие дублей инструментов и расхода шагов, чистота persisted-истории.
   Частичный Responses-ответ и явные HTTP/SSE-ошибки не повторяются как пустые.

## Проверка

- `cd server && npm run build && npm test` — зелёные.
- Ручной сценарий: мок-endpoint (`server/test/mock-openai-manual.mjs`)
  с `MOCK_EMPTY_RESPONSES=N` (например, `MOCK_EMPTY_RESPONSES=2 node
  server/test/mock-openai-manual.mjs`; PowerShell: `$env:MOCK_EMPTY_RESPONSES='2'`,
  затем `node server/test/mock-openai-manual.mjs`). Первые N ответов пустые,
  следующие — обычный текст без инструментов/SSH. При N≤2 агент завершает ход,
  при N>2 приходит ошибка; каждая завершённая попытка попадает в расходы.
  Перезапуск мока сбрасывает счётчик. Рабочие настройки для теста не менять:
  использовать отдельный DATA_DIR и тестовый экземпляр агента.
