# Архитектура и детали реализации

Детальная документация реализации, вынесенная из AGENTS.md (там остались только правила, команды и инварианты). Заглядывай сюда при работе с конкретной подсистемой. Учти: это описание кода, оно может отставать от него — при расхождении верь коду и тестам.

## Структура проекта и фронтенд (web/)

- `server/` — Node.js + TypeScript (ESM). Express + WebSocket (`ws`) + `ssh2`. Вход: `src/index.ts`.
- `web/` — React 18 + Vite + xterm.js. Вход: `src/main.tsx`, корневой компонент `src/App.tsx`. Сообщения чата агента рендерятся как markdown (`react-markdown` + `remark-gfm`, компонент `src/components/Markdown.tsx`). Layout в стиле VS Code: разделы профиля (Обзор/Терминал/Файлы/Docker/Базы данных/Порты/Cron/Службы) — верхним таббаром, левый сайдбар — навигация: сверху пункт «Серверы» (сводный дашборд, `.profile-list-item`), делимитер `.sidebar-divider`, ниже список площадок кнопками `.profile-list-item` с подсветкой активной (скролл при переполнении) и точкой доступности сервера (`status-dot`: зелёная — доступен, красная — недоступен, жёлтая — нет данных; опрос `/api/overview` раз в 10 с, на паузе при скрытой вкладке браузера); вкладки keep-alive (скрываются `display:none`, не размонтируются; страницы получают prop `visible`, фоновые эффекты на паузе при скрытии, xterm делает `fit()` при возврате); AI-агент — постоянная панель справа (drag-разделитель, сворачивание, состояние в `localStorage` `sc-agent-open`/`sc-agent-width`, на окнах < 900 px — оверлей), монтируется keep-alive на каждый посещённый профиль (`key={profile.id}`, неактивные скрываются `display:none` классом `.hidden` в слотах `.agent-page-slot`), WS не рвётся при переключении вкладок, профилей и сворачивании панели; у профиля в сайдбаре — индикатор активности агента `.agent-dot` (зелёная пульсирующая — работает, жёлтая — ждёт подтверждения; App держит `Record<profileId, state>`, AgentPage репортит через `onActivity`). Редактор файлов — CodeMirror 6 (`@uiw/react-codemirror` + `@codemirror/language-data` + `theme-one-dark` + search, компонент `src/components/CodeEditor.tsx`, подключается через `React.lazy` отдельным чанком, тема синхронизирована с `data-theme` через MutationObserver, Ctrl+F) — используется в модалке редактирования FilesPage. Вкладка «Обзор» — `src/pages/OverviewPage.tsx` (метрики, polling 3 c только при видимой вкладке — тем же тиком грузится история нагрузки и рисуются графики `LoadChart` CPU/RAM из `components/Sparkline.tsx` в карточках «Процессор»/«Память», с мин/сред/макс и подписями времени; ось X — временная (частота опросов непостоянна), линия рвётся на null-значениях и гэпах > 3× медианного интервала — пауза опроса не выглядит сплошной линией; шкалы `Meter` и форматтеры `formatBytes/formatUptime/formatPct` экспортируются и переиспользуются). Страница «Серверы» (пункт в сайдбаре, стартовый экран) — `src/pages/ServersPage.tsx` (сводный дашборд всех профилей через `GET /api/overview`, polling 5 c только когда страница видима; карточка на профиль: статус, внешний IP (если определён), шкалы CPU/RAM/диск со спарклайнами истории нагрузки CPU/RAM (`Sparkline` из `components/Sparkline.tsx`, данные — bulk `GET /api/metrics-history` тем же poll-тиком), аптайм, контейнеры; клик — выбор профиля и переход на «Обзор»). Вкладка «Порты» — `src/pages/PortsPage.tsx` (polling 5 c только при видимой вкладке, фильтр по порту/адресу/процессу/контейнеру, scope-бейджи «наружу/локально/интерфейс»; аннотация опубликованных контейнерных портов «docker: имя» в колонке процесса хостовых слушателей; секция «Порты контейнеров» под основной таблицей — контейнер, IP, порт, протокол, доступ: «опубликован на :N» / «только сеть контейнера» / «сеть хоста»; контейнеры с host-сетью видны в основной таблице). Вкладка «Cron» — `src/pages/CronPage.tsx` (polling 5 c только при видимой вкладке): редактируемая таблица crontab SSH-пользователя (добавить/изменить/удалить/вкл-выкл через закомментирование строки; модалка с пресетами @reboot/@hourly/@daily/… и свободным выражением), read-only секции `/etc/crontab` и `/etc/cron.d/*`; человекочитаемое описание расписания (`human`) приходит с сервера; мутации возвращают свежий snapshot и применяются сразу, 409 (crontab изменился) — toast + reload. TerminalPage: палитра истории команд (Ctrl+R), чип контейнера + кнопка «Системный shell», «Спросить агента» (выделение или последние ~30 строк, ≤4 КБ; App держит стейт `agentRequest` с полем `mode: explain|new-dialogue|prefill`, AgentPage авто-отправляет «Объясни этот вывод терминала: …» при готовом WS и свободном агенте, иначе prefill в поле ввода) и меню «В чат ▾» с действиями строго на выделении (`onSelectionChange` трекает наличие, пункты без выделения disabled; обрезка та же ≤4 КБ с сохранением хвоста): «Открыть в новом чате» — `startNewDialogue()` + отложенная отправка первого сообщения в `ws.onopen` нового диалога (сверка `dialogueId`, протухший pending сбрасывается в cleanup WS-effect'а; при занятом агенте — toast-отказ), «Добавить в чат» — всегда только prefill поля ввода (цитата без инструкции, не затирает набранное, фокус и курсор в конец). DockerPage: колонки CPU/MEM (polling 3 c при видимой вкладке), prune-кнопки, секция Compose, кнопка терминала в строке контейнера. AgentPage: история диалогов — dropdown на всю ширину панели по кнопке «История» в тулбаре (в списке — название диалога и относительная дата через `formatRelativeDate` из `api.ts`, удаление по hover-кнопке, там же кнопка «Новый»; рядом с «История» — явная кнопка «Новый диалог» в тулбаре (тот же `startNewDialogue`); у мульти-серверных диалогов — бейдж `.dialogue-badge` «+N» по `extraProfileIds`); в тулбаре кнопка «Проверка безопасности» — модалка с необязательным sudo-паролем (не сохраняется и не передаётся модели) и селектором сервера из подключённых к диалогу (по умолчанию домашний); при запуске фронт шлёт WS `sudo_credentials` с `profileId` выбранного сервера (если пароль введён) и auto-send сообщения с инструкцией выполнить `security_audit`. Мульти-серверность: строка чипов `.agent-servers` под тулбаром (синхронизируется событием WS `servers`; домашний сервер первым без крестика, остальные с `✕` → `detach_server`; кнопка «+» — dropdown профилей → `attach_server`), бейдж сервера `.tool-server` в карточках tool_start/tool_pending/tool_result (поле `server` событий), карточка `connect_server` — «Подключить «сервер» к диалогу?» на стандартных кнопках approve/reject; «Спросить агента» из терминала добавляет в текст имя сервера (`agentRequest` несёт `profileId`, чтобы запрос попадал только в панель своего профиля при keep-alive монтировании). Подтверждения мутирующих инструментов: в сообщении порядок рендера «текст → карточки инструментов» (пояснение модели читается до карточек); единственная точка решения — закреплённая плашка `.pending-bar` у поля ввода (под PlanCard, вне скроллируемой ленты, всегда видна; одновременно висит максимум один pending-вызов — сервер обрабатывает вызовы последовательно, очередь просто сменяет содержимое плашки): статус-точка, лейбл `toolLabel`, бейдж сервера, preview главного аргумента `mainArgPreview` (~80 символов, mono), кнопка «Подробнее» (раскрывает полный главный аргумент `fullArgText` в mono-блоке со скроллом, для write_file/write_memory — путь/причина + размер содержимого, для docker_action — действие с целью; раскрытие сбрасывается при смене вызова) и кнопки «Подтвердить»/«Отклонить» (после клика блокируются со статусом «выполняется…» до `tool_result`; стейт `decidedCalls: Set<callId>` в AgentPage, очищается в `tool_result` и при смене диалога); клик по строке плашки скроллит ленту к карточке вызова (реестр DOM-карточек через callback-ref); в ToolCard кнопок нет — pending-карточка показывает preview аргумента, статус «ждёт подтверждения · кнопки — внизу панели» и «Детали» (JSON args, доступно и для pending).

Вкладка «Базы данных» (эпик 12, итерация 2) — `src/pages/DatabasesPage.tsx`: подключение = сохранённая сущность с явными креденшалами (как в DBeaver/TablePlus), пароль вводится один раз. Левая колонка: список подключений профиля (бейдж PG/MY, имя, движок · пользователь; кнопка «✎» — правка, «+ Добавить» в заголовке секции), ниже — базы выбранного подключения (размер/число таблиц, кнопка «⤓» — дамп .sql.gz) и таблицы (клик — prefill `SELECT * … LIMIT 100`). Форма подключения — модалка `ConnectionModal`: dropdown контейнеров из `/api/db/discovery` (автозаполняет движок/пользователя/базу/flavor подсказками env — env мог протухнуть, источник истины человек), пароль с «Показать» (placeholder в режиме правки «сохранён — пусто = не менять»), кнопка «Проверить подключение» до сохранения (ошибка клиента БД показывается как есть), «Удалить» с confirm — только в правке. Консоль: CodeEditor (тот же lazy-чанк, что файловый менеджер, `onRun` = Ctrl+Enter), тумблер «только чтение» (серверный SET перед запросом, по умолчанию ON и не персистится), EXPLAIN-кнопка (PG — `EXPLAIN (ANALYZE, BUFFERS)`), палитра истории Ctrl+R (localStorage `sc-db-history-<profileId>`, последние 50 — фокус внутри вкладки или hover, иначе браузерный reload), грид первого result set ≤1000 строк с пометками обрезки, сворачиваемый «Полный вывод», ошибки клиента — mono-блоком со stderr и exit code. «Спросить агента»: промпт с движком/версией/схемой (колонки ≤4 КБ, при серверной обрезке — пометка), `agentRequest.mode='send'` + `source='db'` включает кнопку «→ SQL» на sql-блоках ответов агента (вставка в редактор через `sqlInsert` в App + возврат на вкладку); выполняет сгенерированный запрос всегда пользователь. Гонки смены подключения/базы закрыты поколением контекста (`runSeqRef`).

## Архитектура сервера

- `src/auth.ts` — вход по паролю, httpOnly-cookie `sc_session` (24 ч, in-memory), rate-limit 10 попыток / 15 мин на IP (счётчик сбрасывается при успешном входе, протухшие записи чистятся), проверка авторизации для REST и WS.
- `src/profiles.ts` — CRUD профилей в `profiles.json` (zod-валидация, атомарная запись через tmp+rename). Поля профиля: `name, host, port, username, authType (key|password), keyPath, keyPassphrase, password, dockerCommand (по умолчанию docker), note`. Путь к ключу — путь внутри контейнера (`/keys/...`); `keyPassphrase` — passphrase зашифрованного ключа (опционально, пробрасывается в ssh2). При update непереданный секрет (`password`/`keyPath`/`keyPassphrase`) сохраняется из существующего профиля; при смене `authType` новый секрет обязателен. Битый JSON хранилища переименовывается в `*.corrupt-<timestamp>`, а persist отказывается перезаписывать файл до рестарта — молчаливого затирания нет (то же в `ai/dialogues.ts`).
- `src/ssh/manager.ts` — постоянные SSH-подключения на профиль (кэш в памяти, авто-переподключение по `close`; параллельные `getClient` делят один connect, при ошибке подключения клиент закрывается и запись удаляется): `exec` (timeout 60 c, лимит вывода 2 МБ; опциональный `stdin` — пишется в канал с EOF, используется для подачи пароля в `sudo -S`), `execStream` (для `docker logs -f`; `close()` до получения канала закрывает канал сразу после его получения), `execRawChannel` (сырой канал: stdout-стрим + stdin + exit code, для tar-передач файлов), `openShell` (PTY), `getSftp`/`withSftp`.
- `src/ssh/sftp.ts` — promise-обёртки над callback-API SFTP (`readdir, stat, readFile, writeFile, mkdir, rmdir, unlink, rename, chmod`). Всегда использовать их, а не сырые callback-методы.
- `src/services/docker.ts` — docker CLI по SSH: команда собирается из `dockerCommand` профиля + экранированных аргументов (`shq`); `parseDockerJsonOutput` понимает NDJSON, JSON-массив и одиночный объект. Команда контейнера в `run` (`runContainerArgs`) оборачивается в `sh -c <shq(command)>` — многословная команда трактуется как shell-строка, а не имя бинаря. Compose поддерживается только v2 (плагин `docker compose`; standalone v1 отклоняется с понятной ошибкой), детект кэшируется на профиль.
- `src/services/metrics.ts` + `src/routes/metrics.ts` — метрики сервера для вкладки «Обзор» (`GET /api/metrics?profileId=`): CPU/mem/disk/uptime/load по SSH, кэш снимка 2 с на профиль.
- `src/services/metrics-history.ts` + `src/routes/metrics-history.ts` — история нагрузки для графиков (сэмпл — лёгкий срез снимка: `t, cpu, memPct, memUsedBytes, memTotalBytes, load1`): in-memory `Map<profileId, HistorySample[]>` без персистентности (после рестарта копится заново). Пишется хуком внутри `collectMetrics` — собственный опрос не нужен, историю кормят запросы `/api/metrics` и `/api/overview` (сайдбар опрашивает каждые 10 с при открытом UI); дедуп по timestamp (кэш снимка возвращает тот же промис) и минимальный гэп 2 с, лимиты 4320 сэмплов на профиль и 24 ч возраста (возраст проверяется и при записи, и при отдаче по wall clock — пока профиль недоступен и новых сэмплов нет, история всё равно стареет). Чистые функции `toSample`/`shouldAppend`/`trimSamples`/`decimate`; `clearHistory` вызывается при удалении профиля. Маршрут: `GET /api/metrics-history?profileId=` — `{timestamp, samples}` (≤360 точек, «Обзор»), без profileId — `{timestamp, profiles: [{id, samples}]}` (≤120 точек на профиль, спарклайны «Серверов»).
- `src/services/ports.ts` + `src/routes/ports.ts` — прослушиваемые порты для вкладки «Порты» (`GET /api/ports?profileId=`): `ss -tulpn` по SSH (фолбэк `netstat -tulpn`), чистый парсер `parseListeners` (определяет формат по строке, вычисляет scope public/loopback/interface), кэш 2 с на профиль. Без root имена чужих процессов недоступны — колонка процесса пустая. `src/services/container-ports.ts` — порты docker-контейнеров: `docker ps` + батч-`docker inspect`, парсинг `NetworkSettings.Ports` (runtime-биндинги, не строковый `Ports` из `docker ps`), кэш 2 с. Роут собирает хостовые и контейнерные порты параллельно (`Promise.all` + `.catch(() => null)` на контейнерной ветке); docker недоступен → поля `containers` нет (деградация); хостовые слушатели матчатся с опубликованными контейнерными портами по `(proto, hostPort, hostIp)` с wildcard для `0.0.0.0`/`::` — аннотация `container: {id, name}` закрывает дыру «безымянный docker-proxy без root».
- `src/services/cron.ts` + `src/routes/cron.ts` — cron-задачи для вкладки «Cron» (`GET /api/cron?profileId=`): пользовательский `crontab -l` (отсутствие — `null`, не ошибка), `/etc/crontab` и `/etc/cron.d/*` одной командой с маркерами `=== <файл>`; чистые функции `parseCrontab` (system-формат с колонкой user, `@keywords`, env-строки и комментарии отдельно, закомментированные записи → `enabled:false`, у записи `index` = номер строки), `describeSchedule` (русские описания частых расписаний), `validateCronFields`, `applyCrontabOp` (add/update/delete/toggle с защитой от гонки через `expectedRaw` → `CronConflictError`/409); кэш 2 с на профиль. Мутации (`mutateUserCrontab`) только пользовательского crontab: чтение заново без кэша → `applyCrontabOp` → запись целиком через `crontab -` (stdin канала). Системные файлы — read-only.
- `src/services/systemd.ts` + `src/routes/services.ts` — службы systemd для вкладки «Службы» (эпик 13). Снимок (`GET /api/services?profileId=`) — один exec с маркерами и `2>&1`/`LC_ALL=C`: `systemctl --version | head -1`, `list-units --type=service --all --no-pager --plain --no-legend`, `list-unit-files --type=service --no-pager --plain --no-legend`; код возврата игнорируется — решение принимает парсер. Чистые функции: `parseVersionLine` (systemd или `not found`), `parseListUnits` (колонки `UNIT LOAD ACTIVE SUB DESCRIPTION`, `-` → null, описание — всё после 4-й колонки, `--plain` снимает bullet `●`), `parseListUnitFiles` (**STATE — всегда второе поле `fields[1]`**: с systemd ≥ 245 колонок три — `UNIT FILE / STATE / PRESET`, PRESET игнорируется), `mergeUnits` (имя из любого списка, enabled из unit-files — отсутствует → null у transient-юнитов), `parseSnapshot` (детект не-systemd: `not found` → «systemctl не найден…», `has not been booted with systemd` → «не является PID 1 (контейнер?)», ошибка флага в начале секции `Unknown option`/`Invalid option`/`Failed to` → причина с текстом ошибки — иначе парсер молча отбросил бы её как мусор); кэш 2 с на профиль + `invalidateServicesCache` после мутации. Деталь (`GET /api/services/:unit?profileId=`) — `systemctl status --no-pager -n 0` + `systemctl show -p …` (11 полей: MainPID, ActiveState, SubState, UnitFileState, FragmentPath, Restart, NRestarts, Result, MemoryCurrent, TasksCurrent, ActiveEnterTimestamp) через маркер `@@SHOW@@`; `parseShowOutput` — строки `KEY=VALUE`, первое вхождение выигрывает; код возврата статуса (3 = inactive, 4 = not-found) — не ошибка. Действия (`POST /api/services/:unit/action`, whitelist start|stop|restart|reload|enable|disable|reset-failed; reset-failed сверх роадмапа — осознанно) — `runServiceAction`: без sudo `systemctl <action> -- <unit>` (unit через `shq`, `--` — защита от опций), при sudo-needed — ретрай с sudo **прямой формой `sudo -S -p '' -- systemctl <action> -- <unit>` без `sh -c`** (пароль первой строкой stdin, не в argv/логах, живёт в памяти одного запроса; ретрай безопасен — отказ прав означает, что мутация не началась). Классификация `classifyActionFailure`: polkit-формулировки `Interactive authentication required`/`Authentication is required` и безpolkit-ные `Access denied`/`Operation refused`/`Permission denied` → sudo-needed; masked/not-found/job-failed → 400 с текстом systemd как есть (состояние сервиса, не транспорт); прочее → 502. Зонд пароля `sudo -S -p '' -- true` (`classifySudoProbe`): `Sorry, try again.` → 400 «Неверный sudo-пароль», `is not in the sudoers file`/`not allowed to execute` → 400 «нет прав sudo», `not found` → 400 «sudo не установлен». Журнал (`GET /api/services/:unit/logs?profileId=&tail=&follow=1`) — `journalctl -u <unit> --no-pager -n <tail> [-f]`, tail 1..5000 дефолт 500: разовый — exec с таймаутом 30 с и честной пометкой «… (вывод обрезан по лимиту 2 МБ)» при упоре в лимит exec; follow — исправленный `execStream` + chunked `text/plain; charset=utf-8` + `Cache-Control: no-cache` + `req.on('close')` → `handle.close()`, через лимитер и гейт (см. ниже), сверх лимита — 429. **Sudo для журнала в v1 не делается**, отказ маскируется под пустой вывод с кодом 0 — UI показывает подсказку про группы `adm`/`systemd-journal`.
- `src/services/stream-limits.ts` + `src/services/chunk-gate.ts` — общие механики follow-стримов (эпик 13, по плану эпика 14). `stream-limits.ts` — лимитер активных follow-стримов **на профиль, не на подсистему** (один SSH-канал на профиль, `MaxSessions 10` у OpenSSH): `acquireFollowSlot`/`releaseFollowSlot` (идемпотентно), лимит 3, сверх — 429; используют `/api/docker/containers/:id/logs?stream=1` и `/api/services/:unit/logs?follow=1`. `chunk-gate.ts` — `createChunkGate(res)`: при `res.writableLength > 1 МБ` чанки дропаются с подсчётом, при возврате в норму пишется маркер «… (пропущено N байт: сервер занят)» — просмотрщик с кольцевым буфером переживёт потерю середины; pause/resume канала планом отклонён. В `ssh/manager.ts` починен транспорт `execStream`: `handle.code` — настоящий промис с первого момента (раньше `Promise.resolve(null)` подменялся только после открытия канала, и синхронное чтение в роуте закрывало ответ до первого чанка — стрим отдавал пустоту).
- `src/services/tunnels.ts` + `src/routes/tunnels.ts` — SSH-туннели (эквивалент `ssh -L`): in-memory реестр без персистентности (после рестарта туннелей нет). `createTunnel` поднимает `net.createServer()` на `127.0.0.1:localPort`, на каждое TCP-соединение — `client.forwardOut()` через `getClient`, двусторонний pipe socket↔channel. Валидация `validateTunnelParams` (чистая функция): порты 1–65535, `targetHost` до 253 символов `[a-zA-Z0-9._-]`, лимит 10 active туннелей на профиль (closed не считаются), дубль `(profileId, localPort)` → 409. `localPort: 0` → автоподбор свободного в диапазоне `TUNNEL_PORT_MIN`–`TUNNEL_PORT_MAX`. Лимит соединений на туннель — 10. Ошибка сервера (EADDRINUSE) → статус `closed` с ошибкой, туннель остаётся в реестре до `DELETE`. Маршруты: `GET /api/tunnels?profileId=` (список + `portRange`), `POST /api/tunnels` (создание, 409 при EADDRINUSE/конфликте), `DELETE /api/tunnels/:id`.
- `src/services/overview.ts` + `src/routes/overview.ts` — сводный дашборд всех профилей (`GET /api/overview`, без profileId): параллельный опрос (Promise.allSettled), guard-таймаут 8 с на профиль (упавший сервер → `ok:false` с ошибкой, ответ не висит), docker-счётчики через `docker ps -a --format json` (при недоступном docker — просто нет поля), внешний IP через `services/external-ip.ts` (curl к ifconfig.me/api.ipify.org, wget-фолбэк, строгая IPv4-валидация `parseExternalIp`, кэш на профиль: успех 10 мин / неудача 1 мин, никогда не бросает — при недоступности поля нет), кэш всего ответа 4 с. Агрегирующий маппинг — чистые функции `toOverviewEntry`/`countContainers`.
- `src/services/file-search.ts` — поиск файлов: `mode=name` (`find -iname`) и `mode=content` (`grep -rInF`), лимиты 500 результатов / 30 c.
- `src/services/security-audit.ts` — детерминированный аудит безопасности для инструмента агента `security_audit`: фиксированный белый список read-only команд по секциям (`auth, network, updates, activity, docker, filesystem`; чистые билдеры `commandsForSection`/`sudoWrap`/`findContainerIssues`), произвольный shell не принимает. Root-подсекции — через `sudo -S -p '' -- sh -c <shq(cmd)>` с паролем в stdin канала (не в командной строке); без пароля или при нерабочем sudo помечаются «пропущено: нет прав» (мягкая деградация). Docker-секция — через `services/docker.ts` (privileged, host network, монтирование docker.sock и корня ФС). Лимиты вывода: строки и символы на подсекцию + общий ~10 КБ (параметр `sections` для запроса по частям).
- `src/services/transfer.ts` — сборка tar-команд для скачивания/загрузки каталогов (`download-dir`/`upload-dir`), детект отсутствия `tar` с понятной ошибкой.
- `src/services/db-connections.ts` — хранилище подключений БД в `DATA_DIR/db-connections.json` (паттерн `profiles.ts`: zod-валидация, атомарная запись tmp+rename, corrupt-guard `*.corrupt-*` + отказ persist до рестарта). Поля: `id, profileId, name, engine (postgres|mysql), target {kind:'container', containerId} | {kind:'host', host, port} (host — модель под v2, рабочий путь v1 — контейнер), username, password, defaultDatabase?, flavor? ('mariadb' — другой синтаксис SET-таймаута; снапшот с образа при создании), createdAt, updatedAt`. Пароль открытым текстом — тот же trust domain, что SSH-пароли `profiles.json`; `\n`/`\r` в пароле отклоняются валидацией (передаётся первой строкой stdin). Частичный update секрета — как у профилей: непереданный `password` сохраняется из существующей записи. Наружу (`toSafeDbConnection`) пароль не отдаётся, вместо него `hasPassword`.
- `src/services/db-discovery.ts` — discovery контейнеров СУБД для автозаполнения формы подключения (итерация 2: env контейнера — только подсказка, креденшалы задаёт человек): `docker ps` + батч-`docker inspect` (паттерн `container-ports.ts`), кэш 2 с. Чистые функции: `imageRepository` (референс образа → репозиторий), `matchDbEngine` (расширяемый список: postgres, timescale/, postgis, bitnami, mysql, mariadb), `matchMysqlFlavor`, `extractEnv`, `toDbSuggestion` (env-подсказки `POSTGRES_USER`/`POSTGRES_DB`/`MYSQL_USER`/`MYSQL_DATABASE`), `toDbHint` (порт 5432/3306 с неопознанным образом — текстовая подсказка).
- `src/services/db-query.ts` — SQL-консоль: чистые билдеры команд и парсеры вывода под unit-тесты + тонкие exec-обёртки. Цель выполнения — `DbExecTarget {engine, containerId, username, password ('' = без пароля), flavor?, defaultDatabase}`. Пароль — **первой строкой stdin** (`IFS= read -r PGPASSWORD/MYSQL_PWD; export …; exec psql/mysql …`): не светится в argv/ps хоста и не берётся из протухшего env контейнера; `IFS=`/`-r` обязательны (пробелы и бэкслеши в пароле). `buildChannelStdin` собирает `<пароль>\n<SQL>`; SQL-часть (`buildStdinSql`) — SET-таймаут MySQL/MariaDB (`max_execution_time` мс / `max_statement_time` с, PG — `PGOPTIONS` env) + read-only SET + `ensureTerminator` (psql молча отбрасывает незавершённый statement). Двойное экранирование: docker-аргументы — внешний `shq` (dockerCommand), имена пользователя/базы — внутренние кавычки внутри `sh -c`. Парсеры: `parseCsvTable` (psql `--csv`, RFC 4180, обрезанный вывод — последняя строка выбрасывается + `truncated`), `parseTsvTable` (mysql `--batch` с `\t`/`\n`/`\\`/`\0`-escape; NULL неотличим от строки 'NULL' — известное ограничение); оба останавливаются на расхождении колонок (многоstatement'ный вывод — грид берёт первый result set, полный stdout в `rawOutput`). Обёртки: `runDbQuery` (лимит 1000 строк, таймаут канала 120 с, таймаут statement 115 с), `testDbConnection` (SELECT 1, 15 c — для `/connections/test`), `fetchDbOverview/Databases/Tables/Columns` (information_schema/pg_catalog, системные базы/схемы скрыты, у PG счётчик таблиц — отдельный запрос на базу ≤25, фолбэк списка баз без размеров при отказе в правах).
- `src/services/db-dump.ts` — дамп базы `pg_dump|gzip` / `mysqldump|gzip` внутри контейнера (`exec -i` + пароль первой строкой stdin, EOF обязателен — `read` блокируется до конца stdin). Без pipefail (dash 0.5.11 абортит скрипт на неизвестной опции): роут буферизует голову stdout до 64 байт — упавший дамп отдаёт 500 со stderr до отправки заголовков; таймаута канала нет (большой дамп идёт минутами, обрыв — `req.on('close')`).
- `src/services/history.ts` + `src/routes/terminal.ts` — история shell-команд (`GET /api/terminal/history?profileId=&limit=`): форматы bash/zsh, дедуп, по умолчанию 100 / максимум 200.
- `src/services/keys.ts` + `src/routes/keys.ts` — `GET /api/keys` (список файлов в `KEYS_DIR` для выпадающего списка в форме) и `POST /api/keys?name=&overwrite=1` (импорт ключа из UI: raw body ≤ 64 КБ, проверка PEM/OpenSSH-заголовка, санитизация имени `[A-Za-z0-9._-]`, атомарная запись с правами 0600, без `overwrite=1` существующий файл не затирается — 409). Чтение содержимого ключей наружу не отдаётся — только имена.
- `src/services/profile-transfer.ts` — перенос профилей между машинами: `POST /api/profiles/export` (файл бэкапа; секреты — только при `includeSecrets=true`, с `passphrase` шифруется scrypt + AES-256-GCM; ключи вкладываются только из `KEYS_DIR` и только вместе с секретами) и `POST /api/profiles/import` (`{backup, passphrase?}`; всё валидируется до первой записи, конфликты имён — суффикс « (2)», существующие ключи не затираются, `keyPath` перепривязывается к текущему `KEYS_DIR`, профили без секрета попадают в `needSecrets` — секрет задаётся вручную через `importProfile` в `profiles.ts`, который не требует секрет при создании). Формат бэкапа версионируется (`app/version/encrypted`).
- `src/ws/terminal.ts` — терминальные сессии на профиль: буфер ввода до готовности shell, переживают перезагрузку вкладки (60 c после последнего отсоединения), удаляются по завершении процесса. Опциональный `container` в query — PTY-сессия `docker exec -it` в контейнер, ключ сессии `profileId::container` (системный shell и shell контейнера — разные сессии). WS-сообщение `restart` закрывает shell и SSH-подключение и открывает новый shell (применяются новые группы/права).
- `src/ai/` — агент: `client.ts` (Chat Completions, streaming SSE, аккумуляция tool_calls, таймаут соединения 120 c), `tools.ts` (определения инструментов + `READ_ONLY_TOOLS` + гейтинг `getToolDefs` — web_search объявляется модели только при настроенном поиске; во всех SSH-инструментах и инструментах памяти — необязательный параметр `server` (имя профиля, по умолчанию домашний сервер диалога)), `guard.ts` (deny-лист read-only команд), `agent.ts` (цикл, подтверждения, лимит шагов, системный промпт; мульти-серверная сессия — см. ниже), `plan.ts` (режим планирования: `PLAN_MODE_INSTRUCTION`, `toolsForRequest`, `buildPlanRequestMessages`), `messages.ts` (санитизация истории сообщений), `memory.ts` (пер-профильная память MEMORY.md), `web-search.ts` (веб-поиск для агента — см. ниже).
- `src/ai/dialogues.ts` — хранение диалогов агента в `DATA_DIR/ai-dialogues.json` (zod-валидация, атомарная запись tmp+rename, кэш в памяти). Мульти-серверность: `extraProfileIds?: string[]` в схеме (опционально, старые JSON валидны), `attachProfileToDialogue`/`detachProfileFromDialogue` (домашний `profileId` отцепить нельзя), `extraProfileIds` пробрасывается в сводку `listDialogues`.
- `src/ai/web-search.ts` — веб-поиск для инструмента агента `web_search`: Anthropic-совместимый endpoint DeepSeek (`AI_SEARCH_API_BASE`, по умолчанию пусто — фича выключена) с серверным инструментом `web_search_20260209` (`max_uses` 3 на вызов), ключ общий с `AI_API_KEY`, модель — `AI_SEARCH_MODEL` (по умолчанию `deepseek-v4-flash`). Чистые функции: `buildSearchBody` (тело Messages-запроса), `parseSearchResponse` (текст + выполненные запросы + источники; `encrypted_content` и thinking-блоки игнорируются), `formatSearchOutput`, `sanitizeQuery` (лимит 400 символов), `isSearchConfigured`. `searchWeb` — fetch с таймаутом 90 с, никогда не бросает (ошибки возвращаются текстом). Основной клиент агента (OpenAI-формат) не меняется — поиск это отдельный read-only инструмент с собственным HTTP-вызовом; в `agent.ts` лимит 10 вызовов `web_search` за запуск цикла (сброс в начале `runLoop`), без конфигурации инструмент модели не объявляется вовсе.
- `src/routes/ai.ts` — REST для диалогов: `GET/POST /api/ai/dialogues`, `GET/DELETE /api/ai/dialogues/:id`.

- WS `/ws/agent?profileId=&dialogueId=` — клиент `message {content, planMode?}|approve|reject|approve_plan|stop|sudo_credentials {password, profileId?}|attach_server {profileId}|detach_server {profileId}`, сервер `dialogue|token|message|tool_start|tool_pending|tool_result|plan_ready|running|done|error|servers`. `tool_start {callId, name, args, server}` — read-only инструмент начал выполняться (карточка «выполняется…» в UI, без кнопок), `tool_pending` — мутрующий ждёт подтверждения; поле `server` (имя профиля; для connect_server — целевой) — в `tool_start`/`tool_pending`/`tool_result`. Событие `servers {home, attached: [{id, name, host, username}]}` — при подключении WS и на каждое изменение состава серверов диалога (attach/detach/connect_server). Диалог загружается в сессию при подключении и сохраняется по ходу каждого шага; если `dialogueId` не передан, сервер создаёт новый диалог и сообщает его id событием `dialogue`. `sudo_credentials` задаёт sudo-пароль для привилегированного `security_audit` на сервере `profileId` (по умолчанию домашний): пароль хранится только в Map сессии (память), очищается в `stop()`/`onWsClose()` и при detach сервера; не логируется, не сохраняется в диалог и не передаётся модели. `attach_server`/`detach_server` — ручное подключение/отключение сервера к диалогу (действие пользователя, approve не требуется; домашний отцепить нельзя — клиенту уходит error).
