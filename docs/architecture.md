# Архитектура и детали реализации

Детальная документация реализации, вынесенная из AGENTS.md (там остались только правила, команды и инварианты). Заглядывай сюда при работе с конкретной подсистемой. Учти: это описание кода, оно может отставать от него — при расхождении верь коду и тестам.

## Структура проекта и фронтенд (web/)

- `server/` — Node.js + TypeScript (ESM). Express + WebSocket (`ws`) + `ssh2`. Вход: `src/index.ts`.
- `web/` — React 18 + Vite + xterm.js. Вход: `src/main.tsx`, корневой компонент `src/App.tsx`. Сообщения чата агента рендерятся как markdown (`react-markdown` + `remark-gfm`, компонент `src/components/Markdown.tsx`). Layout в стиле VS Code: разделы профиля (Обзор/Терминал/Файлы/Docker/Базы данных/Nginx/Порты/Cron/Службы) — верхним таббаром, левый сайдбар — навигация: сверху пункт «Серверы» (сводный дашборд, `.profile-list-item`), делимитер `.sidebar-divider`, ниже список площадок кнопками `.profile-list-item` с подсветкой активной (скролл при переполнении) и точкой доступности сервера (`status-dot`: зелёная — доступен, красная — недоступен, жёлтая — нет данных; опрос `/api/overview` раз в 10 с одним тиком с `/api/alerts` при включённых алертах — см. эпик 20 ниже; на паузе при скрытой вкладке браузера только когда алерты выключены); вкладки keep-alive (скрываются `display:none`, не размонтируются; страницы получают prop `visible`, фоновые эффекты на паузе при скрытии, xterm делает `fit()` при возврате); AI-агент — постоянная панель справа (drag-разделитель, сворачивание, состояние в `localStorage` `sc-agent-open`/`sc-agent-width`, на окнах < 900 px — оверлей), монтируется keep-alive на каждый посещённый профиль (`key={profile.id}`, неактивные скрываются `display:none` классом `.hidden` в слотах `.agent-page-slot`), WS не рвётся при переключении вкладок, профилей и сворачивании панели; у профиля в сайдбаре — индикатор активности агента `.agent-dot` (зелёная пульсирующая — работает, жёлтая — ждёт подтверждения; App держит `Record<profileId, state>`, AgentPage репортит через `onActivity`). Редактор файлов — CodeMirror 6 (`@uiw/react-codemirror` + `@codemirror/language-data` + `theme-one-dark` + search, компонент `src/components/CodeEditor.tsx`, подключается через `React.lazy` отдельным чанком, тема синхронизирована с `data-theme` через MutationObserver, Ctrl+F) — используется в модалке редактирования FilesPage. Вкладка «Обзор» — `src/pages/OverviewPage.tsx` (метрики, polling 3 c только при видимой вкладке — тем же тиком грузится история нагрузки и рисуются графики `LoadChart` CPU/RAM из `components/Sparkline.tsx` в карточках «Процессор»/«Память», с мин/сред/макс и подписями времени; ось X — временная (частота опросов непостоянна), линия рвётся на null-значениях и гэпах > 3× медианного интервала — пауза опроса не выглядит сплошной линией; шкалы `Meter` и форматтеры `formatBytes/formatUptime/formatPct` экспортируются и переиспользуются); клик по строке диска открывает навигатор «Что занимает» `components/DiskUsageModal.tsx` (эпик 16: `du -d 1` на уровень, проваливание по подкаталогам с хлебными крошками, режим «Файлы» — топ крупнейших, «Открыть в Файлах» переключает вкладку через `onOpenInFiles`; смена пути/режима рвёт прошлый запрос AbortController'ом). Страница «Серверы» (пункт в сайдбаре, стартовый экран) — `src/pages/ServersPage.tsx` (сводный дашборд всех профилей через `GET /api/overview`, polling 5 c только когда страница видима; карточка на профиль: статус, внешний IP (если определён), шкалы CPU/RAM/диск со спарклайнами истории нагрузки CPU/RAM (`Sparkline` из `components/Sparkline.tsx`, данные — bulk `GET /api/metrics-history` тем же poll-тиком), аптайм, контейнеры; клик — выбор профиля и переход на «Обзор»; под сеткой карточек — раздел «Команды» `components/SnippetsSection.tsx` (эпик 18: список сохранённых команд с превью mono-строкой и правкой в модалке, разовая команда без сохранения, чекбоксы целей из профилей App с статус-точками из снапшота overview, подтверждение-модалка до запуска — команда mono-блоком, явный список целей «имя — user@host» и предупреждение о запуске без фильтрации; запуск сниппета с областью (`profileIds !== null`) предвыбирает именно его цели, модалка поясняет сброс выбора строкой «область команды»; во время запуска цели заморожены (дизейбл чекбоксов, счётчик по замороженному списку) и доступна кнопка «Отменить» (AbortController: UI освобождается сразу, команда на серверах дорабатывает своё); результаты — аккордеон по серверам с бейджем кода возврата/«ошибка», stdout/stderr в `.snippets-output` (mono, скролл, пометка «вывод обрезан» при `truncated`), «В чат» — `agentRequest.mode='send'` с хвостом вывода ≤4 КБ; props `onAskAgent`/`profiles` пробрасываются из App тем же путём, что TerminalPage/FilesPage). Вкладка «Порты» — `src/pages/PortsPage.tsx` (polling 5 c только при видимой вкладке, фильтр по порту/адресу/процессу/контейнеру, scope-бейджи «наружу/локально/интерфейс»; аннотация опубликованных контейнерных портов «docker: имя» в колонке процесса хостовых слушателей; секция «Порты контейнеров» под основной таблицей — контейнер, IP, порт, протокол, доступ: «опубликован на :N» / «только сеть контейнера» / «сеть хоста»; контейнеры с host-сетью видны в основной таблице). Вкладка «Cron» — `src/pages/CronPage.tsx` (polling 5 c только при видимой вкладке): редактируемая таблица crontab SSH-пользователя (добавить/изменить/удалить/вкл-выкл через закомментирование строки; модалка с пресетами @reboot/@hourly/@daily/… и свободным выражением), read-only секции `/etc/crontab` и `/etc/cron.d/*`; человекочитаемое описание расписания (`human`) приходит с сервера; мутации возвращают свежий snapshot и применяются сразу, 409 (crontab изменился) — toast + reload. TerminalPage: внутренние вкладки терминалов (эпик 15) — `TerminalPage` держит стейт вкладок `{tabs, nextId, activeId}` в localStorage `sc-terminal-tabs:<profileId>` (стабильный `tabId` = монотонный счётчик, живёт с вкладкой всю жизнь; чтение с валидацией — мусорные элементы и дубли id отбрасываются, битый/пустой → одна вкладка `{id:0}`; запись при каждом изменении), при монтировании сверяется с `GET /api/terminal/sessions`: серверные сессии без локальной вкладки добавляются (после чистки localStorage/другого браузера), переполнение режет с конца локальные вкладки без серверной сессии; все вкладки keep-alive (неактивные `display:none`, каждая держит свой WS — осознанный расход бюджета SSH-каналов, лимит 4 управляет), заголовок host-вкладки `shell N` (N = tabId+1), контейнерной — имя контейнера, статус-точка в заголовке, «✕» шлёт close-фрейм **только по явному закрытию пользователем** (ref-флаг `closeOnUnmountRef`: смена профиля размонтирует страницу, и безусловный close убивал бы все терминалы вместо grace), «+» задизейблена на лимите из ответа сервера; дочерний `TerminalView` — прежний блок (xterm + WS + тулбар + палитра истории Ctrl+R, «Спросить агента», «В чат ▾», «Обновить сессию»), `fit()` по `active` и `visible`; DockerPage открывает терминал контейнера через одноразовый `terminalOpenRequest` в App (паттерн `sqlInsert`: существующая вкладка контейнера активируется, новой нет — добавляется; сбрасывается при смене профиля) — контейнерные вкладки сосуществуют с системным shell. «Спросить агента» (выделение или последние ~30 строк, ≤4 КБ; App держит стейт `agentRequest` с полем `mode: explain|new-dialogue|prefill`, AgentPage авто-отправляет «Объясни этот вывод терминала: …» при готовом WS и свободном агенте, иначе prefill в поле ввода) и меню «В чат ▾» с действиями строго на выделении (`onSelectionChange` трекает наличие, пункты без выделения disabled; обрезка та же ≤4 КБ с сохранением хвоста): «Открыть в новом чате» — `startNewDialogue()` + отложенная отправка первого сообщения в `ws.onopen` нового диалога (сверка `dialogueId`, протухший pending сбрасывается в cleanup WS-effect'а; при занятом агенте — toast-отказ), «Добавить в чат» — всегда только prefill поля ввода (цитата без инструкции, не затирает набранное, фокус и курсор в конец). DockerPage: колонки CPU/MEM (polling 3 c при видимой вкладке), prune-кнопки, секция Compose, кнопка терминала в строке контейнера. AgentPage: история диалогов — dropdown на всю ширину панели по кнопке «История» в тулбаре (в списке — название диалога и относительная дата через `formatRelativeDate` из `api.ts`, удаление по hover-кнопке, там же кнопка «Новый»; рядом с «История» — явная кнопка «Новый диалог» в тулбаре (тот же `startNewDialogue`); у мульти-серверных диалогов — бейдж `.dialogue-badge` «+N» по `extraProfileIds`); в тулбаре кнопка «Проверка безопасности» — модалка с необязательным sudo-паролем (не сохраняется и не передаётся модели) и селектором сервера из подключённых к диалогу (по умолчанию домашний); при запуске фронт шлёт WS `sudo_credentials` с `profileId` выбранного сервера (если пароль введён) и auto-send сообщения с инструкцией выполнить `security_audit`. Мульти-серверность: строка чипов `.agent-servers` под тулбаром (синхронизируется событием WS `servers`; домашний сервер первым без крестика, остальные с `✕` → `detach_server`; кнопка «+» — dropdown профилей → `attach_server`), бейдж сервера `.tool-server` в карточках tool_start/tool_pending/tool_result (поле `server` событий), карточка `connect_server` — «Подключить «сервер» к диалогу?» на стандартных кнопках approve/reject; «Спросить агента» из терминала добавляет в текст имя сервера (`agentRequest` несёт `profileId`, чтобы запрос попадал только в панель своего профиля при keep-alive монтировании). Подтверждения мутирующих инструментов: в сообщении порядок рендера «текст → карточки инструментов» (пояснение модели читается до карточек); единственная точка решения — закреплённая плашка `.pending-bar` у поля ввода (под PlanCard, вне скроллируемой ленты, всегда видна; одновременно висит максимум один pending-вызов — сервер обрабатывает вызовы последовательно, очередь просто сменяет содержимое плашки): статус-точка, лейбл `toolLabel`, бейдж сервера, preview главного аргумента `mainArgPreview` (~80 символов, mono), кнопка «Подробнее» (раскрывает полный главный аргумент `fullArgText` в mono-блоке со скроллом, для write_file/write_memory — путь/причина + размер содержимого, для docker_action — действие с целью; раскрытие сбрасывается при смене вызова) и кнопки «Подтвердить»/«Отклонить» (после клика блокируются со статусом «выполняется…» до `tool_result`; стейт `decidedCalls: Set<callId>` в AgentPage, очищается в `tool_result` и при смене диалога); клик по строке плашки скроллит ленту к карточке вызова (реестр DOM-карточек через callback-ref); в ToolCard кнопок нет — pending-карточка показывает preview аргумента, статус «ждёт подтверждения · кнопки — внизу панели» и «Детали» (JSON args, доступно и для pending).

Вкладка «Базы данных» (эпик 12, итерация 2) — `src/pages/DatabasesPage.tsx`: подключение = сохранённая сущность с явными креденшалами (как в DBeaver/TablePlus), пароль вводится один раз. Левая колонка: список подключений профиля (бейдж PG/MY, имя, движок · пользователь; кнопка «✎» — правка, «+ Добавить» в заголовке секции), ниже — базы выбранного подключения (размер/число таблиц, кнопка «⤓» — дамп .sql.gz) и таблицы (клик — prefill `SELECT * … LIMIT 100`). Форма подключения — модалка `ConnectionModal`: dropdown контейнеров из `/api/db/discovery` (автозаполняет движок/пользователя/базу/flavor подсказками env — env мог протухнуть, источник истины человек), пароль с «Показать» (placeholder в режиме правки «сохранён — пусто = не менять»), кнопка «Проверить подключение» до сохранения (ошибка клиента БД показывается как есть), «Удалить» с confirm — только в правке. Консоль: CodeEditor (тот же lazy-чанк, что файловый менеджер, `onRun` = Ctrl+Enter), тумблер «только чтение» (серверный SET перед запросом, по умолчанию ON и не персистится), EXPLAIN-кнопка (PG — `EXPLAIN (ANALYZE, BUFFERS)`), палитра истории Ctrl+R (localStorage `sc-db-history-<profileId>`, последние 50 — фокус внутри вкладки или hover, иначе браузерный reload), грид первого result set ≤1000 строк с пометками обрезки, сворачиваемый «Полный вывод», ошибки клиента — mono-блоком со stderr и exit code. «Спросить агента»: промпт с движком/версией/схемой (колонки ≤4 КБ, при серверной обрезке — пометка), `agentRequest.mode='send'` + `source='db'` включает кнопку «→ SQL» на sql-блоках ответов агента (вставка в редактор через `sqlInsert` в App + возврат на вкладку); выполняет сгенерированный запрос всегда пользователь. Гонки смены подключения/базы закрыты поколением контекста (`runSeqRef`).

Живой просмотр логов (эпик 14) — переиспользуемый компонент `src/components/LogViewer.tsx`: не знает про источник (файл, journalctl, apt) и про пин — их задаёт вызывающий через `buildUrl(follow)` (стабилизируется `useCallback`, иначе identity пропа перезапускает стрим), опциональные `logPath`/`serverName` (контекст для «В чат») и слот `toolbarExtra`. Внутри: fetch-стрим паттерном LogsModal (AbortController + reader, пауза при `!visible`, рестарт с чистым буфером при смене follow/возврате видимости/retry), чанки копятся в ref и флэшатся в стейт интервалом 250 мс (батчинг против ререндера на каждый чанк); флешится и неполная хвостовая строка (`pendingLine`) — без неё пустой лог и серверная пометка об обрезке (обе без финального `\n`) не видны вовсе; на `done` — финальный флеш; фильтр/копирование/«В чат» работают по линиям + pending как по одному набору. Кольцевой буфер 5000 строк — чистый модуль `src/log-buffer.ts` (`appendChunk` делит по `\n` с неполной хвостовой строкой в `pending`, `lastNChars` для контекста «В чат»; тест-раннера в web/ нет, модуль чистый ради будущих тестов); фильтр-подстрока без учёта регистра по `useMemo`; «В чат» — `agentRequest.mode='send'` («Объясни этот вывод лога <путь> (сервер <имя>): ```хвост ≤4 КБ```» — режим 'explain' говорил бы «вывод терминала», для лога это враньё; вызывающий при этом закрывает модалку просмотрщика — панель агента раскрывается под ней); автоскролл выключается ручным скроллом >40 px от дна и переармируется возвратом к дну, чекбокс отражает; статусы «подключено…»/«остановлено»/текст ошибки + «Переподключиться» (`retry++`) — обрыв после SSH-реконнекта менеджера не возрождает стрим сам (то же честное поведение, что у туннелей). FilesPage: кнопка 👁 «Смотреть хвост (tail -F)» у файлов (не директорий; симлинки можно — серверный stat следует по ссылке) → модалка с LogViewer и «★ Закрепить / ☆ Открепить» в тулбаре; закреплённые пути — ряд чипов `.log-chips` под тулбаром, рендерится безусловно (иначе «+» недостижим при пустом списке): клик — просмотрщик, ✕ — открепить, «+» — модалка добавления пути с клиентской проверкой «начинается с /» (при серверном отказе модалка остаётся открытой); FilesPage теперь получает `visible`/`onAskAgent`/`onProfilesChanged` (после пина App перечитывает профили тем же `loadProfiles`, что и ProfileModal).

Алерты по порогам (эпик 20) — клиентская часть: правила вычисляет сервер (`GET /api/alerts`, см. ниже), во `web/` только stateful-клей. Модуль `src/alerts.ts` (чистый, без React): настройки `AlertsSettings {enabled, disk, mem, load, notify}` в localStorage `sc-alerts` (толерантное чтение по полям с клампом в диапазоны), `alertKey` = `profileId:kind:subject`, дельты снятия `ALERT_CLEAR_DELTA` (`server-down`: 0, disk/memory: 5, load: 0.5) и `mergeAlertStates(prev, rules, now)` — переходы состояний: новое активное правило → `fired` (`since: now`); держащееся (активное или `value > threshold − дельта`) — обновляется без сброса `since` (сервер заполняет `message` всегда — текст несёт текущую цифру, алерт в зоне гистерезиса не показывает устаревшее значение); снявшееся (значение упало ниже порога минус дельта) и пропавшее из ответа (профиль удалён, диск отмонтирован, load без ядер) → `resolved` молча — вселенная состояний определяется ответом. Гистерезис на клиенте, а не на сервере: тест-раннер есть только в `server/`, а серверная `evaluateAlertRules` остаётся чистой функцией. `App.tsx`: эффект статус-точек расширен (не дублирован) — один тик = `Promise.allSettled([fetchOverview(), fetchAlerts(settings)?])`, параллельность обязательна (`/api/alerts` должен прийти на сервер, пока жив кэш overview 4 с — последовательный вызов после медленного зонда мёртвого сервера порождал бы второй опрос SSH); deps эффекта `[authed, pageVisible, alertsSettings.enabled]`, пороги читаются из `alertsSettingsRef` (обновляется при сохранении) — изменение числа в модалке не пересоздаёт таймер; в скрытой вкладке опрос продолжается только при включённых и алертах, и браузерных уведомлениях — единственный сценарий, где фоновый опрос что-то даёт (уведомления по умолчанию выключены, колокольчик в скрытой вкладке не видно — иначе опрос даром дёргал бы SSH-зонды круглосуточно); браузер троттлит скрытые таймеры до ~1/мин — честный ритм фоновой проверки. Ref `syncedOnce` — первая успешная синхронизация тихая (F5 не спамит уведомлениями); сохранение настроек и logout — тихий re-baseline (очистка `activeAlertsRef` + сброс `syncedOnce` — иначе поднятие порога не снимало бы алерт, а гистерезис держал бы его по старому порогу). Отказ запроса алертов — прежний набор без изменений. Браузерные уведомления — только на `fired` после первой синхронизации, при `settings.notify && Notification.permission === 'granted' && document.hidden`; `tag: alertKey` даёт браузерную дедупликацию, `onclick` фокусирует окно и открывает «Обзор» профиля. UI: `components/AlertsBell.tsx` — колокольчик в `.sidebar-head` (новый flex-контейнер вокруг `.logo`), бейдж-счётчик (красный при любом crit, амбер при только warn, при выключенных алертах колокольчик приглушён `.disabled` без бейджа, но остаётся единственным входом в настройки); выпадающая панель (закрытие по клику вне и Escape, паттерн меню «В чат ▾») — список crit-выше-warn, внутри старые выше, элемент = профиль + сообщение + «уже N мин» от `since`, клик — переход на «Обзор»; шестерёнка — модалка настроек (закрытие только кнопками, overlay не закрывает: пороги не теряются случайным кликом): тумблеры «Алерты включены» и «Браузерные уведомления» (разрешение запрашивается по клику на тумблер, не при загрузке; denied → toast и тумблер выключен; API нет — тумблер скрыт с пометкой), числа порогов с валидацией min/max и клампом на сохранении, кнопки «Сохранить» / «Сбросить пороги» / «Отмена»; `requestPermission` обёрнут под legacy-callback API старых Safari. У профиля в сайдбаре — чип `.profile-alert-chip` (`⚠ N`, цвет по максимальной severity, `title` со всеми сообщениями, паттерн размещения `agent-dot`).

Модалка «Управление серверами» (`components/ProfileModal.tsx`) кроме обычной формы имеет режим **«Новый сервер (root + пароль)»** (эпик bootstrap, план — `docs/bootstrap-plan.md`): отдельная кнопка в левой колонке раскрывает свою форму (имя, host, порт 22, пользователь root, пароль, галочка «Запретить вход по паролю после настройки» — вкл по умолчанию, для пользователя ≠ root disabled с подсказкой). Отправка — без живого прогресса (одиночный запрос на десятки секунд): спиннер «Настраивается, это может занять до минуты…», по успеху — итоговый отчёт по шагам (ok/warn/error, warn'ы явно) и выбор созданного профиля (`onProfileCreated` в App); по ошибке — toast + отчёт упавших шагов из тела ответа (`ApiError.body`, для кейса «добавьте профиль вручную» — mono-блок с деталями).

## Архитектура сервера

- `src/auth.ts` — вход по паролю, httpOnly-cookie `sc_session` (24 ч, in-memory), rate-limit 10 попыток / 15 мин на IP (счётчик сбрасывается при успешном входе, протухшие записи чистятся), проверка авторизации для REST и WS.
- `src/profiles.ts` — CRUD профилей в `profiles.json` (zod-валидация, атомарная запись через tmp+rename). Поля профиля: `name, host, port, username, authType (key|password), keyPath, keyPassphrase, password, dockerCommand (по умолчанию docker), note, logPaths?` (закреплённые пути логов эпика 14 — до 50 абсолютных путей; `normalizeLogPaths`: trim/дедуп, не-абсолютный или `..` → ошибка; прогоняется на **каждом** входе — create, update, `PUT /log-paths`, импорт бэкапа (при импорте на этапе валидации, до первой записи — «всё или ничего» не нарушается)). Путь к ключу — путь внутри контейнера (`/keys/...`); `keyPassphrase` — passphrase зашифрованного ключа (опционально, пробрасывается в ssh2). При update непереданный секрет (`password`/`keyPath`/`keyPassphrase`) сохраняется из существующего профиля; при смене `authType` новый секрет обязателен; `logPaths` обновляется так же частично (ProfileModal про поле не знает — пины не затираются), а замена списка — отдельной `updateProfileLogPaths(id, paths)` без закрытия SSH-подключения (полный update рвёт соединение и оборвал бы открытый tail-стрим). Битый JSON хранилища переименовывается в `*.corrupt-<timestamp>`, а persist отказывается перезаписывать файл до рестарта — молчаливого затирания нет (то же в `ai/dialogues.ts`).
- `src/ssh/manager.ts` — постоянные SSH-подключения на профиль (кэш в памяти, авто-переподключение по `close`; параллельные `getClient` делят один connect, при ошибке подключения клиент закрывается и запись удаляется): `exec` (timeout 60 c, лимит вывода 2 МБ; опциональный `stdin` — пишется в канал с EOF, используется для подачи пароля в `sudo -S`), `execStream` (для `docker logs -f` и `tail -F`; `close()` до получения канала закрывает канал сразу после его получения; `handle.code` создаётся сразу при вызове и резолвится на **всех** терминальных путях — ошибка `client.exec`, `close()` до открытия канала, отказ `getClient`, `close` канала с exit code, `error` канала; ошибочные пути дают `null`, промис не висит. До этой гарантии follow-режим docker-логов отдавал пустое тело — потребитель читал `handle.code` синхронно и вешал `.then` на зарезолвленную заглушку. Чанки декодируются через `StringDecoder` на канал — многобайтовый UTF-8, разрезанный границей буферов, не превращается в `�`), `execRawChannel` (сырой канал: stdout-стрим + stdin + exit code, для tar-передач файлов), `openShell` (PTY), `getSftp`/`withSftp`.
- `src/ssh/sftp.ts` — promise-обёртки над callback-API SFTP (`readdir, stat, readFile, writeFile, mkdir, rmdir, unlink, rename, chmod, readRange` — диапазон байт `[start, end]` через read stream, для снифа бинарности без чтения всего файла). Всегда использовать их, а не сырые callback-методы.
- `src/services/file-tail.ts` — живой просмотр логов (эпик 14): сборка команд `tail -n N -- shq(path)` / `tail -n N -F --` (`-F` переживает ротацию, `--` — имена с ведущим дефисом), `clampTailLines` (1..5000), `assertNotDirectory`, `looksBinary` (NUL в первых 512 байтах), `precheckTailable` — stat + сниф бинарности по SFTP **до** `flushHeaders` (отказ — обычная JSON-ошибка; заодно закрывает вечный пустой стрим: `tail -F` на отсутствующем файле молча ждёт его появления).
- `src/services/docker.ts` — docker CLI по SSH: команда собирается из `dockerCommand` профиля + экранированных аргументов (`shq`); `parseDockerJsonOutput` понимает NDJSON, JSON-массив и одиночный объект. Команда контейнера в `run` (`runContainerArgs`) оборачивается в `sh -c <shq(command)>` — многословная команда трактуется как shell-строка, а не имя бинаря. Compose поддерживается только v2 (плагин `docker compose`; standalone v1 отклоняется с понятной ошибкой), детект кэшируется на профиль.
- `src/services/metrics.ts` + `src/routes/metrics.ts` — метрики сервера для вкладки «Обзор» (`GET /api/metrics?profileId=`): CPU/mem/disk/uptime/load по SSH, кэш снимка 2 с на профиль.
- `src/services/metrics-history.ts` + `src/routes/metrics-history.ts` — история нагрузки для графиков (сэмпл — лёгкий срез снимка: `t, cpu, memPct, memUsedBytes, memTotalBytes, load1`): in-memory `Map<profileId, HistorySample[]>` без персистентности (после рестарта копится заново). Пишется хуком внутри `collectMetrics` — собственный опрос не нужен, историю кормят запросы `/api/metrics` и `/api/overview` (сайдбар опрашивает каждые 10 с при открытом UI); дедуп по timestamp (кэш снимка возвращает тот же промис) и минимальный гэп 2 с, лимиты 4320 сэмплов на профиль и 24 ч возраста (возраст проверяется и при записи, и при отдаче по wall clock — пока профиль недоступен и новых сэмплов нет, история всё равно стареет). Чистые функции `toSample`/`shouldAppend`/`trimSamples`/`decimate`; `clearHistory` вызывается при удалении профиля. Маршрут: `GET /api/metrics-history?profileId=` — `{timestamp, samples}` (≤360 точек, «Обзор»), без profileId — `{timestamp, profiles: [{id, samples}]}` (≤120 точек на профиль, спарклайны «Серверов»).
- `src/services/ports.ts` + `src/routes/ports.ts` — прослушиваемые порты для вкладки «Порты» (`GET /api/ports?profileId=`): `ss -tulpn` по SSH (фолбэк `netstat -tulpn`), чистый парсер `parseListeners` (определяет формат по строке, вычисляет scope public/loopback/interface), кэш 2 с на профиль. Без root имена чужих процессов недоступны — колонка процесса пустая. `src/services/container-ports.ts` — порты docker-контейнеров: `docker ps` + батч-`docker inspect`, парсинг `NetworkSettings.Ports` (runtime-биндинги, не строковый `Ports` из `docker ps`), кэш 2 с. Роут собирает хостовые и контейнерные порты параллельно (`Promise.all` + `.catch(() => null)` на контейнерной ветке); docker недоступен → поля `containers` нет (деградация); хостовые слушатели матчатся с опубликованными контейнерными портами по `(proto, hostPort, hostIp)` с wildcard для `0.0.0.0`/`::` — аннотация `container: {id, name}` закрывает дыру «безымянный docker-proxy без root».
- `src/services/cron.ts` + `src/routes/cron.ts` — cron-задачи для вкладки «Cron» (`GET /api/cron?profileId=`): пользовательский `crontab -l` (отсутствие — `null`, не ошибка), `/etc/crontab` и `/etc/cron.d/*` одной командой с маркерами `=== <файл>`; чистые функции `parseCrontab` (system-формат с колонкой user, `@keywords`, env-строки и комментарии отдельно, закомментированные записи → `enabled:false`, у записи `index` = номер строки), `describeSchedule` (русские описания частых расписаний), `validateCronFields`, `applyCrontabOp` (add/update/delete/toggle с защитой от гонки через `expectedRaw` → `CronConflictError`/409); кэш 2 с на профиль (ключ — `profileId` или `profileId::user`). Мутации (`mutateUserCrontab`) только пользовательского crontab: чтение заново без кэша → `applyCrontabOp` → запись целиком через `crontab -` (stdin канала). Системные файлы — read-only. Просмотр чужих персональных crontab — только root: `fetchCronUsers` (spool-каталоги с фолбэком по дистрибутиву + текущий юзер), чтение `crontab -u <user> -l` (фолбэк `cat` spool-файла), имя валидируется `isValidCronUser`; в снапшоте `currentUser`/`editable`, чужие — read-only, `user`-параметр не меняет кэш.
- `src/services/systemd.ts` + `src/routes/services.ts` — службы systemd для вкладки «Службы» (эпик 13). Снимок (`GET /api/services?profileId=`) — один exec с маркерами и `2>&1`/`LC_ALL=C`: `systemctl --version | head -1`, `list-units --type=service --all --no-pager --plain --no-legend`, `list-unit-files --type=service --no-pager --plain --no-legend`; код возврата игнорируется — решение принимает парсер. Чистые функции: `parseVersionLine` (systemd или `not found`), `parseListUnits` (колонки `UNIT LOAD ACTIVE SUB DESCRIPTION`, `-` → null, описание — всё после 4-й колонки, `--plain` снимает bullet `●`), `parseListUnitFiles` (**STATE — всегда второе поле `fields[1]`**: с systemd ≥ 245 колонок три — `UNIT FILE / STATE / PRESET`, PRESET игнорируется), `mergeUnits` (имя из любого списка, enabled из unit-files — отсутствует → null у transient-юнитов), `parseSnapshot` (детект не-systemd: `not found` → «systemctl не найден…», `has not been booted with systemd` → «не является PID 1 (контейнер?)», ошибка флага в начале секции `Unknown option`/`Invalid option`/`Failed to` → причина с текстом ошибки — иначе парсер молча отбросил бы её как мусор); кэш 2 с на профиль + `invalidateServicesCache` после мутации. Деталь (`GET /api/services/:unit?profileId=`) — `systemctl status --no-pager -n 0` + `systemctl show -p …` (11 полей: MainPID, ActiveState, SubState, UnitFileState, FragmentPath, Restart, NRestarts, Result, MemoryCurrent, TasksCurrent, ActiveEnterTimestamp) через маркер `@@SHOW@@`; `parseShowOutput` — строки `KEY=VALUE`, первое вхождение выигрывает; код возврата статуса (3 = inactive, 4 = not-found) — не ошибка. Действия (`POST /api/services/:unit/action`, whitelist start|stop|restart|reload|enable|disable|reset-failed; reset-failed сверх роадмапа — осознанно) — `runServiceAction`: без sudo `systemctl <action> -- <unit>` (unit через `shq`, `--` — защита от опций), при sudo-needed — ретрай с sudo **прямой формой `sudo -S -p '' -- systemctl <action> -- <unit>` без `sh -c`** (пароль первой строкой stdin, не в argv/логах, живёт в памяти одного запроса; ретрай безопасен — отказ прав означает, что мутация не началась). Классификация `classifyActionFailure`: polkit-формулировки `Interactive authentication required`/`Authentication is required` и безpolkit-ные `Access denied`/`Operation refused`/`Permission denied` → sudo-needed; masked/not-found/job-failed → 400 с текстом systemd как есть (состояние сервиса, не транспорт); прочее → 502. Зонд пароля `sudo -S -p '' -- true` (`classifySudoProbe`): `Sorry, try again.` → 400 «Неверный sudo-пароль», `is not in the sudoers file`/`not allowed to execute` → 400 «нет прав sudo», `not found` → 400 «sudo не установлен». Журнал (`GET /api/services/:unit/logs?profileId=&tail=&follow=1`) — `journalctl -u <unit> --no-pager -n <tail> [-f]`, tail 1..5000 дефолт 500: разовый — exec с таймаутом 30 с и честной пометкой «… (вывод обрезан по лимиту 2 МБ)» при упоре в лимит exec; follow — исправленный `execStream` + chunked `text/plain; charset=utf-8` + `Cache-Control: no-cache` + `req.on('close')` → `handle.close()`, через лимитер и гейт (см. ниже), сверх лимита — 429. **Sudo для журнала в v1 не делается**, отказ маскируется под пустой вывод с кодом 0 — UI показывает подсказку про группы `adm`/`systemd-journal`.
- `src/services/processes.ts` + `src/routes/processes.ts` — действия над процессами из «Обзора» (эпик 17): `POST /api/processes/:pid/signal` `{signal: TERM|KILL|HUP, sudoPassword?}` и `POST /api/processes/:pid/renice` `{nice: −20..19, sudoPassword?}`. Чистые функции: `parsePid` (каноничная строка цифр без ведущих нулей/экспоненты, значение 2..4194304 — `0`, `1` и отрицательные запрещены: `kill -TERM -1` бьёт по группам/широковещанием), билдеры `killCommand`/`sudoKillCommand`/`reniceCommand`/`sudoReniceCommand` (без `shq` — сигнал из enum, pid валидирован, строковых аргументов нет; `kill -<sig> <pid>` **без `--`**: builtin login-shell по-разному понимает `--`, а pid опцией быть не может; sudo-форма исполняет `/bin/kill`/`/bin/renice` напрямую), `classifyProcessActionFailure` (ok / sudo-needed `Operation not permitted`|`Permission denied` — обе формулировки, util-linux и builtin bash / gone `No such process` / no-tool `command not found` — BusyBox без `renice` → 400, а не 502 «Сервер недоступен» / transport). Исполнители `runProcessSignal`/`runProcessRenice` — общий поток `withSudoRetry` (паттерн `runServiceAction`): проба без sudo → sudo-needed без пароля → 400 «укажите sudo-пароль»; с паролем → зонд из общего **`src/services/sudo.ts`** (`probeSudo` — вынесен из systemd.ts при эпике 17, systemd.ts реэкспортирует `sudoProbeCommand`/`classifySudoProbe`/`SudoProbeResult` — публичный API модуля не менялся; его же ждёт эпик 19) → явные 400 (неверный пароль/нет прав sudo/sudo не установлен) и 502 → sudo-ретрай; gone → 400 «Процесс больше не существует»; транспорт → 502. Таймаут — дефолт exec 60 с (kill/renice мгновенны, отдельный ACTION_TIMEOUT не нужен). После успешной мутации — `invalidateMetricsCache(profile.id)` (новый экспорт `services/metrics.ts`, паттерн `invalidateServicesCache`) — немедленный refetch «Обзора» и сайдбара (`/api/overview`) без устаревшего кэша 2 с. Инструмент агента не заводится: `kill`/`pkill`/`killall` в deny-листе `guard.ts` осознанно, путь агента — мутating `exec` с approve.
- `src/services/packages.ts` + `src/routes/packages.ts` — обновления пакетов для вкладки «Обзор» (эпик 19). `GET /api/packages/updates?profileId=` — read-only снимок (кэш 60 с на профиль, паттерн `collectMetrics`): детект менеджера одним exec (`command -v apt-get || command -v dnf || command -v yum || command -v apk`), список обновлений + признаки рестарта одним exec с маркерами (`@@LIST_CODE@@` — код списка, т.к. код всей строки принадлежит последней части; `@@REBOOT@@` — apt: маркер печатается только при существующем `/var/run/reboot-required`, dnf/yum: `needs-restarting -r` с `@@RESTART_CODE@@`; apk — конвенции нет). Чистые функции: `parsePmDetection`, `parseAptList` (name/suite версия arch `[upgradable from: cur]`), `parseDnfCheckUpdate` (`name.arch version repo` — текущей версии нет, колонка «— → версия»), `parseApkVersionLt` (`name-version < version`, многострочный перенос), `isUpdatesExitCode` (**код 100 у dnf/yum = есть обновления, не ошибка**), `parseListCode`, `parseRebootSection`, `rebootCheckSuffix`, `snapshotCommand`, `dedupeByName`. Возраст индекса apt (`/var/lib/apt/periodic/update-success-stamp`) — через SFTP-stat, ошибка stat → тихий `null`; `apt-get update` не запускается (мутирует индексы и требует прав). `POST /api/packages/apply?profileId=` `{sudoPassword?}` — мутация: свежий детект менеджера (не из кэша) → sudo-зонд `probeSudo` (`services/sudo.ts`) **до открытия канала** (неверный пароль / не в sudoers / sudo не установлен → 400, `other` → 502) → слот общего лимитера follow-стримов (`stream-limits.ts`, 429) → стрим `execStream` (`buildApplyCommand` — прямая sudo-форма `sudo -S -p '' -- <cmd>` без `sh -c`; `env DEBIAN_FRONTEND=noninteractive` для apt; пароль первой строкой stdin канала) через `createChunkGate`, оба потока в одно тело; `req.on('close')` → `handle.close()`, на settle — `invalidatePackagesCache`. Инструмент агента для пакетов не заводится (обновления покрыты секцией `updates` аудита).
- `src/services/sudo.ts` — общий sudo-зонд (эпик 19, прецедент выноса `stream-limits` в эпике 14): `sudoProbeCommand()` (`sudo -S -p '' -- true`), `classifySudoProbe` (ok / wrong-password / not-in-sudoers / sudo-not-found / other), `probeSudo(profile, password)` — exec со `stdin: <пароль>\n`. Потребители: действия systemd (`systemd.ts` — импорт функций, exec-инъекция для тестов осталась там), действия над процессами (эпик 17), применение пакетов (эпик 19, зонд до стрима → явный 400). `security-audit.ts` не трогаем — ему нужен только код 0.
- `src/services/stream-limits.ts` + `src/services/chunk-gate.ts` — общие механики follow-стримов (эпик 13, по плану эпика 14). `stream-limits.ts` — лимитер активных follow-стримов **на профиль, не на подсистему** (один SSH-канал на профиль, `MaxSessions 10` у OpenSSH): `acquireFollowSlot`/`releaseFollowSlot` (идемпотентно), лимит 3, сверх — 429; используют `/api/docker/containers/:id/logs?stream=1`, `/api/services/:unit/logs?follow=1` и `/api/files/tail?follow=1` (эпик 14); отказ — 429 с общим текстом «Достигнут лимит одновременных журналов…». - `src/services/disk-usage.ts` + `src/routes/disk-usage.ts` — «Что занимает» (эпик 16): проваливание по каталогам с размерами + топ файлов. `GET /api/disk-usage?profileId=&path=` — `du -x -d 1 -k -- <shq(path)>` (`-k`, а не `-B1` из roadmap: BusyBox не знает `-B`, как `df -P -k`; парсер умножает на 1024), `-x` не выпускает обход за пределы ФС. stderr не глушится (отклонение от roadmap): `countUnreadable` считает строки отказа доступа → `incomplete: {unreadable}` — «доступно не всё» честно, а не молча заниженные цифры. `parseDuKb` ищет суммарную строку **по совпадению пути** (GNU и BusyBox печатают каталог последней строкой post-order, но на порядок не полагаемся); отсутствие суммарной строки (`totalKb: null`) — не ошибка, а признак обрезанного вывода 2 МБ: `toDuSnapshot` деградирует в `totalBytes = Σ children`, `truncated: true` (ошибка только если нет и детей). `directBytes = max(0, total − Σ детей)` — размер файлов прямо в каталоге (du их в `-d 1` не печатает; UI показывает отдельной строкой). Кэш 2 с на `(profileId, path)` только для du (самая тяжёлая команда), ошибочный промис удаляется. `GET /api/disk-usage/files?profileId=&path=&limit=` (1..500, дефолт 100) — `find -xdev -type f -printf '%s\t%p\n' | sort -rn | head`; фолбэк `-exec stat -c '%s<литеральный таб>%n' {} +` при `needsStatFallback` по stderr (`unrecognized|unknown primary|invalid option|not supported` — формулировки GNU/BusyBox/BSD разные) или пустом stdout с непустым stderr **без строк отказа доступа** (код пайплайна принадлежит head — провал find по коду не виден; но штатный пустой каталог с `Permission denied` не должен гонять второй обход вхолостую); если и stat-вариант не поддержан — режим «Файлы» деградирует с пояснением, каталоги остаются. Валидация пути — свои `normalizeDiskPath`/`assertNavigablePath` (`assertSafePath` запрещает `/`, а точка монтирования — законный корень). Предпроверка `precheckNavigableDir`: `getSftp` вне try (обрыв соединения → 502), `stat` в try (нет пути/прав → 400) — раньше весь `withSftp` заворачивался в 400, и упавший SSH выглядел как «Путь недоступен». Таймаут du/find (`runDuExec`) → 400 «Превышено время ожидания (60 с)…», а не 502 «Сервер недоступен» (сервер в порядке — это команда не уложилась; заодно чинит деградированную строку агента). Исполнители принимают `deps {execFn?, precheckFn?, skipPrecheck?}` (паттерн systemd.ts) — тесты мокают exec, агент делает одну предпроверку на оба вызова. Ошибки маршрута: 404 — нет профиля, 400 — пользовательские причины (`DiskUsageError`: путь, права, утилиты), 502 — только транспорт (exec reject, обрыв соединения), разделение как в `routes/metrics.ts`. Ответ снимка: `{timestamp, path, totalBytes, directBytes, children: [{name, path, bytes, pctOfParent}], incomplete?, truncated?}`. Инструмент агента `disk_usage {path?, limit?, server?}` — read-only, команды собирает сервис (минуя deny-лист `exec_readonly`, как `security_audit`); каталоги и файлы — `Promise.allSettled` после одной общей предпроверки, файлы при отказе деградируют в строку; `clampAgentLimit` (1..50, дефолт 10); формат отчёта — `formatAgentDiskUsage` (размер, топ подкаталогов с долями, топ файлов, пометки `incomplete`/`truncated`).

Там же `GET /api/terminal/sessions?profileId=` (эпик 15) — живые терминальные сессии профиля `{sessions: [{tabId, container, containerName}], limit}` для восстановления вкладок после F5/чистки localStorage (лимит — для дизейбла «+» в UI).
- `src/services/keys.ts` + `src/routes/keys.ts` — `GET /api/keys` (список файлов в `KEYS_DIR` для выпадающего списка в форме) и `POST /api/keys?name=&overwrite=1` (импорт ключа из UI: raw body ≤ 64 КБ, проверка PEM/OpenSSH-заголовка, санитизация имени `[A-Za-z0-9._-]`, атомарная запись с правами 0600, без `overwrite=1` существующий файл не затирается — 409). Чтение содержимого ключей наружу не отдаётся — только имена.
- `src/services/profile-transfer.ts` — перенос профилей между машинами: `POST /api/profiles/export` (файл бэкапа; секреты — только при `includeSecrets=true`, с `passphrase` шифруется scrypt + AES-256-GCM; ключи вкладываются только из `KEYS_DIR` и только вместе с секретами) и `POST /api/profiles/import` (`{backup, passphrase?}`; всё валидируется до первой записи, конфликты имён — суффикс « (2)», существующие ключи не затираются, `keyPath` перепривязывается к текущему `KEYS_DIR`, профили без секрета попадают в `needSecrets` — секрет задаётся вручную через `importProfile` в `profiles.ts`, который не требует секрет при создании). Формат бэкапа версионируется (`app/version/encrypted`).
- `src/services/bootstrap.ts` — «Новый сервер (root + пароль)» (план — `docs/bootstrap-plan.md`): оркестрация `bootstrapServer(input, deps)` с инъекцией подключений/сохранения ключа/создания профиля (моки в тестах). Порядок: генерация отдельного ed25519-ключа (node:crypto не даёт формата, который читает ssh2 — свой минимальный энкодер OpenSSH-формата, проверяется `utils.parseKey` при генерации; файл `keys/<sanitizedName>.ed25519`, санитизация как у memory/, коллизия — числовой суффикс, права 0600; комментарий pubkey `ssh-commander@<имя профиля>`) → подключение по паролю → идемпотентная установка pubkey (`grep -F` по телу без комментария, append, SELinux-страховка `restorecon -R ~/.ssh`) → верификация входа **отдельным новым** подключением ключом → hardening sshd (галочка, только root): детект поддерживаемых директив по `sshd -T` на немодифицированном конфиге (baseline-валидность; OpenSSH < 8.7 без `KbdInteractiveAuthentication` → пишем `ChallengeResponseAuthentication`), drop-in `/etc/ssh/sshd_config.d/00-ssh-commander.conf` (раннее имя — «первое вхождение побеждает», перекрывает cloud-init) либо fallback: бэкап основного конфига + замена активных директив + вставка отсутствующих до первого `Match`; reload (`systemctl reload sshd/ssh || service ssh/sshd reload`, в контейнерах — SIGHUP старейшему sshd) только после зелёного `sshd -t`; контроль по факту: `sshd -T` (с `-C` при Match-блоках), контрольный вход ключом после reload, password-попытка с ожиданием отказа (пароль всё ещё пускает → честный warn) → `createProfile` (authType=key). Откат: любая ошибка после первой правки конфига → удалить drop-in / восстановить бэкап + reload; исполнитель — живая password-сессия, при обрыве — key-сессия (вход ключом верифицирован до hardening), в крайнем случае свежее key-подключение. Провал до создания профиля → удалить локальный файл ключа + убрать строку из `authorized_keys` best-effort (только через живые сессии). Отдельный кейс «hardening ок, а `createProfile` упал» — ключ сохраняется, ошибка содержит путь и подсказку «добавьте профиль вручную», откат hardening не делается. Пароль живёт только в памяти запроса: не persist'ится, не логируется, в сообщения об ошибках не подставляется. Подключения — прямые ssh2-клиенты (профиля нет, менеджер не нужен), readyTimeout 30 c, close в `finally`. Чистые функции под тесты: билдеры команд (`buildInstallKeyCommand`, `buildDropinWriteCommand`, fallback/rollback), `rewriteSshdConfig`, `parseSshdT`, `detectSupportedDirectives`, `failedEffectiveDirectives`, `buildKeyFileName`, `mapConnectError`.
- `src/ws/terminal.ts` — терминальные сессии: буфер ввода до готовности shell, переживают перезагрузку вкладки (60 c после последнего отсоединения — grace). С эпиком 15 сессий на профиль несколько: ключ `profileId::<container|host>::<tabId>`, где `tabId` — стабильный id вкладки из query (0..9999, отсутствие — дефолт 0 для бесшовного деплоя старого клиента, невалидный — `close(1008)`; чистая функция `parseTabId`), `containerName` — только отображение (≤200 символов, в ключ и shell-команду не попадает). Лимит `MAX_TERMINAL_SESSIONS_PER_PROFILE = 4` живых сессий на профиль (бюджет `MaxSessions 10`: SFTP + follow-стримы + транзитные exec'и); живыми считаются записи с shell или в spawn, повторный attach к существующей сессии лимит не проходит; сверх лимита — error-фрейм с текстом + `close(1013)`, сессия не создаётся. Выход из shell (`exit`) **и отказ spawn** (канал не открылся) удаляют запись из реестра сразу (`sessions.delete` в close-обработчике канала и в catch spawn): реанимировать нечего, а с ключом по вкладке мапа иначе копит призраки, всплывающие в `/api/terminal/sessions`; клиент по close/error-фрейму переподключается тем же tabId и получает свежую запись. `listTerminalSessions(profileId)` отдаёт живые записи для REST. Контейнерная сессия — тот же PTY с `exec docker … sh -c 'exec bash || exec sh'` внутри. WS-сообщение `restart` закрывает shell и SSH-подключение и открывает новый shell (применяются новые группы/права), `close` — явный destroy (кнопка ✕ вкладки).
- `src/ai/` — агент: `client.ts` (Chat Completions, streaming SSE, аккумуляция tool_calls, таймаут соединения 120 c; захват `usage` — см. раздел «Учёт расходов AI»), `tools.ts` (определения инструментов + `READ_ONLY_TOOLS` + гейтинг `getToolDefs` — web_search объявляется модели только при настроенном поиске; во всех SSH-инструментах и инструментах памяти — необязательный параметр `server` (имя профиля, по умолчанию домашний сервер диалога)), `guard.ts` (deny-лист read-only команд), `agent.ts` (цикл, подтверждения, лимит шагов, системный промпт; мульти-серверная сессия — см. ниже; запись usage и WS-событие — см. раздел «Учёт расходов AI»; вырезание маркера подсказки — см. раздел «Подсказка вероятного ответа»), `plan.ts` (режим планирования: `PLAN_MODE_INSTRUCTION`, `toolsForRequest`, `buildPlanRequestMessages`), `messages.ts` (санитизация истории сообщений), `memory.ts` (пер-профильная память MEMORY.md), `pricing.ts` + `usage.ts` (учёт расходов AI — см. ниже), `web-search.ts` (веб-поиск для агента — см. ниже), `suggest.ts` (маркер подсказки `[[SUGGEST]]` — см. раздел «Подсказка вероятного ответа»).
- `src/ai/dialogues.ts` — хранение диалогов агента в `DATA_DIR/ai-dialogues.json` (zod-валидация, атомарная запись tmp+rename, кэш в памяти). Мульти-серверность: `extraProfileIds?: string[]` в схеме (опционально, старые JSON валидны), `attachProfileToDialogue`/`detachProfileFromDialogue` (домашний `profileId` отцепить нельзя), `extraProfileIds` пробрасывается в сводку `listDialogues`.
- `src/ai/web-search.ts` — веб-поиск для инструмента агента `web_search`: Anthropic-совместимый endpoint DeepSeek (`AI_SEARCH_API_BASE`, по умолчанию пусто — фича выключена) с серверным инструментом `web_search_20260209` (`max_uses` 3 на вызов), ключ общий с `AI_API_KEY`, модель — `AI_SEARCH_MODEL` (по умолчанию `deepseek-v4-flash`). Чистые функции: `buildSearchBody` (тело Messages-запроса), `parseSearchResponse` (текст + выполненные запросы + источники; `encrypted_content` и thinking-блоки игнорируются), `formatSearchOutput`, `sanitizeQuery` (лимит 400 символов), `isSearchConfigured`. `searchWeb` — fetch с таймаутом 90 с, никогда не бросает (ошибки возвращаются текстом); при успешном ответе пробрасывает `usage` (input/output токены + `server_tool_use.web_search_requests`). Основной клиент агента (OpenAI-формат) не меняется — поиск это отдельный read-only инструмент с собственным HTTP-вызовом; в `agent.ts` лимит 10 вызовов `web_search` за запуск цикла (сброс в начале `runLoop`), без конфигурации инструмент модели не объявляется вовсе.
- `src/routes/ai.ts` — REST для диалогов: `GET/POST /api/ai/dialogues`, `GET/DELETE /api/ai/dialogues/:id` (summaries и деталь обогащаются `usage` — join с `usageTotalsByDialogue()` на уровне роута), `GET /api/ai/usage?days=30|all` (отчёт по расходам, см. раздел «Учёт расходов AI»).

## Учёт расходов AI (эпик 12, план — `docs/ai-costs-plan.md`)

Агент гоняет десятки платных запросов за диалог; оба API (чат и веб-поиск)
уже возвращают `usage` с токенами. Поток: захват в клиенте → тарификация →
журнал → enrichment/WS → UI (бейдж в панели агента + страница «ИИ-расходы»).

- **Захват (`client.ts`).** В тело запроса добавлен `stream_options:
  { include_usage: true }`; в SSE-цикле `json.usage` читается **до** проверки
  `choices` (финальный usage-чанк приходит с пустым `choices` и раньше
  пропускался строкой `if (!delta) continue`); non-stream fallback читает
  верхнеуровневый `usage`. `streamChatCompletion` возвращает
  `{ message, usage?: TokenUsage }` — usage **не** кладётся в `ChatMessage`,
  иначе попал бы в `this.messages` и в persisted-диалог. `TokenUsage`:
  `promptTokens/cachedTokens/completionTokens/reasoningTokens` (все optional;
  маппинг `prompt_tokens` / `prompt_tokens_details.cached_tokens` /
  `completion_tokens` / `completion_tokens_details.reasoning_tokens`; кэш-хиты
  DeepSeek — `prompt_cache_hit_tokens` — fallback для cachedTokens). Числа —
  только конечные ≥ 0, иначе поле опускается; инварианты `cached ⊂ prompt`
  и `reasoning ⊂ completion` держатся клампом на захвате (формула цен
  вычитает кэш — в минус уходить не должна). `web-search.ts`: usage
  Anthropic-ответа (`input_tokens`/`output_tokens`/
  `server_tool_use.web_search_requests`) пробрасывается в `searchWeb`.
- **Цены (`pricing.ts`).** `DEFAULT_PRICES` — таблица популярных моделей
  (USD за 1M токенов: `input`, `cachedInput?`, `output`, опционально
  `webSearchPerRequestUsd`): gpt-4.1/-mini/-nano, gpt-4o/-mini,
  deepseek-chat/-reasoner и DeepSeek V4 — deepseek-v4-flash
  (0.22 / 0.007 / 0.66) и deepseek-v4-pro (0.66 / 0.022 / 1.98), off-peak
  тарифы (пиковые часы 01:00–04:00 и 06:00–10:00 UTC в 2 раза дороже;
  точность — оверрайдом). Модель без уверенной цены в таблицу не вносится —
  честный unpriced, закрывается оверрайдом. `loadPrices()` — дефолты + мерж
  `data/ai-prices.json`
  (`{ "models": { "<model>": ModelPrice } }`, запись файла полностью
  заменяет дефолтную для модели; битый/невалидный файл — warn + дефолты,
  **без** corrupt-guard: это справочник, не пользовательские данные).
  Формула `computeCostUsd(model, usage & searchRequests)`:
  `(prompt − cached)·input + cached·cachedInput + completion·output +
  searchRequests·webSearchPerRequestUsd`; без `cachedInput` кэш — по цене
  `input`; `reasoning` в формулу НЕ входит (уже посчитан в output);
  слагаемое поиска добавляется только при заданном `webSearchPerRequestUsd`
  (тариф Anthropic); без него поиск считается по токенам — так у DeepSeek
  (серверный web_search оплачивается токенами модели поиска, отдельной
  цены за запрос нет); null — только если модели нет в таблице.
- **Журнал (`usage.ts`).** `data/ai-usage.json` — отдельный стор (удаление
  диалога не стирает финансовую историю), канонический паттерн (zod +
  tmp/rename + corrupt-guard). Запись — `{id, ts, profileId, dialogueId,
  kind: 'chat'|'plan'|'web_search', model, promptTokens, cachedTokens,
  completionTokens, reasoningTokens, searchRequests?, costUsd: number|null}`.
  `recordUsage` — append + persist на каждый вызов API (перезапись всего
  файла через tmp+rename — риск «перезапись на вызов» в плане; при росте —
  батчить persist). Стоимость фиксируется в момент вызова: смена цен не
  переписывает историю, токены позволяют пересчитать. Агрегаты:
  `usageTotalsByDialogue()` — `Map<dialogueId, UsageAgg>` для enrichment и
  WS-бейджа; `usageReport(days: number|'all')` — группы по (локальная дата
  сервера `YYYY-MM-DD`, profileId) + итоги; `UsageAgg = {calls, promptTokens,
  cachedTokens, completionTokens, costUsd, unpricedCalls}` — `unpricedCalls`
  (costUsd === null) нужен, чтобы бейдж/отчёт честно показывали неполную
  сумму. Привязка затрат: домашний профиль диалога + дата вызова (решение 6:
  токены мульти-серверного диалога не делятся по серверам).
- **Запись (`agent.ts`).** После каждого успешного `streamChatCompletion` с
  `usage` — `recordUsage({kind: 'chat', ...})`, в `runPlan` — `kind: 'plan'`;
  после `searchWeb` — `kind: 'web_search'` с `searchRequests`. После каждой
  записи — WS-событие `{type:'usage', totals}` (кумулятивные итоги диалога из
  `usageTotalsByDialogue`) — бейдж двигается во время длинных прогонов, а не
  только по `done`. Всё в try/catch: журнал не должен ломать агента
  (как `save()`).
- **API (`routes/ai.ts`).** summaries и деталь диалога обогащаются
  `usage: UsageAgg | null` (join на уровне роута — сторы друг о друге не
  знают). `GET /api/ai/usage?days=30` (дефолт 30; `days=all` — всё;
  zod-валидация: целое 1–3650 или `all`) →
  `{profiles: [{id, name}], days: [{date, byProfile: {<profileId>: Agg},
  total: Agg}], totals: Agg}`; дни desc, пустые дни не включаются; имена
  профилей — join с `profiles.ts`, удалённый — `<id> (удалён)`.
- **Web.** `api.ts`: `fetchAiUsage(days)`, `formatUsd` (< $1 — 4 знака, иначе
  2). `AgentPage.tsx`: бейдж `≈ $0.0423` в тулбаре рядом со `status-text`
  (tooltip — вызовы и токены вход/выход/кэш; при `unpricedCalls > 0` —
  пометка «неполная сумма»); обновление из summary (`refreshDialogues` на
  `done`/`error`) + живое по WS `usage` (live-значение имеет приоритет,
  сбрасывается при смене диалога); в выпадающем «История» у каждого диалога
  стоимость рядом с датой. `AiCostsPage.tsx` — глобальная страница (кнопка
  «ИИ-расходы» в сайдбаре под «Серверами», слот в `App.tsx` вне таббара
  профиля, как `ServersPage`): карточки итогов периода (всего, среднее в
  день, запросов), матрица `data-table` (строки — дни desc, колонки —
  профили + «Итого», ячейка `$` с tooltip «запросы и токены», пусто — «—»,
  sticky thead и футер-итоги по колонкам), select периода 7/30/90/всё,
  кнопка «Обновить», polling 60 с при видимости, ошибка — `empty-state` с
  повтором. Стили — существующие классы + минимальные `.cost-badge`,
  `.cost-cards`, `.cost-matrix`.

## Подсказка вероятного ответа агента (план — `docs/agent-suggest-plan.md`)

Агент часто заканчивает ответ вопросом («перезапустить контейнер?»); подсказка
вероятного ответа — плейсхолдер пустого поля ввода, Tab подставляет текст,
Enter отправляет. Реализовано **без дополнительного вызова API**: подсказку
даёт сама модель служебным маркером в конце своего ответа.

- **Источник (`agent.ts`).** Системный промпт обязывает модель: если финальный
  ответ запрашивает решение/выбор пользователя — добавить последней строкой
  `[[SUGGEST]] <краткий вероятный ответ>` (одна фраза до 100 символов на
  русском). Ноль доп. вызовов, `ai-usage.json` не затрагивается. Инструкция
  консервативна (асимметрия в пользу молчания, ревизия 3 плана): подсказка —
  только когда один ответ заведомо вероятен (подтверждение безопасного
  следующего шага, очевидный запрос вроде «покажи логи»); на открытые
  вопросы (нужны данные — имя, домен, путь, число), равнозначные варианты и
  необратимые/рискованные действия модель инструктирована не подсказывать
  (в частности — не подсказывать согласие на необратимое); в сомнении —
  молчит: отсутствие подсказки пользователь не замечает, плохая — подрывает
  доверие.
- **Извлечение (`suggest.ts`).** `extractSuggestion(raw)` — регэксп только
  хвостового маркера `/\n?\[\[SUGGEST\]\][ \t]*([^\n]*)\s*$/` (маркер в
  середине — легитимный текст, не трогается); валидация: одна строка, пробелы
  схлопываются, пустая или длиннее 100 символов → `null` (маркер из контента
  вырезается всегда, даже когда подсказка отброшена). Вырезание — в каждом
  ответе модели (`runLoop`, включая промежуточные ходы с tool_calls, и
  `runPlan`) **до** `this.messages.push` и `save()`: в persisted-диалог и
  контекст следующих ходов маркер не попадает. В режиме планирования
  подсказка не шлётся (точка решения — кнопка «Выполнить» в PlanCard).
- **Событие.** WS `{type:'suggestion', text}` — только на финальном ходе
  `runLoop` (ответ без tool_calls); порядок событий `message` (чистый
  контент) → `suggestion` → `done`.
- **Holdback-фильтр (`createSuggestionTokenFilter`).** Обёртка над `onToken`
  против вспышки маркера в стрим-пузыре (классический stop-sequence приём),
  два режима: префиксный — удерживает суффикс стрима, совпадающий с префиксом
  маркера (если следующий чанк маркер не продолжает — удержанное уходит
  наружу сразу, максимум один чанк задержки; `flush()` отдаёт удержанный
  хвост, напр. одиночный `[` в конце обычного текста); подавление — полный
  маркер глушит всё до конца стрима (за ним по контракту только текст
  подсказки), `flush()` в этом режиме ничего не отдаёт. `flush()` зовётся
  только после успешного стрима — на пути ошибки/останова удержанный хвост
  не важен (финального `message` там нет, потеря косметическая). Non-stream
  fallback (`client.ts`) вспышки не имеет вовсе.
- **Web (`AgentPage.tsx`).** Стейт `suggestion` ставится событием WS и живёт
  до следующего хода: сброс на `running`, в `send()`, при смене диалога, на
  `error`; на `done` — НЕ сбрасывается (агент ждёт ответа). Из
  persisted-диалога не восстанавливается (в `ai-dialogues.json` не
  хранится). Плейсхолдер ``${suggestion} · Tab — подставить``; Tab (без
  модификаторов) при строго пустом поле — `preventDefault()` + подстановка
  текста с курсором в конец; при непустом поле Tab сохраняет нативное
  поведение. Подставленный текст — обычное содержимое поля, правится перед
  отправкой. **Инвариант: автоотправки нет никогда** — Enter всегда нажимает
  пользователь, модель не может «ответить за пользователя».

## REST и WebSocket API

Все маршруты кроме `/api/auth/*` и `/api/health` требуют cookie-сессии.

- `POST /api/auth/login|logout`
- CRUD `/api/profiles`, `POST /api/profiles/test-connection` (разовое SSH-подключение по переданным полям без сохранения профиля; кэш соединений не затрагивается — кнопка «Проверить подключение» в форме), `POST /api/profiles/:id/reconnect` (закрывает SSH-подключение профиля; следующее обращение откроет свежее — применяются новые группы/права), `PUT /api/profiles/:id/log-paths` `{paths}` (замена закреплённых путей логов; SSH-подключение не трогает — полный update оборвал бы открытый tail-стрим), `POST /api/profiles/export` и `POST /api/profiles/import` (перенос профилей между машинами, см. `services/profile-transfer.ts`), `POST /api/profiles/bootstrap` («Новый сервер (root + пароль)»: `{name, host, port, username, password, disablePasswordAuth}` → 201 `{profile, steps: BootstrapStep[]}`; ошибки → `{error, steps}` со статусом из `BootstrapError`; запрос живёт десятки секунд — таймаутов < 120 с в цепочке нет), `GET /api/keys` (список имён), `POST /api/keys?name=&overwrite=1` (импорт ключа из UI, raw body)

- `GET /api/metrics?profileId=` — снимок метрик сервера (вкладка «Обзор»).
- `GET /api/metrics-history[?profileId=]` — история нагрузки: с profileId `{timestamp, samples: HistorySample[]}` (≤360 точек) для графиков «Обзора», без — `{timestamp, profiles: [{id, samples}]}` (≤120 точек на профиль) для спарклайнов «Серверов»; пока истории нет, отдаются пустые массивы.

Поле `containers` отсутствует при недоступном docker (деградация); `container` в хостовых слушателях — аннотация для опубликованных контейнерных портов.

- `GET /api/overview` — сводный снимок по всем профилям (вкладка «Серверы»): `{timestamp, servers: [{id, name, host, port, username, ok, error?, externalIp?, metrics?, docker?: {containersTotal, containersRunning}}]}`.

- «Что занимает» (эпик 16): `GET /api/disk-usage?profileId=&path=` — снимок du одного каталога `{timestamp, path, totalBytes, directBytes, children: [{name, path, bytes, pctOfParent}], incomplete?, truncated?}` (400 — путь/права/утилиты, 502 — транспорт); `GET /api/disk-usage/files?profileId=&path=&limit=` — топ файлов `{timestamp, path, files: [{path, bytes}], incomplete?, truncated}` (`truncated` — файлов ровно limit).
- `GET /api/alerts?disk=&mem=&load=` — состояния правил алертов всех профилей (эпик 20, без profileId — колокольчик глобальный): `{timestamp, thresholds: {diskPercent, memPercent, loadPerCore}, rules: [{profileId, kind: server-down|disk|memory|load, subject?, severity: crit|warn, active, value, threshold, message}]}`. Пороги — query-числа с диапазонами 50–99 / 50–99 / 0.5–16 и дефолтами 90/90/2; невалидное → 400. Поверх кэша overview — новых SSH-вызовов не добавляет.
- `GET /api/terminal/history?profileId=&limit=` — история shell-команд (палитра Ctrl+R в терминале).
- `GET /api/cron?profileId=[&user=]` — cron-задачи (вкладка «Cron»): `{timestamp, username, currentUser, editable, userCrontab: {entries, env, comments, raw} | null, systemCrontab: {entries, env, comments} | null, cronD: [{file, entries}]}`; `username` — владелец показанного `userCrontab`, `currentUser` — SSH-юзер (владелец мутируемого crontab), `editable` — `username === currentUser`; entry — `{index, raw, enabled, schedule, command, user?, human}`. Чтение чужих персональных crontab — только для root (`id -u`), путь spool-каталога с фолбэком по дистрибутиву, `crontab -u <user> -l` (фолбэк `cat` spool-файла), имя валидируется `isValidCronUser`; чужие — read-only. `GET /api/cron/users?profileId=` → `{users: string[]}` (пусто, если не root). Мутации crontab пользователя: `POST /api/cron/entries` `{schedule, command}` (201), `PUT /api/cron/entries/:index` `{expectedRaw, schedule, command}`, `DELETE /api/cron/entries/:index` `{expectedRaw}`, `POST /api/cron/entries/:index/toggle` `{expectedRaw}` — все возвращают свежий snapshot; 409 при расхождении `expectedRaw` (crontab изменился), 400 при невалидном расписании.
- Вкладка «Службы» (эпик 13, systemd): `GET /api/services?profileId=` — снимок `{timestamp, available, reason?, units: [{name, description, load, active, sub, enabled}]}` (при не-systemd `available:false` с причиной — не ошибка); `GET /api/services/:unit?profileId=` — деталь `{name, status (raw systemctl status), show: {MainPID, ActiveState, …, ActiveEnterTimestamp}}`; `POST /api/services/:unit/action?profileId=` `{action: start|stop|restart|reload|enable|disable|reset-failed, sudoPassword?}` → `{ok, output}` (400 — пользовательские причины с текстом systemd как есть, 502 — транспорт; имя unit'а валидируется regex `^[A-Za-z0-9@._:\-]+$` до всего остального, `..` отдельно — 400); `GET /api/services/:unit/logs?profileId=&tail=&follow=1` — разовый text/plain (пометка обрезки по лимиту 2 МБ) или follow-стрим chunked text/plain (429 при исчерпании лимитера follow-стримов на профиль).
- Действия над процессами (эпик 17): `POST /api/processes/:pid/signal?profileId=` `{signal: TERM|KILL|HUP, sudoPassword?}` → `{ok, output}` (kill молчит — output пустой) и `POST /api/processes/:pid/renice?profileId=` `{nice: −20..19, sudoPassword?}` → `{ok, output}` (вывод renice «old nice level …» — в notice). pid — каноничное целое 2..4194304, иначе 400 «Недопустимый pid» (запрет `0`/`1`/отрицательных обязателен: `kill -TERM -1` кладёт всё, до чего дотянется); 400 — пользовательские причины (нужен sudo-пароль, неверный пароль, нет прав sudo, процесса больше нет, утилиты нет), 502 — транспорт; после успеха кэш метрик сброшен — refetch «Обзора» сразу свежий.
- Обновления пакетов (эпик 19): `GET /api/packages/updates?profileId=` — снимок `{timestamp, pm: 'apt'|'dnf'|'yum'|'apk'|null, updates: [{name, current, available, source}], rebootRequired, rebootPackages, indexAgeMs, error?}` (кэш 60 с; `pm: null` — менеджера нет, штатная заглушка; у dnf текущая версия `null` — «— → версия»); `POST /api/packages/apply?profileId=` `{sudoPassword?}` — применение: зонд до стрима (400 при неверном пароле/правах, 502 transport, 429 при лимите follow-слотов), вывод — chunked `text/plain` стрим `execStream` в просмотрщик (пароль первой строкой stdin, в argv/логах не появляется), на settle — инвалидация кэша снимка.
- Вкладка «Nginx»: `GET /api/nginx?profileId=` — `{timestamp, sources: NginxSourceSnapshot[]}`; источник — `{type: 'native'|'container', containerId?, containerName?, version, configTest: {ok, output}, sites: NginxSite[], error?}`; site — `{file, serverNames, isDefault, listens: [{addr, port, ssl, defaultServer}], target: {kind: proxy|static|unknown, value}, locationsCount, cert: {path, notAfter, daysLeft} | {path, error} | null}`. nginx не найден нигде → `sources: []` (200); упавший источник — секция с `error`. `POST /api/nginx/test` и `POST /api/nginx/reload` `{profileId, source: 'native'|'container:<id>'}` → `{ok, output}`; источник валидируется против актуального discovery (400 — не найден); reload при красном `nginx -t` не выполняется — 409 `{error, output}`. `GET /api/nginx/config?profileId=&source=&path=` → `{content}` — чтение одного конфиг-файла (кнопка «Открыть»; путь абсолютный, иначе 400).
- `/api/files/list|read|write|mkdir|rename|chmod|delete|download|upload|search|download-dir|upload-dir` — `profileId` и `path` в query/body; upload — raw body (`express.raw`, лимит 200 МБ); download — стрим; search — `mode=name|content`; download-dir — tar.gz стрим; upload-dir — raw tar.gz → `tar -xzf`. `GET /api/files/tail?profileId=&path=&lines=&follow=` (эпик 14) — живой просмотр лога: до старта precheck по SFTP (существует, не директория, не бинарный — иначе JSON-ошибка до открытия канала); `follow=0` — разовый `tail -n` (таймаут 30 с, при упоре в лимит вывода 2 МБ — хвостовая пометка об обрезке), `follow=1` — chunked `text/plain` стрим `tail -n -F` поверх `execStream` (лимит слотов — `services/stream-limits.ts`, 429 при превышении; backpressure-гейт `createChunkGate`; `req.on('close')` → `handle.close()`; служебные ошибки канала после `flushHeaders` идут в теле как строки лога — транспорт другой ошибки не даёт, статус 'stopped' в UI показывает, что стрим закончился).
- `/api/docker/containers|images|volumes|networks`, действия контейнеров (`start|stop|restart|rm`), `pull`, `rmi`, `run`, `logs` (tail и follow-стрим — follow занимает слот общего лимитера `stream-limits.ts` и идёт через backpressure-гейт, 429 при превышении), `GET /stats`, `POST /prune` `{target: containers|images|volumes|system}`, `GET /compose/status`, `GET /compose/ps`, `POST /compose/up|down`.
- Вкладка «Базы данных»: CRUD `GET/POST /api/db/connections?profileId=` (список без паролей, c `hasPassword`), `PUT/DELETE /api/db/connections/:id` (непереданный пароль сохраняется), `POST /api/db/connections/test` (SELECT 1 без сохранения; опциональный `id` — при пустом пароле проверяется сохранённый; ошибка клиента БД — телом `{error: {message, stderr, exitCode}}` со статусом 400, «Access denied» виден до сохранения); `GET /api/db/discovery?profileId=` — `{suggestions, hints}` для автозаполнения формы; `GET /api/db/overview?profileId=&connectionId=`, `GET /api/db/databases|tables|columns?profileId=&connectionId=&database=`, `POST /api/db/query {profileId, connectionId, database, sql ≤64 КБ, readOnly}` → `{columns, rows ≤1000, rowCount, totalRows, durationMs, truncated, rawOutput?}` либо 400 `{error: {message, stderr, exitCode}}`; `GET /api/db/dump?profileId=&connectionId=&database=` — стрим .sql.gz. Подключение чужого профиля → 404.
- WS `/ws/terminal?profileId=&cols=&rows=&tabId=[&container=<id>&containerName=<имя>]` — сообщения: клиент `input|resize|close|restart` (restart закрывает shell и SSH-подключение и открывает новый shell; close — явный destroy вкладки, без него сессию держит grace 60 с), сервер `output|connected|close|error`. `tabId` — вкладка терминала (эпик 15): отсутствие → 0, невалидный → `close(1008)`; лимит 4 живых сессий на профиль, сверх — error-фрейм + `close(1013)`.
- WS `/ws/agent?profileId=&dialogueId=` — клиент `message {content, planMode?}|approve|reject|approve_plan|stop|sudo_credentials {password, profileId?}|attach_server {profileId}|detach_server {profileId}`, сервер `dialogue|token|message|suggestion|tool_start|tool_pending|tool_result|plan_ready|running|done|error|servers|usage`. `tool_start {callId, name, args, server}` — read-only инструмент начал выполняться (карточка «выполняется…» в UI, без кнопок), `tool_pending` — мутрующий ждёт подтверждения; поле `server` (имя профиля; для connect_server — целевой) — в `tool_start`/`tool_pending`/`tool_result`. Событие `servers {home, attached: [{id, name, host, username}]}` — при подключении WS и на каждое изменение состава серверов диалога (attach/detach/connect_server). Диалог загружается в сессию при подключении и сохраняется по ходу каждого шага; если `dialogueId` не передан, сервер создаёт новый диалог и сообщает его id событием `dialogue`. `sudo_credentials` задаёт sudo-пароль для привилегированного `security_audit` на сервере `profileId` (по умолчанию домашний): пароль хранится только в Map сессии (память), очищается в `stop()`/`onWsClose()` и при detach сервера; не логируется, не сохраняется в диалог и не передаётся модели. `attach_server`/`detach_server` — ручное подключение/отключение сервера к диалогу (действие пользователя, approve не требуется; домашний отцепить нельзя — клиенту уходит error). Событие `usage {totals: UsageAgg}` — после каждой записи в журнал расходов (кумулятивные итоги диалога; бейдж в тулбаре обновляется во время прогона). Событие `suggestion {text}` — после финального `message` хода без tool_calls: подсказка вероятного ответа для плейсхолдера поля ввода (см. раздел «Подсказка вероятного ответа»; вырезанный из контента маркер `[[SUGGEST]]` наружу не попадает).
