# План эпика: «Новый сервер (root + пароль)» — bootstrap под ключ

> **Статус: готов к реализации** (ревью 2026-08-21 учтено: честный UI без
> живого прогресса, fallback-откат через key-сессию, кейс «hardening
> прошёл, а профиль не создался», порядок детекта директив через
> `sshd -T`, мелочи реализации). Выращен из обсуждения 2026-08-21.
> Решения согласованы с пользователем: отдельный ключ на каждый сервер;
> галочка «запретить вход по паролю» с жёстким порядком «сначала ключ —
> потом sshd» и откатом.

## Зачем

Сценарий свежего VPS: от провайдера есть только root + пароль. Сейчас
такой сервер добавляется профилем с `authType=password` (пароль ложится
в `profiles.json`), либо ключ приходится прописывать руками через
`ssh-copy-id`. Фича — кнопка **«Новый сервер (root + пароль)»** в UI
добавления сервера: пользователь вводит host, порт, логин и пароль,
сервис сам генерирует отдельный ключ, прописывает его на сервере,
проверяет вход ключом, (опционально) закрывает парольный вход SSH и
создаёт профиль с `authType=key`. Пароль нигде не сохраняется.

## Цели и не-цели v1

**Не делаем (осознанно):**

- Bootstrap под непривилегированным пользователем с sudo — установка
  ключа работать будет, но hardening sshd требует root; v1 — галочка
  hardening активна только при `username=root`, форма принимает любого
  пользователя, подпись честно объясняет.
- Отключение root-пароля как такового (`passwd -l`, консоль провайдера)
  — закрываем только SSH-парольный вход; консоль/rescue провайдера
  остаётся страховкой с паролем, это правильно.
- Правку `PermitRootLogin`, fail2ban, файрвол — без парольных методов
  root и так только по ключу; чем меньше правок, тем проще откат.
- Хранение/повторное использование пароля: живёт только в памяти
  запроса bootstrap.
- Хранение отпечатка хоста — текущее поведение подключения без
  изменений (TOFU не вводим).

## Принятые решения

1. **Отдельный ключ на каждый сервер** — ed25519, файл
   `keys/<sanitizedName>.ed25519` (санитизация как у `memory/`,
   коллизия имени — числовой суффикс), права 0600 как у импорта.
   Комментарий pubkey — `ssh-commander@<имя профиля>`: видно, откуда
   ключ в `authorized_keys`, точечный отзыв по отдельности.
2. **Жёсткий порядок операций (ключевой инвариант):** подключение по
   паролю → установка pubkey → **отдельное новое** подключение ключом
   (верификация) → [галочка] hardening sshd → `sshd -t` → reload →
   контрольные проверки → создание профиля. sshd не трогаем, пока вход
   ключом не доказан.
3. **Галочка «Запретить вход по паролю (SSH)»**, по умолчанию **вкл** —
   сценарий свежего VPS именно этого и хочет; снимается одним кликом,
   подпись предупреждает: «проверьте, что доступ к консоли провайдера
   есть». Гасим **обе** директивы: `PasswordAuthentication no` +
   `KbdInteractiveAuthentication no` (иначе PAM keyboard-interactive
   оставляет парольный вход).
4. **Hardening пишется drop-in'ом**
   `/etc/ssh/sshd_config.d/00-ssh-commander.conf` — раннее имя: OpenSSH
   «первое вхождение побеждает», Include стоит наверху, drop-in
   перекрывает cloud-init `50/60-*.conf` с `PasswordAuthentication yes`
   (правка основного конфига в конце молча не перебьёт). Нет
   `sshd_config.d`/Include (старые дистрибутивы) → бэкап основного
   конфига (`cp sshd_config sshd_config.bak-ssh-commander-<ts>`) и
   замена активных директив со вставкой до первого `Match`.
5. **Reload только после зелёного `sshd -t`** (паттерн `nginx -t`).
   Путь к sshd: `command -v sshd || /usr/sbin/sshd`. Reload:
   `systemctl reload sshd || systemctl reload ssh || service ssh
   reload` — reload не рвёт установленные сессии. Красный тест —
   откат и ошибка с выводом.
6. **Верификация результата по факту, не на слово:** (а) повторное
   подключение ключом после reload; (б) эффективный конфиг `sshd -T`
   (при наличии Match-блоков — с `-C user=…,host=localhost,
   addr=127.0.0.1`); (в) попытка password-входа с ожиданием отказа —
   пароль ещё в памяти запроса; если пароль всё ещё пускает — честный
   warning в результате, не успех.
7. **Откат:** живая password-сессия переживает reload; провал любой
   пост-проверки → удалить drop-in / восстановить бэкап, reload снова,
   ошибка наверх. **Fallback-цепочка отката:** сначала пробуем живую
   password-сессию; если она оборвалась — откат через key-сессию (вход
   ключом верифицирован до hardening, hardening ключевой вход не
   закрывает). Провал до создания профиля → удалить локальный файл
   ключа; строку pubkey убрать из `authorized_keys` best-effort через
   живую сессию.
   Отдельный кейс: **hardening прошёл и проверки зелёные, а
   `createProfile` упал** (гонка имени, диск) — сервер остаётся
   захарденным без профиля, ключ на диске сохраняется; ошибка наверх
   содержит путь к ключу и подсказку «добавьте профиль вручную с этим
   ключом». Откат hardening в этой точке не делаем: состояние
   консистентно и восстановимо руками.
8. **Пароль не persist'ится:** не пишется в `profiles.json`, журналы,
   логи, ответы API; в ошибочные сообщения не подставляется. Семантика
   — как у sudo-пароля аудита.
9. **Идемпотентность:** перед append проверяем наличие ключа
   `grep -F` (фиксированная строка, не регекс — base64 тела ключа
   содержит `+`/`/`/`=`) по телу pubkey **без комментария**: комментарий
   `ssh-commander@<имя>` может содержать пробелы и меняться при
   переименовании, в сравнении не участвует. Повторный bootstrap не
   дублирует строку в `authorized_keys`.
10. **SELinux-страховка:** после установки ключа `command -v
    restorecon >/dev/null && restorecon -R ~/.ssh` — дёшево, закрывает
    RHEL-кейс с контекстом `authorized_keys`.

## Архитектура сервера

### `server/src/services/bootstrap.ts` — весь сценарий в одном сервисе

- `generateKeyPair()` — `node:crypto` ed25519; приватный ключ в формате,
  который парсит ssh2 (см. риски), публичный — строка `authorized_keys`
  (`ssh-ed25519 <base64> ssh-commander@<name>`; ssh-wire blob для
  ed25519 собирается тривиально: `"ssh-ed25519"` + 32 байта ключа).
- `installAuthorizedKey(client, pubkeyLine)` — exec: `umask 077;
  mkdir -p ~/.ssh; touch ~/.ssh/authorized_keys; chmod 700 ~/.ssh;
  chmod 600 ~/.ssh/authorized_keys` + grep-проверка + append + optional
  `restorecon`. Все аргументы через `shq`.
- `applySshdHardening(client, username)` — чистые функции построения
  команд и разбора вывода (под unit-тесты): детект `sshd_config.d` +
  `Include`, содержимое drop-in (обе директивы), fallback-правка
  основного конфига, `sshd -t`, reload, разбор `sshd -T`.
- `bootstrapServer(input)` — оркестрация; возвращает созданный профиль
  + `BootstrapStep[]` (название, статус ok/warn/error, детали) — UI
  рисует прогресс и итоговый отчёт. Ошибки — человекочитаемый маппинг:
  «root по паролю запрещён (`PermitRootLogin prohibit-password`)»,
  «неверный пароль», «порт недоступен» и т.п.
- Подключения — прямые ssh2-клиенты (профиля ещё нет, менеджер не
  нужен): connect timeout 30 с; все клиенты закрываются в `finally`.

### API

- `POST /api/profiles/bootstrap` (монтируется с `requireAuth`, zod):
  `{name, host, port, username, password, disablePasswordAuth}`.
  Пароль не логируется. Ответ: созданный `Profile` + `steps`. Профиль
  создаётся существующим `createProfile` (`authType=key`, `keyPath` на
  новый файл) — валидация и уникальность имени переиспользуются.
  Длительность запроса — десятки секунд (3 SSH-подключения + exec'ы);
  убедиться, что ни HTTP-слой, ни фронтенд-фетч не имеют таймаута
  меньше ~120 с.

## Фронтенд

- В `ProfileModal` (режим добавления) — отдельная кнопка/ссылка
  **«Новый сервер (root + пароль)»**, раскрывающая свою форму: имя,
  host, порт (22), пользователь (по умолчанию `root`), пароль, галочка
  «Запретить вход по паролю после настройки» (вкл по умолчанию, при
  пользователе ≠ root — disabled с подсказкой).
- Отправка: **без живого прогресса** — `steps` приходят только в
  финальном ответе, поэтому во время запроса показываем спиннер
  «Настраивается, это может занять до минуты…»; по успеху — итоговый
  отчёт по шагам (warn'ы показываются явно), модалка закрыта, профиль
  выбран. SSE/WS-стрим прогресса осознанно не вводим: одиночный запрос,
  отчёт в конце закрывает потребность.
- Ошибки — toast + mono-блок с деталями упавшего шага.

## Тесты

- `bootstrap.test.ts` (unit, мок ssh2-клиента): сборка команд установки
  ключа (экранирование, идемпотентность по телу ключа `grep -F`,
  restorecon), содержимое drop-in (обе директивы, раннее имя),
  fallback без `sshd_config.d`, детект директив по `sshd -T` до правок,
  разбор `sshd -T`, формат pubkey-строки, маппинг ошибок, структура
  шагов, откат (в т.ч. fallback через key-сессию при оборванной
  password-сессии и кейс «hardening ок, createProfile упал» — ключ
  сохраняется, подсказка в ошибке).
- `bootstrap.manual.mjs`: контейнер sshd с root-входом по паролю
  (`PermitRootLogin yes`; готовый `docker run` — в шапке скрипта):
  полный сценарий (ключ установлен → вход ключом работает → пароль
  отключён, password-попытка отклонена → повторный bootstrap
  идемпотентен) и кейс отката (сломанный конфиг → восстановление,
  вход паролем снова работает).

## Риски

- **Парсинг ssh2 сгенерированного ключа**: ed25519 в PEM PKCS#8 может
  не читаться ssh2 — при реализации проверить тестом первым; fallback:
  минимальный энкодер OpenSSH-формата (без passphrase, none-kdf, ~50
  строк) или RSA-4096 PKCS#1 PEM (поддержан гарантированно).
- **Старые OpenSSH**: до 8.7 ключевого слова `KbdInteractiveAuthentication`
  нет (там `ChallengeResponseAuthentication`), а неизвестная директива
  валит `sshd -t` целиком. Порядок детекта: **сначала `sshd -T` на
  немодифицированном конфиге** (заодно baseline-проверка, что sshd
  вообще валиден до наших правок), из его вывода определяем, какие
  директивы понимает данный sshd, и пишем только их; для сценария
  «свежий VPS в 2026» редкость, fallback честный.
- **Многообразие дистрибутивов** (Match-блоки, облачные образы с
  сюрпризами в sshd_config.d) — закрывается проверками по факту
  (`sshd -T`, тестовые подключения) и откатом.
- **Неверный пароль/недоступный порт** — детерминированные ошибки,
  bootstrap абортируется до любых мутаций.

**Оценка:** ~1.5–2 дня (1–1.5 при удачном раскладе с форматом ключа;
+0.5 дня, если потребуется OpenSSH-энкодер ключа и отладка
fallback-правки основного конфига).
