Спасибо за предложение! Для home-lab предлагаю опциональный режим доступа через HTTPS reverse proxy, сохранив localhost-only по умолчанию.

Подготовленная реализация использует `APP_ACCESS_MODE=proxy` и `APP_TRUSTED_ORIGINS=https://commander.home.arpa` (точный список HTTPS Origin, с учётом порта). Один и тот же allowlist проверяет REST API и WebSocket терминала/агента. Чужой Origin отклоняется; GET/HEAD без Origin допускаются только с Referer из того же allowlist, а мутации и WS требуют Origin; пароль и сессия остаются обязательными, cookie получает Secure. Сетевой режим не запускается, пока пароль не настроен локально или не задан при первом старте — onboarding не открывается в сеть.

Разрешённые IP/подсети ограничиваются на reverse proxy/firewall по реальному адресу TCP-клиента. Backend остаётся на loopback, SSH-туннельные порты тоже. Приложение не доверяет X-Forwarded-For/Host/Proto и Forwarded: ими нельзя разрешить Origin или обойти проверку сессии. Для nginx подготовлен пример с HTTPS, allow/deny и WebSocket upgrade. На proxy также нельзя включать доверие к произвольным real-IP заголовкам или подменять Origin доверенным значением.

Это по-прежнему однопользовательский инструмент: доступ разрешённому устройству расширяет доверенную зону, а компрометация панели затрагивает все сохранённые SSH-доступы. Публичная публикация не поддерживается; один Origin-allowlist не является IP-фильтром или аутентификацией. Для LAN нужен доверенный сертификат и исключение прямого доступа к backend.

REST и оба WS handshake покрыты регрессионными тестами (разрешённый/запрещённый Origin, отсутствие сессии и поддельные proxy-заголовки). Ограничения IP/TLS необходимо проверить на конкретном proxy. Изменения пока подготовлены в исходниках; закреплённый образ 0.1.3 ещё не поддерживает новые переменные.
