> Сервер: 46 файлов unit-тестов в `server/test/`. Не проверено вживую:
> ручные сценарии (`*.manual.*`) и UI-проход против реального сервера —
> требуют запущенного стенда.

> Эпики 13–20 закрыты (планы — `docs/services-plan.md`,
> `docs/file-tail-plan.md`, `docs/terminal-tabs-plan.md`,
> `docs/disk-usage-plan.md`, `docs/process-actions-plan.md`,
> `docs/snippets-plan.md`, `docs/packages-plan.md`,
> `docs/alerts-plan.md`), детали реализации — в `docs/architecture.md`.
> Дальнейшие эпики раздела «Продолжение» сгруппированы по Tier (частота
> использования), каждый ждёт детального планирования перед взятием
> в работу.

Документ фиксирует эпики развития проекта. Реализация идёт последовательно:
для каждого эпика сначала детальный план (архитектура, API, UI, тесты),
согласование, затем реализация. Порядок эпиков — от простого к сложному,
с учётом переиспользования инфраструктуры между ними.

Общие правила для всех эпиков (действуют молча, не повторяются в каждом):

- Сервер: TypeScript strict, ESM, импорты с `.js`; zod-валидация входа;
  `shq`-экранирование всех аргументов shell; лимиты вывода как у `exec`.
- Фронтенд: React 18 без новых тяжёлых зависимостей без необходимости;
  темы через CSS-переменные; русский язык; `scrollbar-gutter: stable`
  в новых скролл-областях; все async-действия через try/catch → toast.
- Тесты: unit-тесты (vitest) на всю новую логику сервера; перед сдачей —
  `npm run build` в обоих каталогах, `npm test` зелёный, `npm audit` чистый.
- AGENTS.md обновляется по итогам каждого эпика (новые маршруты, env,
  компоненты).

## Эпик 0. Реорганизация layout: вкладки сверху, агент в правом сайдбаре

**Цель:** UX в стиле VS Code: основные разделы (Обзор/Терминал/Файлы/Docker)
— вкладками сверху, агент — постоянно открытой панелью справа. Можно
работать в терминале и параллельно общаться с агентом.

Это фундамент UI: выполняется **первым**, чтобы эпики 1, 5 и 6
(новые вкладки/экраны) сразу строились на новом layout, а не мигрировали.

**Frontend (весь эпик — фронтенд, backend не меняется):**
- `App.tsx`: вместо вертикального сайдбара с разделами — верхняя панель
  вкладок (таббар) + правая панель агента.
- Сайдбар слева сохраняется только для списка профилей (как сейчас) либо
  профили уезжают в выпадающий селектор в шапке — решить на планировании.
- **Живучесть вкладок**: сейчас при переключении раздела компонент
  размонтируется и теряет состояние (терминал-сессия переживает это за счёт
  серверного grace 60 c, но локальный стейт — нет). В новом layout вкладки
  не размонтируются, а скрываются (`display: none` / keep-alive) — терминал,
  открытый путь в файлах и позиция в Docker сохраняются.
- **Панель агента**: фиксированной ширины справа (~380–480 px), сворачивается
  кнопкой (состояние в localStorage), ширину можно тянуть (resize-разделитель).
  AgentPage монтируется один раз на профиль и живёт постоянно — WS не рвётся
  при переключении вкладок.
- Адаптив: при узком окне панель агента уезжает в оверлей поверх контента.
- Таббар: активная вкладка подсвечена; переключение мгновенное (без
  перезагрузки данных).

**Тесты:** unit не требуется; ручной проход: терминал не пересоздаётся при
переключении вкладок, агент продолжает стримить при уходе на другую вкладку,
темы работают в обоих панелях.

**Риски:**
- Держать все вкладки смонтированными = фоновая активность (polling Docker,
  follow-логи). Правило: эффекты ставят на паузу, когда вкладка скрыта
  (visibility-флаг через контекст).
- xterm при `display: none` теряет размеры — вызывать `fit()` при возврате
  на вкладку.
- AgentPage сейчас завязан на размонтирование как способ закрыть WS —
  пересмотреть жизненный цикл (закрытие по смене профиля/диалога, а не
  по unmount).

**Оценка:** ~1–1.5 дня.

## Эпик 1. Мониторинг сервера

**Цель:** вкладка/виджет с живым состоянием сервера: CPU, RAM, диск, uptime,
load average, топ процессов.

**Backend:**
- `server/src/services/metrics.ts` — сбор метрик одним SSH-`exec`
  (чтение `/proc/stat`, `/proc/meminfo`, `df`, `uptime`, `ps`), парсинг в
  типизированную структуру. Никаких новых зависимостей — только парсинг
  вывода стандартных утилит.
- REST `GET /api/metrics?profileId=` — разовый снимок.
- Опрос с фронтенда (polling 2–5 c). WebSocket не нужен: метрики — это
  периодический запрос, а не поток. Polling проще и надёжнее.
- Кэш последнего снимка на профиль (1–2 c), чтобы несколько открытых
  вкладок не плодили exec'ы.

**Frontend:**
- Новая вкладка «Обзор» (первая в сайдбаре): карточки CPU/RAM/диск/uptime,
  шкалы прогресса, таблица топ-10 процессов по CPU.
- Индикация недоступности сервера (SSH не подключается) вместо карточек.

**Тесты:** парсеры `/proc/*` и `df` на фикстурах (linux-вывод, edge-кейсы:
терабайтные диски, tmpfs, контейнерный uptime).

**Риски:** парсинг `/proc` должен быть терпим к формату; деградация —
показывать «недоступно», а не падать.

**Оценка:** ~1 день. Хороший первый эпик — прогревает паттерн
«сервис → роут → вкладка», который переиспользуют эпики 2–4.

## Эпик 2. Поиск по файлам

**Цель:** поиск файлов и по содержимому в файловом менеджере.

**Backend:**
- REST `GET /api/files/search?profileId=&path=&pattern=&mode=name|content&limit=`.
- Реализация через `exec`: `find` для имён, `grep -r` для содержимого
  (с `-I`, `--include`, лимитом результатов, таймаутом). Все аргументы
  через `shq`; pattern — строго аргументом, не интерполяцией.
- Лимиты: макс. глубина, макс. 500 результатов, таймаут 30 c.

**Frontend:**
- Панель поиска в шапке FilesPage: переключатель «имена / содержимое»,
  результаты списком с переходом к файлу/каталогу по клику.
- Подсветка совпавшей строки для content-режима.

**Тесты:** unit на сборку команды (экранирование, флаги), парсинг вывода.

**Риски:** долгий поиск по большим деревьям — решается таймаутом и лимитом;
glob в pattern — только в имени файла, не в пути.

**Оценка:** ~0.5–1 день.

## Эпик 3. Скачивание/загрузка директорий

**Цель:** перенос папок целиком, архивом — быстрее и надёжнее рекурсивного SFTP.

**Backend:**
- `GET /api/files/download-dir?profileId=&path=` — стрим `tar -czf - -C dir base`
  через `execStream`-подобный механизм (stdout в HTTP-ответ,
  `Content-Type: application/gzip`).
- `POST /api/files/upload-dir?profileId=&path=` — raw body (tar.gz),
  распаковка `tar -xzf - -C path` через stdin канала; лимит как у upload
  (200 МБ сжатых данных).
- Проверки: `assertSafePath`, отказ на `/` и `..`; код возврата tar
  проверяется — ошибка до начала отдачи тела (сначала `stat` пути).

**Frontend:**
- Кнопки «Скачать» на директориях (рядом с файловой), «Загрузить архив»
  в тулбаре; прогресс по возможности (размер неизвестен заранее — спиннер
  + байты).

**Тесты:** unit на сборку команд и валидацию путей; ручной интеграционный
сценарий в `integration.manual.mjs` — скачать/загрузить, сравнить содержимое.

**Риски:** tar должен существовать на удалённом сервере (на минимальных
образах может не быть) — детект и понятная ошибка; большие архивы держим
только в потоке, не в памяти.

**Оценка:** ~1 день.

## Эпик 4. История команд терминала

**Цель:** быстрый доступ к последним командам сервера из терминала.

**Backend:**
- REST `GET /api/terminal/history?profileId=&limit=` — чтение
  `~/.bash_history` (фолбэк: `~/.zsh_history` с чисткой zsh-формата
  `: 1234567890:0;cmd`) через `exec_readonly`-совместимый вызов.
- Дедупликация с сохранением порядка (свежие сверху), лимит 100.

**Frontend:**
- Кнопка/хоткей в TerminalPage открывает палитру поверх терминала
  (стрелки/поиск-фильтр, Enter — вставить команду в терминал, не выполняя).
- Вставка идёт через существующий WS `input`.

**Тесты:** парсер zsh/bash-форматов, дедуп, обрезка многострочных команд.

**Риски:** история пишется при закрытии сессии — «свежесть» не гарантируется,
это нормально; секреты в истории — ответственность пользователя, как и в
самом терминале.

**Оценка:** ~0.5 дня.

## Эпик 5. Docker: stats, exec, prune, compose

**Цель:** превратить Docker Explorer в полноценный инструмент.

Четыре подзадачи, идут в одном эпике, но коммитятся раздельно:

**5a. docker stats в реальном времени**
- Backend: `GET /api/docker/stats?profileId=` — стрим (SSE или chunked NDJSON)
  поверх `docker stats --no-stream --format json` в цикле, либо разовый
  polling с фронта (проще — начать с polling 2 c).
- Frontend: колонки CPU%/MEM в таблице контейнеров или отдельная секция;
  останавливается при уходе со вкладки.

**5b. exec в контейнер**
- Backend: WS `/ws/terminal?profileId=&container=` — существующий
  `openShell` переиспользуется: вместо дефолтного shell запускается
  `docker exec -it <container> sh` (детект bash/sh).
- Frontend: кнопка «Терминал» в строке контейнера — открывает
  TerminalPage в режиме контейнера (или модалку с xterm).

**5c. prune-операции**
- Backend: `POST /api/docker/prune` `{target: containers|images|volumes|system}`
  → `docker <target> prune -f`; вывод (освобождено места) возвращается.
- Frontend: кнопки с confirm и отображением результата («освобождено N МБ»).

**5d. docker compose**
- Backend: детект `docker compose version` (v2) / `docker-compose` (v1) на
  профиль; `GET /api/docker/compose/ps?path=`; `POST .../up|down` с `path`
  проекта. Путь к проекту — абсолютный, через `assertSafePath`.
- Frontend: секция «Compose» с указанием каталога проекта, таблица сервисов,
  кнопки up/down.

**Тесты:** unit на сборку команд и парсинг; интеграционный сценарий
расширяется (stats, exec, prune на тестовом sshd с docker-моком или
реальном docker).

**Риски:** exec в контейнер — утечка каналов при обрыве (см. известный баг
с `docker logs -f`, чинить вместе); compose-путь — не давать уйти за
пределы разумного (документировать, что инструмент однопользовательский).

**Оценка:** ~2–3 дня. Самый объёмный эпик.

## Эпик 6. Редактор файлов с подсветкой синтаксиса

**Цель:** заменить plain-textarea в модалке редактирования на CodeMirror 6
(Monaco отбрасываем: ~3 МБ в бандле против ~400 КБ у CM6, для локального
инструмента перебор).

**Frontend (основная масса работы):**
- Зависимости: `@codemirror/*`, `@uiw/react-codemirror` (обёртка) или
  ручная сборка CM6 — решить на планировании, приоритет размеру бандла.
- Подсветка по расширению (shell, Dockerfile, yaml, json, js/ts, python,
  nginx-conf и т.п.), темная/светлая тема синхронизирована с `data-theme`.
- Номера строк, отступы, поиск по файлу (Ctrl+F внутри редактора).
- Режим «только просмотр» для больших файлов и при read-only открытии.
- Lazy-load бандла редактора (`React.lazy`), чтобы не раздувать основной чанк.

**Backend:** без изменений (read/write уже есть).

**Тесты:** без unit-тестов фронта — проверка сборкой и ручным проходом;
следить, чтобы лимит read 1 МБ соблюдался и для редактора.

**Риски:** новые зависимости — зафиксировать версии, `npm audit` после
установки; конфликт стилей CM с глобальным CSS — изолировать классом.

**Оценка:** ~1 день.

## Эпик 7. AI-агент: «объясни ошибку» из терминала

**Цель:** мост между терминалом и агентом: выделил/получил ошибку —
один клик отправляет контекст агенту.

**Frontend:**
- Кнопка «Спросить агента» в TerminalPage: берёт последние N строк буфера
  xterm (или выделение, если есть), переключает на вкладку агента и
  отправляет сообщение вида «Объясни вывод: ```...```» в текущий/новый
  диалог того же профиля.
- Связь между страницами — через поднятие состояния в App или маленький
  event-bus (без Redux); выбрать на планировании простейший вариант.

**Backend:** без изменений (WS агента уже принимает произвольное `message`).

**Тесты:** unit не требуется; ручная проверка сценария.

**Риски:** размер контекста — обрезать до ~4 КБ; не перетягивать секреты —
обрезка по последним строкам снижает, но не устраняет риск (документировать).

**Оценка:** ~0.5 дня.

## Эпик 8. AI-агент: режим планирования

**Цель:** опциональный режим: агент сначала выдаёт план из N шагов,
пользователь подтверждает целиком, затем идёт исполнение.

**Backend:**
- Флаг `planMode` в WS-протоколе агента (`message {text, planMode}`).
- В режиме плана: системный промпт-дополнение «составь план, инструменты
  не вызывать», инструменты в запросе к API отключаются; ответ-план
  приходит как обычное сообщение с маркером.
- Подтверждение плана: клиент шлёт `approve_plan` → агент продолжает с
  тем же диалогом, но уже с инструментами; отклонение — пользователь
  пишет правки, план пересоставляется.
- Мутирующие инструменты в исполнении по-прежнему требуют approve —
  режим плана не отменяет защиту, а добавляет уровень видимости.

**Frontend:**
- Переключатель «План» в шапке AgentPage; карточка плана с кнопками
  «Выполнить» / «Изменить».

**Тесты:** unit на ветвление режимов в `agent.ts` (мок client); ручной
сценарий `agent.manual.mjs` расширяется кейсом план→approve→исполнение.

**Риски:** модель может проигнорировать «не вызывай инструменты» —
отключение инструментов на уровне API-запроса, а не только промптом;
рост диалога (план + исполнение) — приемлемо.

**Оценка:** ~1 день.

## Эпик 9. Аудит безопасности сервера (baseline + diff)

**Цель:** вкладка «Безопасность»: набор read-only проверок гигиены VPS +
механика «снимок эталона → diff при следующих проверках». Не-специалисту
не нужно оценивать «нормально ли это» — инструмент показывает статусы
OK/предупреждение/критично с объяснением и сообщает, что изменилось с
прошлого раза. Честные рамки: это гигиена + обнаружение аномалий, а не
гарантия — руткит может подменить вывод любых команд (документировать в UI
и AGENTS.md).

Никакого расписания/фонового мониторинга — проверка только по кнопке
(компьютер спит — проверок нет, и это нормально; инструмент локальный).

**Backend:**
- `server/src/services/security.ts` — набор проверок, каждая возвращает
  `{id, category, title, status: ok|warn|crit|unknown, summary, details[],
  advice}`. Все команды read-only, через существующий `exec` (лимиты и
  таймауты его же), аргументы через `shq` там, где они есть.
- Проверки гигиены:
  - sshd: `PasswordAuthentication`, `PermitRootLogin` — предпочтительно
    `sshd -T` (итоговая конфигурация), fallback — парсинг
    `/etc/ssh/sshd_config` + `sshd_config.d/*`. Оба «yes»/не выключены →
    crit/warn.
  - Обновления: `apt list --upgradable` (счётчик, отдельно security),
    статус `unattended-upgrades` (установлен и включён).
  - Файрвол: `ufw status` (active?) иначе наличие правил iptables;
    «файрвола нет» → warn.
  - fail2ban: установлен/запущен (`fail2ban-client status`), число
    забаненных IP; не установлен → warn с советом.
- Проверки со снимком (baseline) — храним в
  `DATA_DIR/security/<profileId>.json` (атомарная запись tmp+rename,
  zod-валидация при чтении, битый файл → `*.corrupt-*`, как в
  `dialogues.ts`):
  - `authorized_keys` всех пользователей (`/root/.ssh/`, `/home/*/.ssh/`) —
    сохраняются только fingerprint/хэши ключей, сами ключи не храним и не
    логируем.
  - Пользователи с шеллом (`/etc/passwd`), члены группы sudo/wheel,
    файлы `/etc/sudoers.d/`.
  - Слушающие порты (`ss -tulpn`): адрес:порт + процесс.
  - Cron: `crontab -l` всех пользователей с шеллом, содержимое
    `/etc/cron.*` (хэши), systemd unit-файлы, изменённые за последние N дней.
  - Первый запуск: baseline сохраняется, diff пустой, статус «эталон
    создан». Следующие: diff списком «добавлено/удалено» по каждой
    категории; любые добавления ключей/пользователей/портов → warn/crit.
- Проверки-симптомы (без baseline):
  - Свежие входы: `last -20` (успешные, с IP), `lastb -20` (неудачные;
    требует root — при отказе status `unknown`, не ошибка).
  - Процессы: топ по CPU (майнеры), процессы с удалённым exe
    (`ls -l /proc/*/exe` → `(deleted)`), suspicious established-соединения.
- REST: `GET /api/security?profileId=` — полный отчёт (проверки +
  diff + метка времени baseline); `POST /api/security/baseline {profileId}` —
  принять текущее состояние как эталон (после того как пользователь
  разобрался с diff). Кэш отчёта на профиль ~30 c, чтобы повторное
  открытие вкладки не дёргало сервер.
- Деградация: отсутствие утилиты или неподдерживаемый дистрибутив
  (нет `apt`, `ss`, `fail2ban`…) → `status: unknown` с пояснением, отчёт
  в целом не падает; каждая проверка изолирована try/catch.

**Frontend:**
- Новая вкладка «Безопасность» в таббаре (keep-alive, prop `visible`,
  как остальные страницы): кнопка «Проверить», время последней проверки.
- Сверху — карточка «Изменения с прошлой проверки» (diff по категориям)
  с кнопкой «Принять как эталон» (confirm) — появляется только при
  непустом diff.
- Ниже — карточки проверок по категориям (Вход по SSH / Обновления /
  Сеть / Пользователи / Автозапуск / Активность): иконка статуса,
  summary, раскрывающиеся details, блок «Что делать» (advice) простым
  языком.
- Кнопка «Спросить агента» на карточке проверки — переиспользует
  механику `agentRequest` из эпика 7: агенту уходит «Объясни результат
  проверки безопасности: …» (контекст ≤ 4 КБ); агент может предложить
  исправление через обычный approve мутирующих инструментов.
- Polling нет — только ручной запуск; при скрытой вкладке ничего не
  происходит.

**Тесты:** unit на парсеры по фикстурам (`sshd -T`, `apt list`, `ss`,
`/etc/passwd`, `last`, `crontab -l`), diff-логика (новый ключ → warn,
новый пользователь → crit, удаление — информационно), изоляция ошибок
(проверка упала → unknown, остальные работают), хранилище baseline
(round-trip, corrupt-файл, атомарность).

**Риски:**
- Разнообразие дистрибутивов — целимся в Debian/Ubuntu (apt, ufw,
  fail2ban), остальное честно `unknown`; не раздуваем матрицу поддержки.
- `lastb`, часть `/proc`-проверок требуют прав — молчаливо деградируем
  в `unknown`.
- Diff ловит и легитимные действия самого пользователя — поэтому
  «принять эталон» ручное, а статусы diff — warn (не crit) по умолчанию,
  кроме новых пользователей/ключей.
- Агент не должен получать содержимое authorized_keys — в контекст
  уходят только fingerprint'ы и счётчики.

**Оценка:** ~2 дня.

## Эпик 10. Порты контейнеров во вкладке «Порты» + SSH-туннели

**Цель:** вкладка «Порты» показывает полную картину «куда можно подключиться»
на сервере: не только слушателей хоста (`ss -tulpn`), но и порты
docker-контейнеров — включая неопубликованные, доступные только через сеть
контейнеров, — а из любой строки можно поднять проброс порта (SSH-туннель)
на локальную машину. Частая цель проброса — именно контейнерные порты
(БД, админки, которые принципиально не выставляют наружу), а `ss` их не
показывает: опубликованные видны как безымянные слушатели `docker-proxy`
(без root имя процесса недоступно), внутренние не видны вообще.

Две фазы; 10a ценна сама по себе, 10b опирается на неё:

**10a. Порты контейнеров (фаза A)**

Бэкенд:

- `server/src/services/container-ports.ts`:
  - `collectContainerPorts(profile)` — два exec'а:
    `docker ps --format '{{json .}}'` (только запущенные, через
    `dockerExec`/`parseDockerJsonOutput` из `services/docker.ts`) и один
    батч-`docker inspect <id…>` полным JSON по всем id разом (аргументы
    через `shq`; вывод — JSON-массив, `parseDockerJsonOutput` его уже
    понимает) — не по контейнеру отдельно;
  - порты — из `NetworkSettings.Ports` inspect'а (runtime-биндинги, именно
    их слушает docker-proxy), а НЕ из человекочитаемой строки `Ports`
    `docker ps`: `"80/tcp": [{"HostIp": "0.0.0.0", "HostPort": "8080"}]` →
    опубликован (`hostIp`, `hostPort`, `containerPort`, `proto`);
    `"5432/tcp": null` → только сеть контейнера; диапазоны уже развёрнуты
    по портам; публикация на конкретный интерфейс (`192.168.1.5:8080:80`)
    получается бесплатно. `HostConfig.PortBindings` не используем — это
    конфигурация, а не фактические биндинги. Строковый парсер
    `parseDockerPortsString` (запятые-разделители, `:::`, диапазоны) не
    нужен вовсе;
  - из того же inspect — `HostConfig.NetworkMode` и IP из
    `NetworkSettings.Networks`;
  - результат `ContainerPortEntry { containerId, name, networkMode, ip,
    ports }`; у контейнеров с host-сетью `ip: null` (их порты — порты
    хоста, уже в основной таблице);
  - кэш 2 с на профиль (паттерн `ports.ts`).
- Расширение `GET /api/ports` до единого снимка: хостовые и контейнерные
  порты собираются параллельно (`Promise.allSettled`); docker недоступен
  или нет прав → поля `containers` просто нет (деградация как у
  docker-счётчиков overview). Ответ:
  `{timestamp, ports, containers?}`. Роут структурно не меняется;
- связка хостовых слушателей с контейнерами: после сборки обоих наборов
  слушатели хоста матчатся по порту и протоколу с опубликованными
  `hostPort` — совпавшая строка получает аннотацию `container: {id, name}`.
  Опубликованные порты видны в `ss` как безымянные `docker-proxy` (без
  root имя процесса недоступно) — аннотация закрывает именно эту дыру.

Фронтенд:

- секция «Порты контейнеров» под таблицей слушателей хоста (только при
  наличии `containers`): контейнер, IP, порт в контейнере, протокол,
  доступ («опубликован на :8080» / «только сеть контейнера» / «сеть
  хоста»);
- в основной таблице слушателей аннотированные строки подписываются
  «docker: <имя контейнера>» в колонке процесса (нет поля `containers` —
  подписей нет, деградация бесшовная);
- существующий фильтр расширяется на имя контейнера и IP;
- подсказка: контейнеры с host-сетью видны в основной таблице.

Тесты: `container-ports.test.ts` — фикстуры inspect-JSON (опубликованные
IPv4/IPv6/конкретный интерфейс, exposed-без-публикации `null`, диапазоны,
несколько портов, host-network), маппинг `ContainerPortEntry`, матчинг
хостовых слушателей с контейнерами, деградация без docker.

**Оценка фазы A:** ~0.5–1 день.

**10b. SSH-туннели (фаза B)**

Бэкенд:

- `server/src/services/tunnels.ts` — in-memory реестр без персистентности
  (после рестарта приложения туннелей нет, осознанно):
  - `createTunnel`: `net.createServer()` слушает `127.0.0.1:localPort`,
    на каждое соединение — `client.forwardOut('127.0.0.1', 0, targetHost,
    targetPort, …)` через `getClient` из `ssh/manager.ts`, двусторонний
    pipe socket↔stream с обработчиками `error` на обоих концах (socket и
    ssh2-стрим) и destroy второй стороны — unhandled `error` event роняет
    процесс. Лимит одновременных соединений на туннель — 10, сверх лимита
    socket закрывается сразу. Эквивалент `ssh -L` каналом direct-tcpip;
  - валидация — отдельная чистая функция `validateTunnelParams` (под
    unit-тесты): порты 1–65535; локальный конец только `127.0.0.1`;
    `targetHost` — hostname/IP-подобная строка до 253 символов (в shell не
    попадает — это аргумент SSH-протокола, но формат ограничим); лимит 10
    туннелей на профиль; дубль `(profileId, localPort)` → конфликт;
  - `localPort: 0` → автоподбор свободного (в разрешённом диапазоне,
    retry на EADDRINUSE);
  - жизненный цикл: `close` SSH-клиента туннеля → статус `closed` с
    ошибкой, сервер закрывается. Автопересоздания нет — в UI явная кнопка
    «Пересоздать» (честное поведение v1). Закрытый туннель остаётся в
    реестре со статусом и ошибкой до `DELETE`: после restart/reconnect
    SSH-подключения менеджер переподключится, а туннель останется closed —
    поведение согласовано, но UI обязан это показать. Self-heal
    альтернатива (listener переживает reconnect, `forwardOut` через
    `getClient` на каждое новое соединение) сознательно отложена;
- Маршруты `routes/tunnels.ts` (zod): `GET /api/tunnels?profileId=`
  (`{tunnels, portRange}` — диапазон отдаём для подсказок UI),
  `POST /api/tunnels` (409 при занятом порте/дубле),
  `DELETE /api/tunnels/:id`; монтирование с `requireAuth`.
- Развёртывание в Docker: локальный конец туннеля поднимается внутри
  контейнера приложения, поэтому compose публикует диапазон с интерполяцией
  env в обе стороны маппинга:
  `127.0.0.1:${TUNNEL_PORT_MIN:-10000}-${TUNNEL_PORT_MAX:-10049}:${TUNNEL_PORT_MIN:-10000}-${TUNNEL_PORT_MAX:-10049}`.
  Источник истины один: compose требует равные диапазоны по обе стороны,
  обе берутся из одних переменных — поменял env, поменялся и маппинг,
  сценарий «поменял env и молчаливо не работает» исключён. Те же
  `TUNNEL_PORT_MIN`/`TUNNEL_PORT_MAX` читаются приложением и ограничивают
  локальные порты (локальный запуск без env — без ограничений). Не
  host-сеть: это меняет security-постуру — сейчас изоляция задаётся именно
  compose-маппингом на 127.0.0.1. До реализации проверить: `docker compose
  config` и `up` корректно публикуют диапазон из 50 портов (поддерживается;
  ожидаемо ~50 записей docker-proxy — это норма).

Фронтенд:

- секция «Активные туннели» (над контейнерной):
  `localhost:10001 → 172.17.0.5:5432`, статус-точка, кнопки «Открыть»
  (`http://127.0.0.1:<порт>`, новая вкладка) и «Стоп»; closed-туннели
  показываются с ошибкой и кнопкой «Пересоздать» (видимый результат
  SSH-reconnect'а); polling 5 с при видимой вкладке (общий паттерн);
- кнопка «Проброс порта» в тулбаре — модалка ручного туннеля
  (targetHost/targetPort/localPort, подсказка допустимого диапазона);
- кнопки «Пробросить» в строках: контейнерная → преfill
  `targetHost = IP контейнера` (`localhost` при host-сети),
  `targetPort` = порт контейнера; слушатель хоста →
  `127.0.0.1:порт`; UDP-строки — кнопка неактивна с подсказкой
  «SSH-туннели только TCP»;
- создание/удаление через try/catch → toast (включая отказ sshd в
  `AllowTcpForwarding` — сообщение сервера как есть).

Тесты: `tunnels.test.ts` — `validateTunnelParams` (порты, localHost,
charset targetHost, границы диапазона), автоподбор порта, дубли, лимит на
профиль (вся чистая логика). Сетевая часть (net + ssh2) — ручной сценарий
`test/tunnels.manual.mjs` против тестового sshd
(`linuxserver/openssh-server` на `127.0.0.1:2222`, паттерн
`security-audit.manual.ts`): создать → соединение через туннель → закрыть
→ статус closed; отдельно — обрыв SSH (перезапуск sshd) → туннель closed
с ошибкой виден в UI, «Пересоздать» поднимает заново; больше 10
одновременных соединений → лишние закрываются.

Риски:

- `AllowTcpForwarding no` на целевом сервере → туннель не создастся,
  ошибка видна в UI (детерминированный аудит уже подсвечивает
  sshd-настройки);
- IP контейнера меняется при его пересоздании → туннель умирает,
  пересоздание ручное (не резолвим имена на каждое соединение —
  сознательное упрощение v1);
- UDP не поддерживается (direct-tcpip — только TCP); локальный конец
  всегда `127.0.0.1` — наружу туннели не выставляются;
- туннель обходит `APP_PASSWORD`: открытый слушатель на `127.0.0.1`
  доступен любому локальному процессу/пользователю без авторизации. Для
  однопользовательской машины приемлемо (как и сам терминал), но это
  ослабление модели безопасности — по реализации задокументировать в
  AGENTS.md (секция «Безопасность»), формулировку предложить на одобрение
  до правки.

**Оценка фазы B:** ~1.5 дня.

## Эпик 11. Веб-поиск для агента (DeepSeek)

**Цель:** инструмент `web_search` у AI-агента — поиск документации, changelog
и актуальных версий прямо в диалоге вместо ответов по памяти. Провайдер —
серверный web search DeepSeek на их Anthropic-совместимом endpoint'е
(проверено вживую 2026-08-19: `POST https://api.deepseek.com/anthropic/v1/messages`
с `tools: [{type: 'web_search_20260209', max_uses}]`, тот же API-ключ,
модели deepseek-v4-flash/pro; ответ — текст + блоки `server_tool_use` /
`web_search_tool_result` с заголовками и URL, `encrypted_content` непрозрачен;
авторизация — `x-api-key` или `Bearer`).

Ключевое архитектурное решение: основной клиент агента не меняется — он как
работал по OpenAI-формату (`/chat/completions`) с любым провайдером, так и
работает. Поиск — отдельный read-only инструмент, чей обработчик делает
один HTTP-вызов к Anthropic-endpoint'у DeepSeek и возвращает агенту
отформатированный текст с источниками.

**Backend:**

- `config.ts`: env `AI_SEARCH_API_BASE` (Anthropic-совместимая база;
  пусто — фича выключена, инструмент модели не объявляется вовсе) и
  `AI_SEARCH_MODEL` (по умолчанию `deepseek-v4-flash` — дешёвая). Ключ
  общий с `AI_API_KEY`.
- `src/ai/web-search.ts` — весь поиск в одном сервисе: чистые функции
  `buildSearchBody` (Anthropic-тело с серверным инструментом
  `web_search_20260209` и `max_uses`), `parseSearchResponse` (текстовые
  блоки + выполненные запросы + источники; `encrypted_content` и thinking
  игнорируются), `formatSearchOutput`, `sanitizeQuery` (схлопывание
  пробелов, лимит 400 символов), `isSearchConfigured`; `searchWeb` —
  fetch с таймаутом 90 с, никогда не бросает, ошибки возвращаются текстом
  (паттерн runTool).
- `tools.ts`: определение `web_search {query}` + имя в `READ_ONLY_TOOLS`;
  `getToolDefs(enabled)` — гейтинг: без конфигурации web_search не
  объявляется (модель его не видит и не может вызвать).
- `agent.ts`: кейс в `runTool` с двойным гейтингом (вызов из старого
  диалога без конфигурации → понятная ошибка), лимит 10 вызовов за запуск
  цикла (каждый — до 3 реальных поисков `max_uses`), сброс счётчика в
  начале `runLoop`; системный промпт дополнительно упоминает поиск, только
  когда он включён. `plan.ts` `toolsForRequest` проходит через
  `getToolDefs()`.
- Класс инструмента — read-only (выполняется автоматически): поиск ничего
  не мутирует на управляемом сервере; в том же классе `security_audit`,
  который тоже ходит в сеть. Нюанс приватности: текст запроса уходит во
  внешний API — отключается целиком через env.

**Frontend:** только метка `web_search: 'Поиск в интернете'` в ToolCard —
рендер tool-карточек и статусов уже универсальный.

**Тесты:** `web-search.test.ts` — билдер тела (формат серверного
инструмента, max_uses), sanitizeQuery, парсер по фикстуре реального ответа
(несколько поисков, источники без title, пустой ответ, отсутствие
encrypted_content в выводе), форматирование, гейтинг getToolDefs; правка
`plan.test.ts` под `getToolDefs`.

**Риски:**

- Качество поиска DeepSeek — среднее (приемлемо для документации);
  endpoint официально документирован с мая 2026, но формат версионирован
  именем инструмента (`web_search_20260209`) — при смене версии имени
  правка в одном месте (`buildSearchBody`).
- Поиск оплачивается токенами модели поиска (отдельной цены нет);
  двойной LLM-вызов (поиск + основной агент) — осознанный компромисс
  ради неизменности основного клиента.
- Провайдер жёстко связан с DeepSeek: другой провайдер без
  Anthropic-совместимого серверного поиска работать не будет (env пустой
  → фича просто выключена).

**Оценка:** ~0.5 дня.

## Эпик 12. Учёт расходов AI — стоимость диалогов, страница «ИИ-расходы»

**Цель:** видеть, сколько стоил каждый диалог агента (бейдж в панели агента и
в истории) и иметь отчёт по дням и проектам (глобальная страница «ИИ-расходы»
в сайдбаре под «Серверы»). Оба API (чат и веб-поиск) уже возвращают `usage`
с токенами — код его отбрасывал; теперь он захватывается, тарифицируется и
пишется в журнал. Подробный план — `docs/ai-costs-plan.md`, детали —
`docs/architecture.md` (раздел «Учёт расходов AI»).

**Backend:**

- `src/ai/client.ts`: `stream_options: { include_usage: true }`, usage
  читается из SSE независимо от `choices` (финальный usage-чанк — с пустым
  `choices`) и из non-stream `data.usage`; возврат `{ message, usage? }`
  (`TokenUsage` — prompt/cached/completion/reasoning, числа только конечные
  ≥ 0, инварианты cached ⊂ prompt и reasoning ⊂ completion держатся клампом).
- `src/ai/pricing.ts` (новый): дефолтная таблица цен USD за 1M токенов
  (gpt-4.1/-mini/-nano, gpt-4o/-mini, deepseek-chat/-reasoner, DeepSeek V4 —
  deepseek-v4-flash 0.22/0.007/0.66 и deepseek-v4-pro 0.66/0.022/1.98,
  off-peak; пик ×2) + оверрайд `data/ai-prices.json` (мерж по имени модели;
  битый файл — warn + дефолты, без corrupt-guard: это справочник; модель
  без уверенной цены — честный unpriced). Формула:
  `(prompt − cached)·input + cached·cachedInput + completion·output +
  searchRequests·webSearchPerRequestUsd`; без `cachedInput` кэш — по цене
  `input`; слагаемое поиска только при заданном тарифе — у DeepSeek поиск
  оплачивается токенами модели поиска (отдельной цены за запрос нет).

  которым нужны права (как в аудите).
- Журнал unit'а — компонент просмотрщика из эпика 14; при скрытой вкладке

**Тесты:** `systemd.test.ts` — парсеры на фикстурах (имена с `@`, masked,
not-found, пустой вывод, длинные описания с пробелами), слияние двух

### Эпик 16. «Что съело диск» — навигатор по `du`

> **Статус: реализован (2026-08-23).** План и решения — в
> `docs/disk-usage-plan.md`; реализация — `server/src/services/disk-usage.ts`,
> `server/src/routes/disk-usage.ts`, `web/src/components/DiskUsageModal.tsx`;
> тесты — `server/test/disk-usage.test.ts`. Осознанные отклонения от текста
> ниже — как в плане: `-k` вместо `-B1` (BusyBox не знает `-B`, портируемость
> как у `df -P -k`); stderr du не глушится, а ловится — иначе пометку
> «доступно не всё» нечем подтвердить; инструмент агента `disk_usage`
> собирает команды сервисом (минуя deny-лист `exec_readonly`, как
> `security_audit`).

**Цель:** «Обзор» показывает диск на 92% и не даёт следующего шага.
Проваливание по каталогам с размерами и топ крупнейших файлов.

**Backend:**
- `src/services/disk-usage.ts`.
  `GET /api/disk-usage?profileId=&path=` — `du -x -d1 -B1 -- <shq(path)>
  2>/dev/null | sort -rn`. `-x` не выпускает обход за пределы файловой
  системы (иначе `/proc`, сетевые монтирования и вложенные диски портят
  картину), `-B1` — байты, стабильный парсинг вместо `-h`.
- `GET /api/disk-usage/files?profileId=&path=&limit=` — `find <path> -xdev
  -type f -printf '%s\t%p\n' | sort -rn | head -<limit>`; фолбэк на
  `stat`-вариант при отсутствии `-printf` (BusyBox).
- Таймаут 60 с (по большому дереву `du` идёт долго), лимит вывода как у
  `exec`, `assertSafePath`.
- Всё read-only → инструмент агента `disk_usage` по правилам расширения
  набора (`tools.ts` + `READ_ONLY_TOOLS` + `runTool`): «почему кончился
  диск» — типовой запрос к агенту.

**Frontend:**
- На «Обзоре» у каждой строки диска — кнопка «Что занимает»: панель с
  точкой монтирования как корнем.
- Подкаталоги с долей от родителя (полоска — переиспользовать `Meter`),
  клик — вглубь, хлебные крошки — назад; переключатель «каталоги /
  крупнейшие файлы»; «Открыть в файлах» — переход в FilesPage по пути.

**Тесты:** `disk-usage.test.ts` — парсер `du -B1` (табы, пути с пробелами,
битые строки отбрасываются), сортировка и доли, сборка команд и
экранирование, фолбэк `find`.

**Риски:** `du` по `/` на большом диске — минуты; спасают `-x`, таймаут и
старт от точки монтирования, а не от корня. Без sudo часть каталогов
недоступна — `2>/dev/null` плюс пометка «доступно не всё» в UI, чтобы
цифры не выглядели враньём.

**Оценка:** ~1 день.

> прецедент `stream-limits`); вход в действия — кнопка «⋯» + модалка, а не
> dropdown в строке (общего dropdown-компонента в проекте нет, модалка уже
> переиспользуется); HUP показывается в UI как «Перечитать конфиг (HUP)»;
> категория ошибки «утилиты нет на сервере» (BusyBox без `renice`, образ без
> `/bin/kill` под `sudo --`) → 400 вместо 502 «Сервер недоступен»; после
> мутации — инвалидация кэша метрик (`invalidateMetricsCache`), иначе
> «Обзор» до 2 с показывал бы убитый процесс.

**Цель:** таблица топ-процессов уже есть (`OverviewPage.tsx`), действий
нет — цикл «нашёл пожирателя → убил» не замыкается.

**Backend:**
- `POST /api/processes/:pid/signal` `{signal}` — белый список
  `TERM|KILL|HUP`; pid — целое > 1. Запрет `0`, `1` и отрицательных
  обязателен: `kill -TERM -1` кладёт всё, до чего дотянется. Команда —
  `kill -<sig> -- <pid>`.
- `POST /api/processes/:pid/renice` `{nice}` (−20..19) — понизить приоритет
  вместо убийства, когда процесс нужен; повышение требует root, отказ —
  понятной ошибкой.
- Sudo — по схеме эпика 13 (чужие процессы без прав не убить).
- Агенту инструмент не даём: `kill`/`pkill` уже в deny-листе `guard.ts` —
  не ослаблять.

**Frontend:** в строке процесса — меню «Завершить (TERM) / Убить (KILL) /
Понизить приоритет»; модалка показывает команду и владельца; после действия
немедленный refetch метрик.

**Тесты:** `processes.test.ts` — валидация pid (0, 1, −1, нечисло, строка) и
сигнала, сборка команды, диапазон `nice`.

**Риски:** убийство системного или чужого процесса — предупреждение в
модалке, когда владелец не совпадает с пользователем профиля или pid < 100.
Произвольный сигнал строкой не принимаем.

**Оценка:** ~0.5 дня.

  `db-connections.ts`: zod, атомарная запись tmp+rename, поведение на битом

- Раздел «Команды» на странице «Серверы» — там уже сводка по всем профилям,

- Результаты — аккордеон по серверам: код возврата бейджем, stdout/stderr

- Подтверждение перед запуском с явным перечислением серверов: запуск на

**Тесты:** `snippets.test.ts` — стор (CRUD, валидация, битый JSON,
частичное обновление), маппинг `Promise.allSettled` в ответ (отказ профиля,
таймаут), лимит профилей, выбор `snippetId` vs явной команды.

**Риски:** массовый запуск деструктивной команды — подтверждение со списком
целей; большие выводы — лимит `exec` (2 МБ) на профиль и обрезка в UI.

**Оценка:** ~1.5 дня.

### Эпик 19. Обновления пакетов

> **Реализовано (2026-08-23).** План — `docs/packages-plan.md`. Шаг 0 —
> опциональный `stdin` у `execStream` (пароль в `sudo -S` первой строкой
> канала) и вынос sudo-зонда в общий `services/sudo.ts`. Read-only часть
> (снимок обновлений, карточка и раздел на «Обзоре») и применение
> (`POST /api/packages/apply` со зондом до стрима и живым выводом через
> LogViewer `buildRequest`/`oneShot`) — отдельными коммитами. Инструмент
> агента не заводился; применение — только стримом с подтверждением.

**Цель:** видеть, что на сервере есть обновления и нужен ли рестарт, не
заходя в терминал.

**Backend:**
- `src/services/packages.ts`; детект менеджера (`apt-get`/`dnf`/`yum`/`apk`)
  одним exec.
- `GET /api/packages/updates?profileId=` — apt: `apt list --upgradable`;
  dnf: `dnf -q check-update` (**код 100 = есть обновления, не ошибка**);
  apk: `apk version -l '<'`. `apt-get update` не запускаем — он мутирует
  индексы и требует прав.
- Признаки рестарта: `/var/run/reboot-required` (+ `.pkgs`), для RHEL —
  `needs-restarting -r`, если есть.
- Возраст индекса apt (mtime `/var/lib/apt/periodic/update-success-stamp`) —
  показываем рядом с числом обновлений.
- Кэш 60 с: список меняется редко, команда не мгновенная.
- Применение (`apt-get upgrade -y` и аналоги) — мутация: sudo, обязательное
  подтверждение, вывод стримом (`execStream`) в просмотрщик из эпика 14.
  **Отдельным коммитом после read-only части** — read-only полезна сама по
  себе, применение несёт риск.

**Frontend:** бейдж на «Обзоре» («12 обновлений · нужен рестарт»), раздел со
списком пакетов (текущая → доступная версия), «Обновить всё» с
подтверждением и живым выводом.

**Тесты:** `packages.test.ts` — парсеры apt/dnf/apk на фикстурах («нет
обновлений», код 100 у dnf, предупреждение apt про нестабильный CLI,
многострочные записи apk), детект менеджера, парсинг reboot-required.

**Риски:** без свежего `apt-get update` картина устаревшая — отсюда возраст
индекса в UI. Обновление может утащить sshd или сеть — предупреждение в
подтверждении. Долгий вывод — только стрим, не буфер.

**Оценка:** ~1 день (read-only часть ~0.5).

### Эпик 20. Алерты по порогам

> **Статус: реализовано** (2026-08-23, план — `docs/alerts-plan.md`;
> дополнение — кнопка «Отмена» в модалке настроек. Правки по ревью:
> `message` заполняется всегда — алерт в зоне гистерезиса показывает
> текущую цифру; фоновый опрос в скрытой вкладке только при включённых
> браузерных уведомлениях; клиентский merge покрыт тестами раннером
> сервера). Ключевые решения:
> ответ `/api/alerts` — состояния всех правил с `value`/`threshold`
> (гистерезису на клиенте нужно значение, а не только факт срабатывания);
> `server-down` — булево правило без дельты; при включённых алертах опрос
> продолжается и в скрытой вкладке (браузерный троттлинг ~1/мин — честный
> ритм фоновой проверки), первая синхронизация и смена настроек — тихий
> re-baseline активного набора.

**Цель:** узнавать про «диск кончился» и «сервер недоступен», не
разглядывая вкладку.

**Backend:**
- Данные уже есть: сайдбар опрашивает `/api/overview` раз в 10 с
  (`App.tsx:31`, `SERVER_STATUS_POLL_MS`), метрики приходят тем же ответом.
- `src/services/alerts.ts` — чистая `evaluateAlerts(overview, thresholds)`
  → `{profileId, kind, severity, message}[]`; правила: сервер недоступен,
  диск ≥ порога (90%), память ≥ порога, `load1 / cores` ≥ порога.
  Вычисление держим на сервере намеренно: в `web/` нет тест-раннера
  (`web/package.json` — только dev/build/preview), а правило проекта —
  unit-тесты на всю новую логику. Заводить vitest во фронте ради одной
  функции не стоит.
- `GET /api/alerts?profileId=&thresholds=…` поверх кэша overview — новых
  SSH-вызовов не добавляет.

**Frontend:**
- Дедупликация и гистерезис — на клиенте: алерт срабатывает на переходе
  состояния и молчит, пока значение не упадёт ниже порога минус дельта
  (иначе на границе 90% уведомления посыплются каждые 10 с).
- Колокольчик в сайдбаре со счётчиком и списком, подсветка проблемного
  профиля; браузерное `Notification` — опционально, включается явно
  (разрешение запрашиваем по клику, не при загрузке).
- Пороги и включение — `localStorage`: это настройка клиента.

**Тесты:** `alerts.test.ts` — правила на фикстурах overview (недоступный
сервер, несколько дисков, отсутствующие метрики `null`, деление на `cores`
при неизвестном числе ядер), границы порогов.

**Риски:** работает только при открытой вкладке — осознанное ограничение
локального инструмента; пуши требуют серверной подписки, это другой класс
задачи. Не превращать в систему мониторинга: пороги простые, история не
персистится.

**Оценка:** ~0.5–1 день.

## Чего не делаем (осознанно)

Фиксируется, чтобы не возвращаться к этим идеям на каждом планировании:

- **Персистентная история метрик в БД.** Это Netdata/Prometheus, а не
  ssh-commander. История остаётся in-memory (`metrics-history.ts`).
- **Пользователи, роли, RBAC.** Инструмент однопользовательский по дизайну
  (localhost-only, один `APP_PASSWORD`, пароли открытым текстом в `data/`) —
  роли создали бы иллюзию изоляции внутри одного trust domain.
- **Kubernetes.** Другая модель и объём, отдельный инструмент.
- **Интеграции с мессенджерами (уведомления в Telegram и т.п.).** Требуют
  сервера, который живёт без открытой вкладки — противоречит локальности.
- **Git-UI и diff-редактор во вкладке файлов.** Есть терминал; выигрыш не
  покрывает объём.
