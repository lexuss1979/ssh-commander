# План: порядок «плашка подтверждения → текст» у агента + показ команды в плашке

> Эпик из бэклога (`docs/roadmap.md`): объединяет два пункта —
> «Порядок «плашка подтверждения → текст» у агента» и «Показ команды в плашке
> подтверждения (высокий приоритет)». Статус: реализовано (плашка
> `.pending-bar`, порядок «текст → карточки инструментов» — см.
> `docs/architecture.md`).
> Дата плана: 2026-08-20 (обновлён после ревью). Только фронтенд (`web/`):
> сервер и WS-протокол не меняются — `args` в `tool_pending` уже приходят.

## Проблема

При запросе разрешения у агента карточка подтверждения появляется в ленте
раньше поясняющего текста модели — текст «догоняет» стримом. Пользователь
не понимает, где ждать кнопку: «просят разрешить, а где подтверждать —
не видно». Вдобавок плашка неинформативна: только имя инструмента
(«Выполнить команду») — что именно запустит агент, не видно
(`argPreview` в ToolCard выводится лишь в статусе `running`).

## Диагноз (по коду)

Две независимые причины, обе на фронтенде:

1. **Инвертированный порядок внутри сообщения** — `web/src/pages/AgentPage.tsx`
   (рендер `messages.map`, ~строки 657-671): в `chat-row` блок `tool-calls`
   рендерится ВЫШЕ текстового пузыря (`bubble`). Хронологически текст
   пояснения стримится первым (`server/src/ai/client.ts` отдаёт `onToken`
   по мере генерации, карточки добавляются после финализации сообщения
   событием `tool_pending`/`tool_start`), но в DOM плашка разрешения
   оказывается над текстом — читается «сначала разрешение, потом текст».
2. **Кнопки внутри скроллируемой ленты** — при появлении `tool_pending`
   авто-скролл уходит в конец строки сообщения, а плашка стоит выше текста:
   при длинном пояснении кнопки оказываются за пределами вьюпорта; если
   пользователь прокрутил вверх — плашку вообще надо искать в ленте.

## Ключевой факт: одновременно висит максимум одно подтверждение

Сервер обрабатывает вызовы инструментов строго последовательно
(`for…await` в `runLoop`, `server/src/ai/agent.ts:500-566`): `tool_pending`
отправляется для одного вызова, и цикл ждёт решения, прежде чем слать
следующий. Модель может вернуть пачку из 2-3 мутирующих вызовов в одном
ответе — пользователь получает очередь подтверждений **подряд**, но не
одновременно. При переподключении WS старая сессия убивается целиком
(`attachAgent` → `existing.stop()`, все pending резолвятся `aborted`) —
«осиротевших» подтверждений не бывает.

Следствия для дизайна:

- PendingBar показывает **ровно один** вызов — никакого map по pending,
  никаких стопок плашек;
- при очереди вызовов плашка после `tool_result` почти мгновенно заменяется
  следующим `tool_pending` — это нормально; **никаких анимаций
  появления/исчезновения**, только мгновенная смена содержимого (без моргания
  размеров: высота строки кнопок фиксированная).

## Решение

### 1. Порядок «текст → карточки» в сообщении

В рендере `chat-row` переставить блоки местами: сначала `{m.content && bubble}`,
потом `tool-calls`. Пояснение читается до карточек, плашка оказывается внизу
сообщения — рядом с закреплённой плашкой после авто-скролла. История диалога
рендерится тем же компонентом (`messagesToViews` → тот же маппинг), порядок
меняется согласованно.

### 2. Закреплённая плашка подтверждения (PendingBar) у поля ввода

Новый слот рядом со слотом PlanCard (между `.agent-messages` и `.agent-input`,
вне скроллируемой области — всегда видима). Если одновременно активны план
и подтверждение (теоретически невозможно: `approve_plan` запускает цикл,
который только потом доходит до tool-вызовов), слоты идут друг над другом,
PlanCard сверху.

Содержимое плашки:

- **строка**: статус-точка + лейбл инструмента + бейдж сервера (класс
  `.tool-server`) + короткий preview главного аргумента (команда/путь/запрос,
  mono, обрезка ~80 символов — переиспользуем `mainArgPreview`, см. п. 4) +
  кнопка раскрытия + кнопки «Подтвердить» / «Отклонить»;
- **раскрытие (пункт бэклога «Показ команды в плашке подтверждения»)**:
  кнопка «Подробнее»/«Скрыть» разворачивает под строкой mono-блок
  (`.args-view`-стиль) с **полным главным аргументом** — команда `exec`
  целиком (многострочная, без обрезки), путь `write_file` (+ размер
  содержимого), docker-действие с целью, текст `write_memory`. Если главного
  аргумента нет или хочется деталей — fallback на JSON `args`, как в
  `tool-details` карточки. Раскрытие не должно раздувать панель бесконечно:
  блок с `max-height` (~200 px) и внутренним скроллом. Состояние раскрытия
  сбрасывается при смене pending-вызова;
- после клика кнопки блокируются, статус «выполняется…» — до прихода
  `tool_result` (для мутирующих инструментов сервер не шлёт промежуточного
  `tool_start`, выполнение может занять время);
- **клик по плашке** (по строке, не по кнопкам) скроллит ленту к
  соответствующей карточке в сообщении (`scrollIntoView`) — плашка остаётся
  привязанной к контексту, полный текст пояснения и карточка одним кликом.

### 3. Кнопки из карточки в ленте убираем

Единая точка решения — закреплённая плашка (паттерн PlanCard: кнопка
«Выполнить» тоже живёт внизу, а не в ленте). Карточка в ленте в статусе
`pending` показывает лейбл, бейдж сервера, preview главного аргумента
(выравниваем с running: pending тоже показывает `argPreview`) и статус
«ждёт подтверждения · кнопки — внизу панели», после решения —
«выполняется…». Раскрытие «Детали» в карточке ленты оставляем как есть —
оно становится доступно и для pending (сейчас рендерится только не-pending
веткой).

Локальный `decided`-стейт ToolCard заменяется поднятым в AgentPage:
`decidedCalls: Set<callId>` — клик добавляет callId, `tool_result` убирает,
смена диалога сбрасывает. PendingBar читает его для блокировки кнопок.

### 4. Общие хелперы

Вынести из ToolCard в модульные функции:

- `toolLabel(tool)` — словарь лейблов инструментов + спец-кейс
  `connect_server` («Подключить «X» к диалогу?»);
- `mainArgPreview(args)` — первый непустой строковый аргумент из
  `query/command/path/target/containerId`;
- `fullArgText(tool)` — полный текст главного аргумента для раскрытия
  (для `write_file`/`write_memory` — путь + сводка по содержимому,
  для остальных — значение главного аргумента целиком; fallback —
  pretty-JSON `args`).

Используются и карточкой в ленте, и PendingBar — без дублирования.

### 5. CSS (`web/src/styles.css`)

Класс `.pending-bar` по образцу `.plan-card`: flex, `margin: 0 12px 8px`,
рамка `var(--warn)` (подтверждение = внимание), фон `var(--bg-raised)`,
темы через CSS-переменные; подстрока превью — mono с ellipsis; раскрытый
блок — mono, `max-height` + `overflow-y: auto`, white-space: `pre-wrap`
(многострочные команды читаемы). Удалить ставший неиспользуемым
`.tool-actions-mini`, если он больше нигде не встречается.

## Затрагиваемые файлы

- `web/src/pages/AgentPage.tsx` — порядок рендера, PendingBar,
  `decidedCalls`, общие хелперы;
- `web/src/styles.css` — `.pending-bar`;
- `docs/roadmap.md` — оба пункта бэклога («Порядок «плашка подтверждения →
  текст»» и «Показ команды в плашке подтверждения») перечеркнуть +
  «Реализовано» (по прецеденту мульти-серверного режима);
- `AGENTS.md` — описание AgentPage дополнить: закреплённая плашка
  подтверждения у поля ввода (кнопки только там, раскрытие полного
  аргумента, клик скроллит к карточке в ленте), порядок
  «текст → карточки инструментов» в сообщении.

Без изменений: сервер, WS-протокол, «Спросить агента», индикатор
`agent-dot` в сайдбаре (жёлтая точка уже сигнализирует о pending).

## Проверки

- `cd web && npm run build` (tsc строгий: `noUnusedLocals` поймает остатки
  рефакторинга);
- `cd server && npm run build && npm test` — сервер не меняется, прогон
  по правилам «перед сдачей»;
- ручной сценарий:
  - длинное пояснение + мутирующий вызов → плашка всегда видна у поля
    ввода, текст читается до кнопок;
  - в плашке виден preview команды; «Подробнее» показывает команду целиком
    (многострочную — с переносами, длинную — со скроллом блока);
  - клик по плашке скроллит ленту к карточке;
  - после клика «Подтвердить» — «выполняется…», после `tool_result` плашка
    исчезает; при очереди из 2-3 вызовов плашка сменяется следующим
    подтверждением без моргания;
  - `connect_server` показывает «Подключить «X» к диалогу?»;
  - история диалога рендерится в новом порядке.
