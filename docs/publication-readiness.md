# Готовность первого релиза

Дата проверки: 2026-09-10. Версия: `v0.1.0`.
Это отчёт проверок, а не гарантия отсутствия уязвимостей. Владелец согласовал выпуск
и открытие репозитория 2026-09-10. Факт публикации и исходники версии проверяются
на [странице релиза](https://github.com/lexuss1979/ssh-commander/releases/tag/v0.1.0).

## Зависимости

- `server`: Vitest `3.2.7` заменён на `4.1.11`, включая `@vitest/mocker`.
  Исправление опубликовано в [уведомлении Vitest](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9).
  Выбрана исправленная ветка 4, совместимая с Node 20; переход на 5 потребовал бы Node 22.12+.
  Требования описаны в руководствах миграции [Vitest 4](https://v4.vitest.dev/guide/migration) и [Vitest 5](https://vitest.dev/guide/migration/).
- Vite `7.3.6`, уже использовавшийся тестами транзитивно, явно указан как devDependency сервера.
  Это удерживает совместимую ветку peer dependency при разрешении зависимостей.
  Фронтенд остался на Vite `6.4.3`; зависимости runtime не обновлялись.
- `web`: транзитивный `js-yaml` обновлён с `4.3.1` до `4.3.2` внутри допустимого диапазона ESLint.
  Исправление: [уведомление js-yaml](https://github.com/nodeca/js-yaml/security/advisories/GHSA-2883-xcg3-v3hh).
- `npm audit --audit-level=low` в обоих каталогах: **0 уязвимостей**, включая devDependencies.
- Обычный `npm ci` воспроизводит оба lock-файла. Для первоначального разрешения обновления
  использовался npm 11: npm 10.9.4 падал внутри Arborist (`edgesOut`).
  Для установки готового lock-файла обновление npm не требуется.

Базовый проверенный HEAD: `c24627d8658f4ed6c93fd8061ceed90922670051`.
После `git fetch origin --tags` проверены все 167 достижимых коммитов всех refs,

Использован Gitleaks `8.30.1`, образ

Сканирование выполнено локально в Docker с `--network none`, репозиторий смонтирован read-only.
Вывод и JSON-отчёты редактируются через `--redact=100`.

Первичный прогон дал 15 срабатываний, каждое разобрано:

| Файл | Число | Причина |
|---|---:|---|
| `server/test/redact.test.ts` | 2 | Неполная фикстура OpenSSH и искусственный API-ключ для проверки удаления секретов |

| `server/test/keys.test.ts` | 2 | Неполная фикстура OpenSSH, повторённая в merge-коммите |

Демонстрационный TLS-ключ является настоящим ключом тестового сертификата,
а не ложным распознаванием формата. Он предназначен только для одноразового стенда;
использовать его для реальной инфраструктуры нельзя.

В [.gitleaksignore](../.gitleaksignore) внесены только точные fingerprints
`commit:file:rule:line` этих исторических срабатываний. Исключений по всему файлу,
каталогу тестов или целому коммиту нет. Повторный прогон: **0 неразобранных срабатываний**.
Новые срабатывания должны разбираться отдельно, а не автоматически добавляться в исключения.

### Повторная проверка

Из корня репозитория, PowerShell (Docker должен быть запущен):

```powershell
git fetch origin --tags
git rev-parse --is-shallow-repository
git rev-list --all --count
docker run --rm --network none --mount "type=bind,source=$($PWD.Path),target=/repo,readonly" -w /repo -e GIT_CONFIG_COUNT=1 -e GIT_CONFIG_KEY_0=safe.directory -e GIT_CONFIG_VALUE_0=/repo zricethezav/gitleaks@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f git /repo --log-opts="--all --full-history -m" --redact=100 --no-banner
```

Если `--is-shallow-repository` вернул `true`, сначала нужно получить полную историю.
Прогонять после финального коммита и непосредственно перед открытием репозитория.
В обычном режиме Gitleaks пропускает merge-diff: флаг `-m` здесь намеренный.
Команды и опции: [документация Gitleaks](https://github.com/gitleaks/gitleaks#usage).

- `docker compose up -d --build`: успешно, production-контейнер перезапущен;
  `http://127.0.0.1:8080` возвращает HTTP 200 с HTML приложения.

  проверены onboarding, создание SSH-профиля, терминал, очистка диска агентом с подтверждением
  и установка Nginx на чистом тестовом SSH-сервере до HTTP 200 и открытия сайта в браузере.
